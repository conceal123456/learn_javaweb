## 2. 知识点精讲

### 2.1 Axios 与 request.js 封装

**① 讲义怎么说** —— "一、1 安装 axios 封装前后端对接数据工具"给的命令是 **`npm i axios -S`**；紧接着"2. 按下面进行一系列操作，粘贴代码"点明封装的作用：**"统一创建实例、请求头配置、响应解析、全局错误提示，之后所有接口都导入这个 request 对象发请求。"**

**② 一句话讲透** —— 不封装的话，每个页面都要自己写 `axios.get('http://localhost:8080/...')`、自己判断状态码、自己弹错误框，十个页面就是十套写法，后端一换端口就得全项目搜一遍。`request.js` 相当于给全项目开了一个"收发室"：包裹统一从这里寄出，地址前缀统一贴（`baseURL`），外包装统一（`Content-Type`），回来的箱子统一拆（`response.data`），出了问题统一报警（`ElMessage`）。拦截器的本质，是 axios 在发请求前、收响应后各留的一个钩子：钩子拿到配置或响应，改完再往下传；不写钩子，这些活儿就只能散落在每一个页面里。以后换后端地址只动一行，加登录令牌也只在拦截器里加一次。

**③ 示例代码** ——

```js
import axios from "axios";
import {ElMessage} from "element-plus";

const request = axios.create({
    baseURL: 'http://localhost:8080',
    timeout: 30000  // 后台接口超时时间
})
// request 拦截器
// 可以自请求发送前对请求做一些处理
request.interceptors.request.use(config => {
    config.headers['Content-Type'] = 'application/json;charset=utf-8';
    return config
}, error => {
    return Promise.reject(error)
});

// response 拦截器
// 可以在接口响应后统一处理结果
request.interceptors.response.use(
    response => {
        let res = response.data;
        // 兼容服务端返回的字符串数据
        if (typeof res === 'string') {
            res = res ? JSON.parse(res) : res
        }
        return res;
    },
    error => {
        // 网络错误 / 跨域被拦截时 error.response 是 undefined，先做保护判断
        const status = error.response ? error.response.status : null
        if (status === 404) {
            ElMessage.error('未找到请求接口')
        } else if (status === 500) {
            ElMessage.error('系统异常，请查看后端控制台报错')
        } else if (status === null) {
            ElMessage.error('无法连接后端服务，请检查后端是否启动或跨域是否配置成功')
            console.error(error.message)
        } else {
            console.error(error.message)
        }
        return Promise.reject(error)
    }
)
export default request
```

**④ 逐行拆解** ——
- `axios.create({...})` 不是发请求，而是造一个"预设好配置的实例"。之后 `request.get('/employee/selectPage')` 的真实地址是 `baseURL + url`，页面里只写半截路径。
- `timeout: 30000` 单位是毫秒，超时走的是 `error` 分支，不会返回 `code:500`，别把"超时"和"后端报错"混为一谈。
- 请求拦截器里设 `Content-Type: application/json;charset=utf-8`：POST/PUT 的 JSON 体能不能被 `@RequestBody` 认出来，全靠这个头；GET 没有请求体，这个头对它没有影响。
- 响应拦截器的成功分支只 `return response.data`：axios 原本返回的是 `{data, status, headers, config}` 这层壳，拆掉壳以后页面里的 `res` 直接就是后端 `Result` 对象，所以取列表写 `res.data.list`，不是 `res.data.data.list`。
- `typeof res === 'string'` 这层判断兼容"后端直接返回字符串"的老接口，能解析就解析，解析不了原样返回。
- `error.response ? ... : null` 是仓库比讲义多出来的一层保护：跨域被浏览器拦下、后端没启动、断网时，`error.response` 根本不存在，照讲义原样写 `error.response.status` 会先抛一个 `TypeError`，把真正的错误盖住。
- `export default request` 配合 `import request from '@/utils/request.js'`，全项目共用同一个实例。

**⑤ 在你仓库里** —— 封装本体在 `D:\my-project\xm-pro\vue\src\utils\request.js`：第 4~7 行是实例与 `baseURL`，第 10~15 行是请求拦截器，第 19~43 行是响应拦截器（第 30 行就是那层判空保护）。调用方看 `D:\my-project\xm-pro\vue\src\views\Employee.vue` 第 92 行引入、第 104~115 行的 `load()`；讲义里那个测试实例在 `D:\my-project\xm-pro\vue\src\views\Home.vue` 第 17 行、第 24~28 行。

**⑥ 常见坑** —— ① 页面拿到 `res` 却是 `undefined` → 拦截器里写成了 `return response`，或者自己又包了一层 → 先 `console.log(res)` 看结构，再决定写 `res.data` 还是 `res.data.data`。② 后端明明启动了，控制台却报 `Cannot read properties of undefined (reading 'status')` → 讲义版拦截器没有判空，跨域时 `error.response` 不存在 → 换成仓库第 30 行的写法。③ 改了 `baseURL` 请求还打旧地址 → 页面里绕过封装直接 `import axios` 了 → 全局搜 `axios.`，只保留 `request.js` 里那一处。

**⑦ 自测** —— 页面里 `then(res => ...)` 拿到的 `res`，为什么取后端数据写 `res.data.list`，而不是 `res.data.data.list`？

<details><summary>展开解析</summary>

因为响应拦截器已经 `return response.data`，把 axios 的响应壳（`status` / `headers` / `config` / `data`）拆掉了，`res` 直接就是后端返回的 `Result` 对象：`{code, msg, data}`。所以 `res.data` 是 `Result.data`，列表就在里面。如果拦截器返回的是整个 `response`，那才需要 `res.data.data.list`——**先看拦截器，再决定拆几层**。

</details>

### 2.2 跨域与 CorsConfig

**① 讲义怎么说** —— "一、4 解决跨域问题：在 Springboot 里面设置统一的跨域处理"，做法是"在指定位置新建类：**CorsConfig**"，并给了整段 `@Configuration` + `CorsFilter` 的代码，四个 `addAllowed...` 后面分别标着 1、2、3、4。

**② 一句话讲透** —— 浏览器的同源策略像小区门禁：前端住在 5173 号楼，后端在 8080 号楼，虽然都叫 localhost，端口不同就算两个小区。浏览器允许大家把信送过去，但不许把回信带回来，于是控制台报 CORS，而后端日志显示接口其实执行了。解法是后端在响应头里盖一个章 `Access-Control-Allow-Origin`，浏览器看见章才放行。`CorsFilter` 就是站在所有 Controller 前面的门卫，统一盖章；对 PUT、DELETE、JSON 这种"非简单请求"，浏览器还会先派一个 OPTIONS 探路，门卫也得答得上来。预检先问"我能不能用 PUT 发 JSON"，后端答"可以"，真正的请求才会发出——所以跨域出问题时，常常是请求根本没到 Controller。

**③ 示例代码** ——

```java
package com.example.common;

import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.web.cors.CorsConfiguration;
import org.springframework.web.cors.UrlBasedCorsConfigurationSource;
import org.springframework.web.filter.CorsFilter;

/**
 * 跨域配置
 */
@Configuration
public class CorsConfig {

    @Bean
    public CorsFilter corsFilter() {
        UrlBasedCorsConfigurationSource source = new UrlBasedCorsConfigurationSource();
        CorsConfiguration corsConfiguration = new CorsConfiguration();
        corsConfiguration.addAllowedOrigin("*"); // 1 设置访问源地址
        corsConfiguration.addAllowedHeader("*"); // 2 设置访问源请求头
        corsConfiguration.addAllowedMethod("*"); // 3 设置访问源请求方法
        source.registerCorsConfiguration("/**", corsConfiguration); // 4 对接口配置跨域设置
        return new CorsFilter(source);
    }
}
```

**④ 逐行拆解** ——
- `@Configuration` 告诉 Spring 这是一个配置类，启动时扫描并执行里面的 `@Bean` 方法；类必须放在启动类同包或子包下，否则扫描不到。
- `@Bean` 把 `CorsFilter` 注册成容器里的 Bean，Spring Boot 会把它挂进 Servlet 过滤器链，位置在 `DispatcherServlet` **之前**。
- `UrlBasedCorsConfigurationSource` 是"按路径配规则"的注册表，第 4 步 `registerCorsConfiguration("/**", ...)` 表示所有接口都套这份规则。
- `addAllowedOrigin("*")` 允许任何来源发起请求。教学项目够用；将来如果要在请求里带 Cookie，`*` 就不合法了，必须写具体域名。
- `addAllowedHeader("*")` 放行任意请求头。少了这一条，带 `Content-Type: application/json` 的预检会被拒。
- `addAllowedMethod("*")` 放行 GET/POST/PUT/DELETE/OPTIONS。只配 GET/POST 的话，编辑保存的 PUT 会在预检阶段就失败。
- 返回 `new CorsFilter(source)` 而不是在 Controller 上贴 `@CrossOrigin`：过滤器在进入 Spring MVC 之前就处理 OPTIONS 并直接返回，连"接口不存在"的 404 响应也能带上跨域头。

**⑤ 在你仓库里** —— 配置类在 `D:\my-project\xm-pro\springboot\src\main\java\com\example\common\CorsConfig.java` 第 13~24 行，四个 `addAllowed` 正好对应讲义标注的 1~4。它保护的前端在 `D:\my-project\xm-pro\vue\src\utils\request.js` 第 5 行，`baseURL` 指向 8080；前端 dev server 默认起在 5173（`D:\my-project\xm-pro\vue\vite.config.js` 第 18~23 行只配了 watch，没改端口，用的就是默认值）。

**⑥ 常见坑** —— ① 浏览器红字报 CORS，可后端控制台显示 SQL 已经执行、数据也查到了 → 响应头没盖章，浏览器把回信扔了 → 加 `CorsConfig` 并**重启后端**。② GET 正常，一保存（PUT）或一删除（DELETE）就跨域 → 预检 OPTIONS 没被允许 → `addAllowedMethod("*")`，至少要把 PUT/DELETE/OPTIONS 补上。③ 配置类写了还是不生效 → 包放在 `com.example` 之外，启动类根本扫不到 → 确认路径是 `com/example/common/CorsConfig.java`，改完重启一次。

**⑦ 自测** —— 浏览器地址栏直接敲 `http://localhost:8080/employee/selectAll` 能返回 JSON，页面里 axios 调同一个地址却报 CORS，为什么？

<details><summary>展开解析</summary>

地址栏输入是"导航请求"，不受同源策略约束；axios 是脚本发起的跨域请求，浏览器必须检查响应头里有没有 `Access-Control-Allow-Origin`。**能返回 JSON 说明接口本身是通的**，问题只在跨域配置或没重启。所以看到 CORS 别去改 SQL，先看响应头。

</details>

### 2.3 查询全部与条件查询

**① 讲义怎么说** —— "三、条件查询"第 1 条是**"实现按姓名这个条件进行查询"**；第 3 条写：**"在查询框中输入要查询的姓名，点'查询'，系统就会把姓名放到 Http 请求中"**；第 4 条紧接着问：**"此时，前端已经发送了请求，那问题是：后端如何拿到这个请求，接下来进行如下处理"**。

**② 一句话讲透** —— 查询像点菜：前端把"我要姓名含 thc 的"写在 URL 的 `?name=thc` 上，相当于在菜单边上贴张便签；后端不用逐字去抠 URL，Spring MVC 看到方法参数是个 `Employee` 对象，就按"参数名等于属性名"自动调用 `setName("thc")`，把便签内容填进对象。于是 Controller 拿到的是一个"只有 name 有值、其他字段全是 null"的 Employee——它既是查询条件，也是动态 SQL 的开关：有值就拼这段条件，没值就跳过。查询全部和条件查询因此共用一个接口，后面分页也复用同一个实体。记住一句话：URL 上每一个键值对，都是给实体属性准备的一格抽屉，名字对上就自动放进去。

**③ 示例代码** ——

```java
@RestController
@RequestMapping("/employee")
public class EmployeeController {

    @Resource
    private EmployeeService employeeService;

    /**
     * 查询所有的数据
     */
    @GetMapping("/selectAll")
    public Result selectAll(Employee employee) {
        List<Employee> list = employeeService.selectAll(employee);
        return Result.success(list);
    }
}
```

**④ 逐行拆解** ——
- `@RestController` 等于 `@Controller` 加 `@ResponseBody`，方法返回的 `Result` 会被 Jackson 直接转成 JSON，不会去找页面。
- 类上的 `@RequestMapping("/employee")` 只是前缀，和方法上的 `@GetMapping("/selectAll")` 拼起来才是 `GET /employee/selectAll`。
- `selectAll(Employee employee)` 没写任何注解：Spring 对"自定义对象"类型的参数走模型属性绑定，URL 上 `?name=thc&sex=男` 会依次调用 `setName`、`setSex`；没传的字段保持 null。
- 如果参数是 `String`、`Integer` 这类简单类型，就必须写 `@RequestParam`，否则拿不到值——这是"对象参数不用注解"的边界。
- `employeeService.selectAll(employee)` 把条件对象原样往下传，Controller 里一个 if 都不写；分层的意思就是"收发的只管收发"。
- `Result.success(list)` 把 List 装进 `data`；查不到数据不是错误，返回的是 `data: []`，前端表格显示"暂无数据"，不要写成 `Result.error()`。

**⑤ 在你仓库里** —— 接口在 `D:\my-project\xm-pro\springboot\src\main\java\com\example\controller\EmployeeController.java` 第 22~26 行；Service 在 `...\service\EmployeeService.java` 第 18~20 行；真正带条件的 SQL 在 `...\resources\mapper\EmployeeMapper.xml` 第 8~16 行。前端输入框和请求参数在 `D:\my-project\xm-pro\vue\src\views\Employee.vue` 第 5~14 行、第 104~115 行（`params` 里的 `name` 就是那个便签）。

**⑥ 常见坑** —— ① 输入姓名点查询没反应 → 前端 `params` 里的 key 写成了 `username` 或 `employeeName`，实体没有这个属性 → 必须和实体属性名一致，打开 Network 看 Query String 里到底是什么。② 在第 3 页输入姓名点"查询"，表格直接空了 → `pageNum` 还停在第 3 页，过滤后只剩 1 页 → 查询前把 `data.pageNum` 置 1（仓库的 `reset()` 做了，直接点"查询"时没做，自己补一句）。③ 后端返回空数组但数据库有数据 → 参数根本没绑上（比如前端传的是 JSON body 而接口是 GET）→ 看后端日志的 `Parameters:`，为空就是没收到。

**⑦ 自测** —— 前端发 `GET /employee/selectAll?name=thc`，后端方法签名是 `selectAll(Employee employee)`，`employee.getName()` 是谁赋的值？

<details><summary>展开解析</summary>

是 Spring MVC 的参数解析器（`ServletModelAttributeMethodProcessor`）按"请求参数名 = 属性名"反射调用 `setName("thc")` 赋的。自定义对象默认走模型属性绑定，所以不用 `@RequestParam`；简单类型（String、Integer）没有属性可绑，才必须显式加注解。

</details>

### 2.4 分页查询与 PageHelper

**① 讲义怎么说** —— "二、分页查询"第 1 条要求**"新建员工管理页面，显示的内容与数据库中 Employee 表的字段一致"**，代码参见"参考代码：分页查询 Employee.vue 代码.txt"；第 2 条是**"修改 Manage.vue，增加'员工管理'栏目，并配置路由"**。分页插件本身在实训8 的"五、分页查询"里已经装过。

**② 一句话讲透** —— 分页不是"前端把一万条切成十条"，而是"后端只给这一页的十条"。像去图书馆借书：你说"第 2 页、每页 10 本"，管理员不会把整个书库推给你再让你自己数，而是直接取第 11~20 本，同时告诉你"库里一共 137 本"。PageHelper 就是这个管理员：`startPage(2, 10)` 先在 ThreadLocal 里放一张便条，下一次 MyBatis 查询时它偷偷把 SQL 改成带 `LIMIT` 的形式，再补一条 `COUNT(*)` 算出总数，一起塞进 `Page` 对象；`PageInfo.of(list)` 把"这一页的数据 + 总数 + 页码"打包成前端认识的结构。所以分页是"数据库少给"，不是"前端少显示"——数据量再大，网络和浏览器都不会被拖垮。

**③ 示例代码** ——

```java
public PageInfo<Employee> selectPage(Employee employee, Integer pageNum, Integer pageSize) {
    PageHelper.startPage(pageNum, pageSize);
    List<Employee> list = employeeMapper.selectAll(employee);
    return PageInfo.of(list);
}
```

**④ 逐行拆解** ——
- `PageHelper.startPage(pageNum, pageSize)` 只对**紧挨着的下一条** MyBatis 查询生效，中间插一句别的查询，分页就跑到别人身上了。
- `employeeMapper.selectAll(employee)` 的静态类型是 `List`，运行时其实是 `Page`（ArrayList 的子类），总数就藏在这个对象里，所以 `PageInfo.of(list)` 拿得到 `total`。
- `PageInfo` 常用字段：`total` 总条数、`list` 当前页数据、`pageNum`、`pageSize`、`pages` 总页数。前端只取前两个。
- SQL 里千万不要自己再写 `LIMIT`：PageHelper 会再拼一次，变成 `LIMIT ? LIMIT ?`，直接语法错。
- Controller 的 `@RequestParam(defaultValue = "1")` 保证前端不传时也有默认值，避免 `null` 拆箱成 `int` 时抛 NPE。
- 配套的 `ORDER BY employee.id DESC` 决定"谁在第一页"：新插入的记录 id 最大，倒序才排在最前面，新增后一眼能看到。

**⑤ 在你仓库里** —— 分页逻辑在 `D:\my-project\xm-pro\springboot\src\main\java\com\example\service\EmployeeService.java` 第 30~34 行，接口在 `...\controller\EmployeeController.java` 第 43~49 行，插件坐标在 `D:\my-project\xm-pro\springboot\pom.xml` 第 43~54 行。前端分页器在 `D:\my-project\xm-pro\vue\src\views\Employee.vue` 第 39~50 行，取数在 `load()` 第 112~113 行。

**⑥ 常见坑** —— ① 一查就把全表返回，SQL 日志里没有 `LIMIT` → `startPage` 后面没紧跟查询，或插件依赖没加 → 看控制台 `Preparing:` 那条到底长什么样。② 表格有数据，分页器却显示共 0 条 → 前端取的是 `res.data.records`（那是 MyBatis-Plus 的字段名），PageInfo 里叫 `list` → 改成 `res.data.list`、`res.data.total`。③ 启动报 `NoSuchMethodError` 或 MyBatis 版本冲突 → PageHelper 自带的旧版 mybatis 覆盖了 starter 的 → 在 pom 里排除 `org.mybatis:mybatis`（仓库第 48~53 行就是这么做的）。

**⑦ 自测** —— `PageHelper.startPage(2, 10)` 之后先查了一次员工，又查了一次部门，分页会作用在哪次查询上？

<details><summary>展开解析</summary>

只作用在**紧挨着的员工查询**上，第二次部门查询不再分页。便条用完即清；但如果第一次查询压根没执行（比如前面抛了异常），便条会留在 ThreadLocal 里，传染给后面的查询。所以 `startPage` 必须紧贴目标查询，中间别塞别的数据库操作。

</details>

### 2.5 动态 SQL：where 与 if

**① 讲义怎么说** —— 讲义在"三、条件查询"只给了两步：**"2. 在 Employee 中添加相应代码"**、**"4. 此时，前端已经发送了请求……接下来进行如下处理"**，具体的 SQL 拼写在配图里，文字部分没有展开。这一块正好是本讲要补的：条件到底怎么"按需"拼进去。

**② 一句话讲透** —— 动态 SQL 像按需拼装的家具：条件有几个就装几块板，没选的板不装。`<if test="name != null and name != ''">` 就是"姓名过滤板"的开关；`<where>` 是聪明的底板，它会自动补上 `WHERE`，还会把开头多出来的那个 `AND` 削掉。好处是既不用在 Java 里拿字符串拼 SQL（容易漏空格、招注入），又能让"查全部"和"按姓名查"共用同一条语句：条件为空时 `<where>` 整块消失，SQL 退化成一条普通的全表查询。这两个标签都在生成 SQL 之前被解析，最终发给数据库的仍是一条完整、合法的 SQL 字符串。

**③ 示例代码** ——

```xml
<select id="selectAll" resultType="com.example.entity.Employee">
    SELECT * FROM employee
    <where>
        <if test="name != null and name != ''">
            employee.name LIKE CONCAT('%', #{name}, '%')
        </if>
    </where>
    ORDER BY employee.id DESC
</select>
```

**④ 逐行拆解** ——
- `<select id="selectAll">` 的 `id` 必须和 `EmployeeMapper` 里的方法名一字不差，MyBatis 靠它把接口调用和 SQL 对上号。
- `resultType="com.example.entity.Employee"` 指定每一行映射成什么对象；字段名和下划线列名的对应靠 `map-underscore-to-camel-case: true`。
- `<where>` 只有在内部至少一个 `<if>` 成立时才输出 `WHERE`；全不成立就整块消失，不会留下一个孤零零的 `WHERE`。
- `test="name != null and name != ''"`：判 null 防"没传这个参数"，判空串防"传了但输入框是空的"（清空输入框后 axios 会带一个 `name=`）。
- `LIKE CONCAT('%', #{name}, '%')`：`#{}` 会被编译成 `?` 走预编译，值里的单引号破坏不了 SQL；百分号在数据库端用 `CONCAT` 拼，别写成 `'%#{name}%'`，那样占位符根本不生效。
- 现在只有一个条件，`<where>` 看着有点多余，但它是给后面加 `sex`、`age` 留的插槽：加条件时只需再写一个 `<if>`，前面的结构一个字都不用动。
- `ORDER BY` 放在 `<where>` 外面：排序不是过滤条件，塞进 `<if>` 里会导致"有姓名时排序、没姓名时不排序"。

**⑤ 在你仓库里** —— 这段 SQL 在 `D:\my-project\xm-pro\springboot\src\main\resources\mapper\EmployeeMapper.xml` 第 8~16 行；接口声明在 `...\mapper\EmployeeMapper.java` 第 13 行；`mapper-locations` 和 SQL 日志开关在 `D:\my-project\xm-pro\springboot\src\main\resources\application.yml` 第 12~18 行（第 17 行 `StdOutImpl` 就是看最终 SQL 的窗口）。

**⑥ 常见坑** —— ① 不传 name 反而一条都查不到 → `test` 只写了 `name != ''`，null 也能通过这个判断，最后拼出 `LIKE NULL` → 必须写成 `name != null and name != ''`。② 报 `You have an error in your SQL syntax ... near 'AND'` → 多个 `<if>` 直接拼在 `WHERE` 后面，第一个条件前多了一个 `AND`，或者干脆漏了 `<where>` → 用 `<where>` 包住所有 `<if>`。③ 图省事写成 `${name}` → 字符串拼接，带引号就报错，还有注入风险 → 一律 `#{}`，模糊查询用 `CONCAT` 拼百分号。

**⑦ 自测** —— 把 `<where>` 去掉、只留 `<if>`，当 name 有值时最终 SQL 会变成什么样？错在哪？

<details><summary>展开解析</summary>

会变成 `SELECT * FROM employee name LIKE ... ORDER BY ...`——**少了 WHERE**，直接语法错。如果有两个 `<if>` 都成立，第一个条件前面还会多一个 `AND`。`<where>` 的职责就两条：有条件时补 `WHERE`，并削掉开头多余的 `AND`/`OR`。

</details>

### 2.6 新增记录

**① 讲义怎么说** —— "四、增加记录"先列了四个动词：**"get：查询操作、post：新增操作、put：修改操作、delete：删除操作"**，然后四步：**"1. 在 EmployeeController 中，写上 add() 方法"**一直到**"4. 在 EmployeeMapper.xml 中，写上插入语句"**；中间专门警告：**"注意：数据库的表名要用反引号括起来：`employee`"**；前端 `save()` 里还写着**"新增后一定要重新加载最新的数据"**。

**② 一句话讲透** —— 新增像填表投递：前端把整个表单对象序列化成 JSON，POST 到 `/employee/add`；`@RequestBody` 让 Spring 用 Jackson 把 JSON 反序列化成 Employee 对象，而不是一个个 `@RequestParam` 去接。真正落库靠 `<insert>`：列名里故意不写 id，因为 id 是自增主键，由 MySQL 发号；`useGeneratedKeys="true" keyProperty="id"` 是把刚发的号抄回 Java 对象的 id 字段——没有它，插完的记录在内存里还是"没有身份证的人"。最后前端必须 `load()` 重新查一次，因为页面上的表格只是上一次查询的快照，数据库变了它不会自己变。反过来，新增永远不该由前端指定主键：前端传了 id，反而会和自增机制打架。

**③ 示例代码** ——

```xml
<insert id="insert" useGeneratedKeys="true" keyProperty="id">
    INSERT INTO employee (name, sex, no, age, description)
    VALUES (#{name}, #{sex}, #{no}, #{age}, #{description})
</insert>
```

**④ 逐行拆解** ——
- `id="insert"` 对应 `EmployeeMapper.insert(Employee employee)`，方法名改了这里必须跟着改。
- 显式写出列名 `(name, sex, no, age, description)`：顺序和 `VALUES` 一一对应；不写列名就得按表结构给全部字段赋值，以后加一列就崩。
- 列名里没有 `id`：它是 `AUTO_INCREMENT`，交给数据库生成，前端传不传都不影响。
- `#{name}` 编译成 `?` 并调用对应的 `setString`；`age` 是 `Integer`，没填时写进去的是 `NULL` 而不是 0。
- `useGeneratedKeys="true"` 告诉 JDBC"我要回填自增主键"，`keyProperty="id"` 指定填回对象的哪个属性。
- `parameterType` 可以省略：MyBatis 能从接口方法参数推断出类型；讲义写了全限定类名，跟省略是等价的。
- 表名 `employee` 建议加反引号：MySQL 里有些词是关键字，加引号最稳，讲义那句警告就是为这个。

**⑤ 在你仓库里** —— SQL 在 `D:\my-project\xm-pro\springboot\src\main\resources\mapper\EmployeeMapper.xml` 第 18~21 行；Controller 在 `...\controller\EmployeeController.java` 第 54~58 行（`@PostMapping({"/add", "/insert"})` 两个路径都收）；Service 在 `...\service\EmployeeService.java` 第 36~38 行；前端提交在 `D:\my-project\xm-pro\vue\src\views\Employee.vue` 第 128~131 行（`handleAdd` 清空表单）与第 143~153 行（`add()`）。

**⑥ 常见坑** —— ① 后端 400，日志写 `Required request body is missing` → 前端写成了 `request.post(url, { params: form })`，或者请求头不是 json → 直接把表单对象当第二个参数传（仓库第 144 行），别包 `params`。② 提示"操作成功"但表格里没有新记录 → 没调 `load()`，或者排序是 id 正序、新记录落在最后一页 → 补 `load()`，并把 SQL 改成 `ORDER BY id DESC`。③ 插入成功但 `employee.getId()` 是 null，紧接着的编辑或返回新对象出问题 → `<insert>` 少写了 `useGeneratedKeys` → 补上（仓库第 18 行）。④ 中文变问号 → 库或表不是 `utf8mb4` → 建库时就指定字符集。

**⑦ 自测** —— 把 `useGeneratedKeys="true" keyProperty="id"` 删掉，新增还能成功吗？会留下什么隐患？

<details><summary>展开解析</summary>

数据照样能插进去，接口也返回成功——**所以这类配置最容易被忽略**。区别是插入后 `employee.id` 仍是 null：如果接口要把新对象回给前端、或者插入后紧接着用 id 做关联操作，就拿不到主键。当前页面每次新增后都重新 `load()`，看起来毫无异常，但换个场景就会露馅。

</details>

### 2.7 修改记录

**① 讲义怎么说** —— "五、修改记录或更新记录"第 5 条讲得很直白：**"当我们选择'编辑'时，打开了编辑的对话框，其实这个对话框跟'新增'的对话框是一样的，我们点击'保存'按钮，其实是新增，所以，我们要对'保存'按钮的事件重新进行编写"**，并给出判断依据：**"根据数据是否有 id 来判断是新增还是编辑"**。

**② 一句话讲透** —— 修改和新增在页面上是"同一个弹窗、同一个保存按钮"，差别只在对象有没有 id：有 id 说明这条记录已经在库里躺着，走 `PUT /employee/update`，SQL 是 `UPDATE ... WHERE id = ?`；没 id 就是新面孔，走 POST。像给病人建档：新病人发新病历号，老病人拿旧号改内容，绝不会给老病人再发一个号。而后端的 update 必须带 WHERE id——否则一条 UPDATE 会把全表所有人都改成同一个名字，这是 SQL 里最危险的一类手误。为什么用 id 判断？因为姓名可以重名、工号也可能填错，只有主键能唯一确定"这一行是谁"。

**③ 示例代码** ——

```xml
<update id="updateById">
    UPDATE employee
    SET name = #{name},
        sex = #{sex},
        no = #{no},
        age = #{age},
        description = #{description}
    WHERE id = #{id}
</update>
```

**④ 逐行拆解** ——
- `id="updateById"` 对应 `EmployeeMapper.updateById(Employee employee)`，名字对不上就是 `BindingException`。
- `SET` 里列出所有可编辑字段，等于"整行覆盖"：前端必须把完整对象传回来，所以编辑前一定要先回显整行数据。
- 每个赋值后面的逗号只在中间几个字段有，最后一个 `description` 后面**不能有逗号**，多一个就语法错。
- `WHERE id = #{id}` 是安全阀：id 为 null 时条件恒不成立，影响 0 行——不会误伤全表，但会出现"提示成功却没变化"。
- Controller 上是 `@PutMapping("/update")` 配 `@RequestBody`，与前端的 `request.put` 必须成对，写成 `@PostMapping` 就是 405。
- 前端 `handleUpdate(row)` 用 `JSON.parse(JSON.stringify(row))` 深拷贝：如果直接 `data.form = row`，弹窗里一改，表格那一行立刻跟着变（同一个对象引用），点"取消"也回不去。

**⑤ 在你仓库里** —— SQL 在 `D:\my-project\xm-pro\springboot\src\main\resources\mapper\EmployeeMapper.xml` 第 23~31 行；Controller 在 `...\controller\EmployeeController.java` 第 63~67 行；Service 在 `...\service\EmployeeService.java` 第 40~42 行；前端回显与分流在 `D:\my-project\xm-pro\vue\src\views\Employee.vue` 第 133~137 行（`handleUpdate`）、第 139~141 行（`save` 三元判断）、第 155~165 行（`update()`）。

**⑥ 常见坑** —— ① 点保存报 405 Method Not Allowed → 前端 `put`，后端写成了 `@PostMapping`（或反过来）→ 动词与注解一一对应。② 改 A 行时 B 行也跟着变，或者点了取消表格却被改脏 → 直接把 row 赋给 form，引用共享 → 深拷贝（仓库第 135 行）。③ 提示成功但数据没变 → 表单里没有 id（回显漏了，或被 `data.form = {}` 覆盖）→ Network 里看 Payload 有没有 id，后端看日志 `Updates: 0`。

**⑦ 自测** —— 编辑弹窗打开后什么都不改直接点"取消"，表格里的数据为什么不会变？仓库靠什么保证的？

<details><summary>展开解析</summary>

因为 `handleUpdate` 做了深拷贝，`data.form` 是一个新对象，弹窗里的 `v-model` 改的是副本；取消只是把 `formVisible` 设成 false，原 `row` 一动没动。若浅拷贝或直接赋值，改副本就等于改原行，取消也回滚不了——**这就是那一行 `JSON.parse(JSON.stringify(row))` 的全部意义**。

</details>

### 2.8 删除记录

**① 讲义怎么说** —— "六、删除记录"四步：**"1. 在 EmployeeController 中，写上 deleteById() 方法"**、Service、Mapper、**"4. 在 Employee.vue 中"**；前面"四、增加记录"的动词表里也写明 **"delete：删除操作"**。

**② 一句话讲透** —— 删除像按号销户：id 是唯一钥匙，前端把 id 拼在 URL 路径上（`/employee/deleteById/3`），后端用 `@PathVariable` 从路径里抠出来，Mapper 用注解写一条 `DELETE FROM employee WHERE id = ?`。为什么点删除要先弹确认框？因为 HTTP 的 DELETE 没有回收站，点错就是永久消失。`ElMessageBox.confirm` 返回 Promise，点"确定"才进 `then` 发请求，点"取消"走 `catch`——catch 里必须写个空函数把这次拒绝吞掉，否则控制台会多一条红色的未处理异常。删除是四个动词里步骤最少的，也是最不可逆的。删除用路径参数而不是请求体，是因为 DELETE 带 body 在很多服务器和代理上会被直接丢掉，放在 URL 里最稳。

**③ 示例代码** ——

```java
@DeleteMapping({"/deleteById/{id}", "/delete/{id}"})
public Result deleteById(@PathVariable Integer id) {
    employeeService.deleteById(id);
    return Result.success();
}
```

**④ 逐行拆解** ——
- `@DeleteMapping` 只接受 DELETE 请求；前端必须用 `request.delete`，用浏览器地址栏敲是 GET，直接 405。
- `{"/deleteById/{id}", "/delete/{id}"}` 一个方法映射两个路径，讲义叫 `deleteById`、仓库另有 `delete` 的写法，两个都收，前端改哪个都不会 404。
- `@PathVariable Integer id` 从 URL 模板 `{id}` 里取值并转成 Integer；路径里传了 `abc` 会返回 400（类型转换失败），不是 500。
- `employeeService.deleteById(id)` 一路传到 Mapper 的 `@Delete` 注解：SQL 是 `DELETE FROM employee WHERE id = #{id}`（表名两侧要加反引号）。注解里写了 SQL，XML 里就不要再写 `<delete>`，两边都写会报重复映射。
- `Result.success()` 不带 data：前端只需要一个 `code` 判断成败，删完自己重新查。
- 返回 void 的方法删 0 行也不报错（id 不存在时），所以"删成功"只代表 SQL 执行了，不代表真的删掉了记录。

**⑤ 在你仓库里** —— Controller 在 `D:\my-project\xm-pro\springboot\src\main\java\com\example\controller\EmployeeController.java` 第 72~76 行；Mapper 注解在 `...\mapper\EmployeeMapper.java` 第 25~26 行；Service 在 `...\service\EmployeeService.java` 第 44~46 行；前端确认与请求在 `D:\my-project\xm-pro\vue\src\views\Employee.vue` 第 167~179 行。

**⑥ 常见坑** —— ① 点删除没反应，控制台一条 `Uncaught (in promise) cancel` → `confirm` 的 `.catch` 没写 → 补 `.catch(() => {})`。② 报 404 → 前端拼的是 `/employee/deleteById/5`，后端只写了 `@DeleteMapping("/delete")` → 对齐路径，以 Network 里的 Request URL 为准。③ 提示删除成功但那一行还在 → 忘了 `load()`，或者 `del(scope.row)` 传了整个对象、拼出来是 `[object Object]` → 传 `scope.row.id`。

**⑦ 自测** —— 后端删除一个不存在的 id（比如 999），接口返回什么？前端会怎么显示？

<details><summary>展开解析</summary>

`DELETE ... WHERE id = 999` 影响 0 行，MyBatis 不抛异常，接口照样返回 `{"code":"200","msg":"请求成功"}`；前端提示"操作成功"，刷新后数据没有任何变化。想区分"删了 0 行"，可以把 Mapper 的返回值从 `void` 改成 `int`（影响行数），在 Service 里判断后抛 `CustomException`——这是可以自己加的改进。

</details>

### 2.9 前后端联调：一条请求的四层链路

**① 讲义怎么说** —— "一、3 运行前、后端的方式，后面开发都需要运行前、后端"；"一、5 测试一下，写一个简单的请求实例，在 Home.vue 中编写如下代码"；代码后面写：**"在浏览器中（在空白处右键，选择'检查'）能看见这些信息"**，配图就是控制台里的返回结果。

**② 一句话讲透** —— 联调就是把前端页面和后端接口这两根水管接起来：先确认两边都通水（服务都起着），再顺着管道找漏点。一条请求要过五道门：Vue 组件的事件 → axios（拼 baseURL、过拦截器）→ 浏览器（跨域预检）→ Tomcat 的 DispatcherServlet（按 URL 找 Controller 方法）→ Service → Mapper 代理 → XML 里的 SQL → MySQL；回来时 `Result` 被 Jackson 序列化成 JSON，拦截器拆壳，页面 `then` 里才拿到 `res`。任何一道门写错，现象都不一样：404 是门牌号错，405 是敲门方式错，400 是材料不对，500 是屋里着火了。排错的顺序也照这个来：先看请求有没有发出去，再看后端有没有收到，最后才看数据对不对。

**③ 示例代码** ——

```js
import router from "@/router/index.js";
import request from "@/utils/request.js";
import { reactive } from "vue";

const data = reactive({
  employeeList: []
})

request.get('/employee/selectAll').then(res => {
  console.log(res)
```

### 2.10 Employee.vue 的表格与弹窗

**① 讲义怎么说** —— "二、1 新建员工管理页面，显示的内容与数据库中 Employee 表的字段一致"；"五、5①"解释操作列：**"el-table-column：表格操作列；#default='scope' 插槽，可以通过 scope.row 获取当前行的数据，就是该行员工完整数据"**；"四、5"则给出"参考代码：Employee.vue 的弹窗代码.txt"。

**② 一句话讲透** —— 这个页面是后台系统的"标准件"：一张表加一个弹窗。`el-table` 负责把数组画成行，`:data` 给它什么数组它就画什么，`prop` 决定每列取对象里的哪个字段；操作列用 `#default="scope"` 插槽，`scope.row` 就是当前这一行的完整对象，所以编辑和删除能把 id 带出去。弹窗 `el-dialog` 由 `v-model` 控制显隐，里面的 `el-form` 绑的是 `data.form`：新增时清空、编辑时深拷贝，保存时看 id 分流。整页数据是单向流动的——`load()` 拉数据填 `data.tableData`，表格重画；用户改 `data.form`，保存完再 `load()`，形成闭环。表格只管展示、弹窗只管收集，两者都通过 `data` 这个响应式对象交换数据，谁也不用去碰对方的内部状态。

**③ 示例代码** ——

```vue
<el-table :data="data.tableData" stripe>
  <el-table-column label="姓名" prop="name" />
  <el-table-column label="性别" prop="sex" />
  <el-table-column label="工号" prop="no" />
  <el-table-column label="年龄" prop="age" />
  <el-table-column label="个人介绍" prop="description" show-overflow-tooltip />
  <el-table-column label="操作" width="160">
    <template #default="scope">
      <el-button type="primary" @click="handleUpdate(scope.row)">编辑</el-button>
      <el-button type="danger" @click="del(scope.row.id)">删除</el-button>
    </template>
  </el-table-column>
</el-table>

<div style="margin-top: 15px">
  <el-pagination
      v-model:current-page="data.pageNum"
      v-model:page-size="data.pageSize"
      :page-sizes="[5, 10, 15, 20]"
      background
      layout="total, sizes, prev, pager, next, jumper"
      :total="data.total"
      @size-change="handleSizeChange"
      @current-change="load"
  />
</div>
```

**④ 逐行拆解** ——
- `<el-table :data="data.tableData" stripe>`：`:data` 是单向绑定，数组换了表格就重画；`stripe` 只是斑马纹，不影响数据。
- `<el-table-column label="姓名" prop="name" />`：`prop` 必须和对象属性名完全一致，写错这一列就是空白，**而且不报错**。
- `show-overflow-tooltip`：内容过长时省略，鼠标悬停显示全文，"个人介绍"这种长文本必加。
- `<template #default="scope">`：插槽的作用域写法，`scope.row` 是当前行对象，`scope.$index` 是当前页内的行号（不是数据库 id）。
- `handleUpdate(scope.row)` 传整行，是为了回显；`del(scope.row.id)` 只传主键，因为后端要的是路径参数。
- `v-model:current-page` / `v-model:page-size`：双向绑定，用户点页码或改每页条数会直接改 `data` 里的值，`load()` 读的就是这两个值。
- `:page-sizes` 与 `layout` 决定"每页几条"的选项和分页器长什么样；`:total` 必须用后端返回的总数，否则页数算错。
- `@size-change="handleSizeChange"` 里会把 `pageNum` 拉回 1；`@current-change="load"` 则是翻页直接重查。

**⑤ 在你仓库里** —— 页面在 `D:\my-project\xm-pro\vue\src\views\Employee.vue`：表格第 25~37 行、分页第 39~50 行、弹窗第 54~84 行、`handleAdd`/`save` 第 128~141 行。路由在 `D:\my-project\xm-pro\vue\src\router\index.js` 第 28 行（`/manage/employee`），左侧菜单项在 `D:\my-project\xm-pro\vue\src\views\Manage.vue` 第 60~68 行（第 67 行"员工信息"）。

**⑥ 常见坑** —— ① 表格全空但接口明明返回了数据 → `prop` 和实体字段对不上，或 `:data` 绑成了整个 `res.data`（PageInfo）→ `prop` 对齐实体，`data.tableData = res.data.list`。② 点"新增"，弹窗里还留着上一条的内容 → `handleAdd` 没清空表单 → `data.form = {}`（仓库第 129 行）。③ 改成每页 20 条后表格变空 → 当前页码超出了新的总页数 → `handleSizeChange` 里先把 `pageNum` 置 1 再查（仓库第 123~126 行）。

**⑦ 自测** —— `#default="scope"` 里的 `scope.row` 和 `scope.$index` 分别是什么？删除按钮为什么传 `scope.row.id` 而不是 `scope.row`？

<details><summary>展开解析</summary>

`scope.row` 是当前行的完整数据对象（含 id、name、sex 等），`scope.$index` 是这一行在当前页里的下标，从 0 开始、随翻页变化，**不能当数据库主键**。删除只需要主键，传 `scope.row.id` 才能拼成 `/employee/deleteById/5`；传整个对象会变成 `[object Object]`，或者被当成请求体，与 `@PathVariable` 的接口对不上。

</details>
