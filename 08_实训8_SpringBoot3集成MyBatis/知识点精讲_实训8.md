## 0. 这一讲在整门课里的位置

上一讲大家第一次把后端跑起来了：8080 端口、`/hello`、统一的 `Result`、全局异常处理，但数据全是代码里写死的字符串——关掉 IDEA 就什么都没了。这一讲要干的事只有一件：**把“数据”从 Java 代码里搬进 MySQL**，让后端真正变成一个能存东西、能查东西的系统。

搬家的工具就是 MyBatis。它在 Java 对象和数据库表之间当翻译：Java 这边叫 `Employee` 对象，数据库那边叫 `employee` 表，中间靠 Mapper 接口 + XML 里的 SQL 对接。这一讲建立的 **entity → mapper → service → controller** 四层骨架，是后面每一讲的模板；实训9 的增删改查、实训10 的登录、实训12 的账号管理，都是往这四层里填代码，不会再有新的架构。

对前端同学来说，这一讲也是第一次“真连上”：`vue/src/views/Employee.vue` 里的表格和分页早写好了，它请求的 `/employee/selectPage` 在上一讲是 404，这一讲补上后端之后，页面上的姓名、性别、工号才会真的从数据库里冒出来。所以本讲不是孤立的一讲，它是**前后端真正会师的节点**。

## 2. 知识点精讲

### 2.1 MyBatis 是什么、一次查询怎么走完

**① 讲义怎么说** —— 讲义“一、什么是 MyBatis”开篇：**“MyBatis 是一款轻量级、持久层 ORM 框架，原名 iBatis，2010 年改名为 MyBatis”**，核心作用是**“简化 Java 程序操作数据库（JDBC），替代原生 JDBC、简化繁琐的数据库操作代码”**；执行流程里又写：**“调用接口方法 → MyBatis 根据方法名匹配 XML 中 SQL”**。

**② 一句话讲透** —— 把 MyBatis 想成餐厅里的**服务员**：Mapper 接口是印好的菜单，只写菜名（`selectAll`），不写做法；XML 是后厨的配方柜，每个抽屉上贴着菜名，里面才是真正的 SQL；MyBatis 这个服务员负责把客人点的菜名，精确对到后厨某个抽屉，把参数递进去，再把做好的菜（结果集）摆成客人要的盘（`List<Employee>`）。没有它，大家就得自己进后厨：加载驱动、开连接、拼 SQL、取结果、关连接，一步忘了就泄漏连接。更关键的是，它把“接口方法”和“SQL”这两件本来没关系的东西，用 namespace 和 id 焊在一起——以后加一个查询，只补一个方法和一段 SQL，调用方一行都不用改。

**③ 示例代码** ——

```java
@GetMapping("/selectAll")
public Result selectAll(Employee employee) {
    // ① 浏览器发来 GET /employee/selectAll
    List<Employee> list = employeeService.selectAll(employee); // ② 交给 Service
    // ③ Service 调 Mapper 接口 → ④ MyBatis 找到 XML 里 id=selectAll 的 SQL
    return Result.success(list);                               // ⑤ 结果包装成统一 JSON
}
```

**④ 逐行拆解** ——
- 第 ① 步只认 URL 和方法：`@GetMapping("/selectAll")` 加上类上的 `/employee`，拼出完整地址，跟数据库一点关系都没有。
- 第 ② 步是**纯 Java 调用**：`employeeService` 是 Spring 注入进来的对象，这时候还没碰数据库。
- 第 ③ 步才进入 MyBatis 的地盘：`EmployeeMapper` 只有接口没有实现类，运行时拿到的是**JDK 动态代理**生成的 `MapperProxy`。
- 第 ④ 步靠两把钥匙对暗号：`namespace="com.example.mapper.EmployeeMapper"` 找到这个 XML，`id="selectAll"` 找到这条 SQL。
- 第 ⑤ 步把 `List<Employee>` 塞进 `Result.data`，Jackson 再把它序列化成前端认识的 JSON——**数据库的行、Java 的对象、前端的 JSON，三种形态在这里完成转换**。

**⑤ 在你仓库里** —— `D:\my-project\xm-pro\springboot\src\main\java\com\example\mapper\EmployeeMapper.java` 第 10~13 行：`@Mapper` 接口里只有 `List<Employee> selectAll(Employee employee);` 一行声明；`D:\my-project\xm-pro\springboot\src\main\resources\mapper\EmployeeMapper.xml` 第 6~16 行：`namespace` 指向这个接口、`<select id="selectAll">` 里才是真正的 SQL；`D:\my-project\xm-pro\springboot\src\main\java\com\example\service\EmployeeService.java` 第 18~20 行：Service 只做了一次转发。

**⑥ 常见坑** —— ① 以为接口要自己写实现类，新建 `EmployeeMapperImpl` → 与 MyBatis 生成的代理冲突，启动报 Bean 重复 → 删掉实现类，接口只留方法声明。② 方法名随便起成 `queryAll`，XML 里却写 `selectAll` → 启动不报错，一访问就 `Invalid bound statement` → 两边改成同一个名字。③ 继续用原生 JDBC 的 `DriverManager` 写工具类 → 连接用完不关，跑久了 `Too many connections` → 交给 MyBatis 和 Spring 管连接池。

**⑦ 自测** —— Mapper 接口只有一行方法声明，为什么 `@Resource` 注入后就能调用，还能查到数据库里的数据？

<details><summary>展开解析</summary>

因为 MyBatis 在启动时用 **JDK 动态代理**给接口生成了一个代理对象，注册进 Spring 容器。调用 `selectAll()` 时，代理会拦截这次调用，用“接口全名（namespace）+ 方法名（id）”找到 XML 里的 SQL，交给 `SqlSession` 执行，再把结果集反射封装成 `List<Employee>`。大家从头到尾没有写过实现类，实现是**运行时生成**的。

</details>

### 2.2 数据库与 employee 表

**① 讲义怎么说** —— 讲义“二、配置 Mybatis”第 9 步只有一句：**“在你连接的数据库中，新建数据库表:employee”**，紧接着**“添加几条记录”**；第 10 步再建 `entity` 包和 `Employee` 实体类，让表结构与 Java 类对上。

**② 一句话讲透** —— 数据库是**仓库**，库 `xm-pro` 是仓库里的一间房，表 `employee` 是房里的一排货架，一行就是一个员工，一列就是一个属性。`id` 上的 `AUTO_INCREMENT` 是**排队机**：不用大家自己算下一个号，数据库保证不会重号；`PRIMARY KEY` 是**身份证**，一行一个、不能重复。表建好之后，Java 里那个 `Employee` 类才有“模具”可依——类有几个属性，表就该有几列，名字还要对得上。表结构一旦定下来，实体类、XML、前端表格全都围着它转；改一个列名，三处都要跟着改，所以建表时字段名要一次想清楚。

**③ 示例代码** ——

```sql
CREATE TABLE IF NOT EXISTS `employee` (
    `id`          INT NOT NULL AUTO_INCREMENT COMMENT '主键',
    `name`        VARCHAR(255) DEFAULT NULL COMMENT '姓名',
    `sex`         VARCHAR(255) DEFAULT NULL COMMENT '性别',
    `no`          VARCHAR(255) DEFAULT NULL COMMENT '工号',
    `age`         INT DEFAULT NULL COMMENT '年龄',
    `description` LONGTEXT DEFAULT NULL COMMENT '个人介绍',
    PRIMARY KEY (`id`)
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4 COLLATE = utf8mb4_unicode_ci;

INSERT INTO `employee` (`name`, `sex`, `no`, `age`, `description`)
VALUES ('thc', '男', '100001', 18, '勤学钻研，自强不息'),
       ('zhangsan', '男', '100002', 19, '积极开拓，敢于创新'),
       ('lisi', '女', '100003', 23, '做事细致严谨');
```

**④ 逐行拆解** ——
- 库名 `xm-pro` 带中划线，SQL 里必须写反引号 `` `xm-pro` ``，否则 MySQL 把 `-` 当减号，报 `You have an error in your SQL syntax`。
- `id INT NOT NULL AUTO_INCREMENT`：自增主键，插入时**不要传 id**，传了反而可能打乱自增序列。
- `name`/`sex`/`no` 用 `VARCHAR(255)`：`no` 是工号，虽然看着像数字，但工号可能有前导零（`001001`），**必须用字符串**，用 INT 会把前导零吃掉。
- `description` 用 `LONGTEXT`：个人介绍可能几百字，`VARCHAR(255)` 装不下；Java 侧对应 `String`。
- `utf8mb4` 而不是 `utf8`：`utf8` 在 MySQL 里只存 3 字节，生僻字和 emoji 会乱码或报错，`utf8mb4` 才是真正的 UTF-8。
- 三条 INSERT 只是“让页面有东西可看”，`selectAll` 查出来按 `id DESC` 排序，最后插入的排最前面。

**⑤ 在你仓库里** —— `D:\my-project\xm-pro\springboot\src\main\resources\application.yml` 第 3 行：URL 里的库名就是 `xm-pro`，和第 4~6 行的 `root/123456` 一起决定连哪个库；`D:\my-project\xm-pro\springboot\src\main\java\com\example\entity\Employee.java` 第 4~9 行：六个属性 `id/name/sex/no/age/description` 与表结构逐列对应；前端表格在 `D:\my-project\xm-pro\vue\src\views\Employee.vue` 第 25~30 行，`prop="name"`、`prop="no"` 这些名字必须和实体属性一致才能显示。建表脚本可对照 `D:\course\Javaweb\08_实训8_SpringBoot3集成MyBatis\db\init.sql` 第 9~19 行。

**⑥ 常见坑** —— ① 建库时写成 `xm_pro`（下划线），yml 里却写 `xm-pro`（中划线）→ 报 `Unknown database 'xm-pro'` → 两边改成完全一致，推荐统一用 `xm-pro` 并给 SQL 加反引号。② 表名建成 `employees`（复数）→ `Table 'xm-pro.employees' doesn't exist` → 改成 `employee`，XML 里三处表名一起改。③ 建表没指定字符集，插入中文变成 `???` → 库/表/连接三处字符集不一致 → 建库建表都用 `utf8mb4`，URL 带 `characterEncoding=utf-8`。

**⑦ 自测** —— 工号 `no` 为什么在数据库和实体类里都用字符串，而不是 `INT`？

<details><summary>展开解析</summary>

因为工号是**编号**不是**数量**，不参与加减乘除，而且现实中常有前导零（如 `001001`）。用 `INT` 存会变成 `1001`，前导零丢失，和纸质档案对不上；用 `VARCHAR` 原样保存，长度也更自由。

</details>

### 2.3 三个依赖各自的作用

**① 讲义怎么说** —— 讲义没有单列“依赖”一节，但“二、配置 Mybatis”的所有步骤都建立在建工程时勾选的 **Spring Web、MyBatis Framework、MySQL Driver** 之上；“五、1”又明确要求**“在项目的 pom.xml 文件里，引入分页插件”**，并解释**“Maven 通过 groupId + artifactId + version 三维定位一个 jar 包”**。

**② 一句话讲透** —— 三个依赖像开一家餐厅：**`spring-boot-starter-web` 是店面**，有了它才有内嵌 Tomcat 这个“门面”，别人才找得到 8080 端口；**`mybatis-spring-boot-starter` 是店长**，负责把 `SqlSessionFactory`、`SqlSession`、Mapper 代理这些人和事组织起来，让大家只管写接口；**`mysql-connector-j` 是电话线**，Java 只会说 JDBC，MySQL 只会说自己的协议，中间得靠它翻译。三者缺一：没 Web 启动不了服务器，没 MyBatis 注入不了 Mapper，没 Driver 一连库就报“找不到驱动”。判断缺哪个也有窍门：看报错发生在“启动”还是“第一次查询”——启动就报数据源，多半是 Driver 或 yml；查询才报 Mapper，多半是 MyBatis starter。按这个顺序查，比一条条试依赖快得多。

**③ 示例代码** ——

```xml
<dependencies>
    <!-- 店面：Spring MVC + 内嵌 Tomcat -->
    <dependency>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-starter-web</artifactId>
    </dependency>

    <!-- 店长：MyBatis 与 Spring 的粘合剂，版本必须自己写 -->
    <dependency>
        <groupId>org.mybatis.spring.boot</groupId>
        <artifactId>mybatis-spring-boot-starter</artifactId>
        <version>3.0.5</version>
    </dependency>

    <!-- 电话线：MySQL 的 JDBC 驱动，只在运行时需要 -->
    <dependency>
        <groupId>com.mysql</groupId>
        <artifactId>mysql-connector-j</artifactId>
        <scope>runtime</scope>
    </dependency>
</dependencies>
```

**④ 逐行拆解** ——
- `spring-boot-starter-web` 不写 `<version>`：它由父工程 `spring-boot-starter-parent:3.5.16` 的 `<dependencyManagement>` 统一管版本，**Spring 官方 starter 都不写版本**。
- `mybatis-spring-boot-starter` 是第三方（`org.mybatis.spring.boot`），父工程管不到，**必须自己写 3.0.5**；写 2.x 是给 Spring Boot 2 用的，在 Boot 3 里会因 `javax` 包路径对不上而启动失败。
- 这个 starter 里已经带了 `mybatis` 和 `mybatis-spring`，**不要再单独引 `org.mybatis:mybatis`**，否则两个版本打架。
- `mysql-connector-j` 的 `<scope>runtime</scope>`：编译时大家代码里没有 `import com.mysql.*`，只有 `jdbc:mysql://...` 这个字符串，运行起来才需要它注册驱动。
- 分页的 `pagehelper-spring-boot-starter` 是第四个依赖，它里面也带了一份 `mybatis`，所以仓库里用 `<exclusion>` 把它排掉（见 2.11）。

**⑤ 在你仓库里** —— `D:\my-project\xm-pro\springboot\pom.xml` 第 24~27 行是 web、第 30~34 行是 mybatis 3.0.5、第 37~41 行是 mysql 驱动；同一个文件的第 44~54 行是后加的分页插件（带 `org.mybatis:mybatis` 排除）。依赖装好没有，最直接的证据在 `D:\my-project\xm-pro\springboot\src\main\resources\application.yml` 第 6 行：启动时 Spring 会按这一行去加载 `com.mysql.cj.jdbc.Driver`，能正常连上库，就说明驱动 jar 已经在 classpath 上。

**⑥ 常见坑** —— ① 启动报 `Failed to determine a suitable driver class` → 少了 `mysql-connector-j`，或 yml 里 `driver-class-name` 拼错 → 补依赖、对照 `com.mysql.cj.jdbc.Driver` 一个字母一个字母看。② 启动报 `NoSuchMethodError` 或 `ClassNotFoundException`（常见于 `javax` 与 `jakarta` 混用）→ 把 Boot 3 的工程配了 MyBatis 2.x 的 starter → 换成 `3.0.5`。③ 加了 PageHelper 后启动报 `NoSuchMethodError` 或 `Invalid bound statement` → 两个 mybatis 版本冲突 → 按仓库写法加 `<exclusion>` 排掉旧 mybatis。

**⑦ 自测** —— 三条依赖里，为什么只有 `mybatis-spring-boot-starter` 写了 `<version>`？

<details><summary>展开解析</summary>

因为 `spring-boot-starter-web` 和 `mysql-connector-j` 都是 **Spring 官方维护**的，版本被父工程 `spring-boot-starter-parent` 的 `<dependencyManagement>` 锁死；而 `mybatis-spring-boot-starter` 属于 MyBatis 社区，父工程不认识它，不写版本 Maven 会报 `'dependencies.dependency.version' ... is missing`。

</details>

### 2.4 application.yml 的三行 MyBatis 配置

**① 讲义怎么说** —— 讲义“二、1 配置 mybatis 实体和 xml 映射”开宗明义：**“告诉 MyBatis 去哪里找写 SQL 的 Mapper.xml 文件”**，并逐条解释：`mapper-locations` **“指定 mapper.xml 文件存放路径”**；`log-impl` **“开启 mybatis 日志，控制台打印执行的 SQL”**；`map-underscore-to-camel-case: true` **“开启下划线自动转驼峰映射，数据库下划线字段自动封装到实体驼峰属性”**。

**② 一句话讲透** —— yml 是**写给框架看的地图**，不是写给人看的注释。`mapper-locations` 告诉 MyBatis “XML 都放在 classpath 的 mapper 目录下，自己去找”；`log-impl` 相当于在数据库门口装了个**监控**，每条真正执行的 SQL、传进去的参数、查回来几行，都会原样打在控制台；`map-underscore-to-camel-case` 是**自动翻译器**，数据库的 `create_time` 会自动装进 Java 的 `createTime`。YAML 靠缩进表达层级，**两个空格是一层，Tab 不是空格**，缩错一层配置就挂到别的节点下面，而且往往不报错。还有个容易忽略的点：键名拼错（比如少写一个 s）也不会报错，只是配置悄悄失效，最后表现成“XML 明明在，SQL 却找不到”。

**③ 示例代码** ——

```yml
spring:
  datasource:
    url: jdbc:mysql://localhost:3306/xm-pro?useUnicode=true&characterEncoding=utf-8&serverTimezone=Asia/Shanghai
    username: root
    password: 123456
    driver-class-name: com.mysql.cj.jdbc.Driver

mybatis:
  mapper-locations: classpath:mapper/*.xml
  configuration:
    log-impl: org.apache.ibatis.logging.stdout.StdOutImpl
    map-underscore-to-camel-case: true
```

**④ 逐行拆解** ——
- `spring.datasource` 下四行是一个整体：`url` 说“连哪台机器的哪个库”，`username`/`password` 是门禁，`driver-class-name` 说“用哪个驱动类”。四个**必须左对齐**，多一个空格就变成 `url` 的子属性，启动时报绑定失败。
- URL 里 `useUnicode=true&characterEncoding=utf-8` 管中文，`serverTimezone=Asia/Shanghai` 管时区；少时区可能报 `The server time zone value '中国标准时间' is unrecognized`。
- `mybatis.mapper-locations` 的 `classpath:` 指的是**编译后的类路径**，即 `target/classes`，不是源码目录 `src/main/resources`；Maven 打包时会把 resources 原样复制过去。
- `classpath:mapper/*.xml` 只匹配 `mapper` 这一层，**不递归子目录**；如果以后按模块建子包，要改成 `classpath:mapper/**/*.xml`。
- `log-impl` 用 `StdOutImpl` 表示直接用 `System.out` 打印，学习阶段最直观；生产环境一般交给 SLF4J，不会用这个。
- `map-underscore-to-camel-case: true` 只影响**自动映射**：`resultType` 直接映射实体时才生效，自己写 `<resultMap>` 的字段不受它管。

**⑤ 在你仓库里** —— `D:\my-project\xm-pro\springboot\src\main\resources\application.yml` 第 1~6 行是数据源，第 12~18 行是 MyBatis 三项配置（中间的空行不影响解析）；`D:\my-project\xm-pro\springboot\src\main\resources\mapper\EmployeeMapper.xml` 就放在 `mapper` 目录下，正好被 `classpath:mapper/*.xml` 扫到；如果把它挪到 `resources/sql/` 下，`D:\my-project\xm-pro\springboot\src\main\java\com\example\mapper\EmployeeMapper.java` 第 13 行的方法就再也绑不到 SQL。

**⑥ 常见坑** —— ① 报 `Invalid bound statement (not found)`，XML 明明写了 → `mapper-locations` 拼成 `mapper-location`（少 s）或路径写成 `mapper/*.xml`（少了 `classpath:`）→ 照抄仓库第 14 行。② yml 里用了 Tab 或缩进多一格 → 启动报 `while scanning a simple key` 或配置静默不生效 → 全部改成两个空格，`url` 与 `username` 左对齐。③ URL 里直接写 `&` 在 yml 里通常没问题，但复制进 XML 的 `<property>` 时必须写 `&amp;` → 报 `The reference to entity "characterEncoding" must end with the ';' delimiter` → XML 里转义。

**⑦ 自测** —— XML 明明放在 `src/main/resources/mapper` 下，为什么运行时 MyBatis 却去 `target/classes/mapper` 找？

<details><summary>展开解析</summary>

因为 `classpath:` 指向的是 **Maven 编译输出目录** `target/classes`。`mvn compile` / IDEA 启动时会把 `src/main/resources` 下的文件**原样复制**到 `target/classes`，所以源码目录只是“存放地”，运行时真正读的是复制后的那份。改完 XML 如果没重新编译，`target/classes` 里还是旧文件，就会出现“代码改了但 SQL 没变”。

</details>

### 2.5 实体类 Employee

**① 讲义怎么说** —— 讲义“二、10”：**“新建一个包：entity，新建一个实体类 Employee”**；后面解释 Mapper 时又写：**“Employee 是实体类，一条数据库记录对应一个 Employee 对象”**，查询结果会**“自动映射为实体对象返回”**。

**② 一句话讲透** —— 实体类是数据库表在 Java 里的**模具**：表里一行记录，倒进模具就压出一个 `Employee` 对象；表有几列，模具就有几个属性。MyBatis 拿到 `ResultSet` 后，靠**反射**挨个找同名的 setter——列 `name` 找 `setName()`，列 `age` 找 `setAge()`——把值塞进去。所以实体类不是“随便写个类”，它必须**有无参构造、有 getter/setter、属性名和列名对得上**，否则查出来一堆 `null`，还不报错。判断写得对不对有个笨办法：把表 `DESC` 出来的列名和类里的属性名一行行对，再把 getter/setter 数一遍——六个属性应该有十二个方法，少一个都可能让某个字段永远是 null。

**③ 示例代码** ——

```java
package com.example.entity;

public class Employee {
    private Integer id;
    private String name;
    private String sex;
    private String no;
    private Integer age;
    private String description;

    public Integer getId() { return id; }
    public void setId(Integer id) { this.id = id; }

    public String getName() { return name; }
    public void setName(String name) { this.name = name; }

    public String getSex() { return sex; }
    public void setSex(String sex) { this.sex = sex; }

    public String getNo() { return no; }
    public void setNo(String no) { this.no = no; }

    public Integer getAge() { return age; }
    public void setAge(Integer age) { this.age = age; }

    public String getDescription() { return description; }
    public void setDescription(String description) { this.description = description; }
}
```

**④ 逐行拆解** ——
- `package com.example.entity;` 必须和磁盘目录 `src/main/java/com/example/entity/` 完全对应，包名写错编译就过不去。
- 六个属性顺序不重要，**名字和类型重要**：`id`、`age` 用包装类 `Integer`，因为数据库这两列允许 `NULL`；用 `int` 接收 `NULL` 会抛 `NullPointerException`。
- `no` 是工号，用 `String`；`description` 对应 `LONGTEXT`，也用 `String`，JDBC 驱动会自动把大文本读成字符串。
- 每个属性配一对 `getXxx()` / `setXxx()`：Jackson 序列化 JSON 时用 getter，MyBatis 填值时用 setter，**缺一不可**。
- 没有写构造方法，Java 会送一个**无参构造**；如果自己写了带参构造，记得把无参构造补回来，否则 MyBatis 反射创建对象时找不到它。
- 这里没用 Lombok 的 `@Data`：讲义和仓库都手写 getter/setter，初学阶段看得见每个字段，排错更直接。

**⑤ 在你仓库里** —— `D:\my-project\xm-pro\springboot\src\main\java\com\example\entity\Employee.java` 第 3~28 行：六个属性 + 十二个 getter/setter，一个不多一个不少；`D:\my-project\xm-pro\springboot\src\main\resources\mapper\EmployeeMapper.xml` 第 8 行的 `resultType="com.example.entity.Employee"` 就是告诉 MyBatis “按这个模具装”；前端 `D:\my-project\xm-pro\vue\src\views\Employee.vue` 第 25~30 行的 `prop` 用的也是这套属性名。

**⑥ 常见坑** —— ① 查询结果每个字段都是 `null`，但 SQL 明明有数据 → 只写了 getter 没写 setter，或属性名写成 `userName` 而列是 `name` → 补齐 setter、对齐列名，必要时开 `map-underscore-to-camel-case`。② 实体类放在 `entity` 包，文件却丢在 `controller` 目录下 → IDEA 能编译但包路径和目录不一致，运行时报 `ClassNotFoundException` → 包名与目录必须一致。③ 用 `int age` 接收可空的 `age` 列 → 某条记录年龄为空时抛 `NullPointerException` → 换成 `Integer`。

**⑦ 自测** —— 数据库的 `age` 列允许为 `NULL`，实体类里为什么必须用 `Integer` 而不是 `int`？

<details><summary>展开解析</summary>

`int` 是基本类型，没有“空”的概念，默认值是 `0`；MyBatis 把 `NULL` 往 `int` 上塞时会尝试拆箱，直接抛 `NullPointerException`。`Integer` 是包装类型，可以为 `null`，能如实表达“这条记录没填年龄”。所以**数据库可空的数字列，Java 侧一律用包装类**。

</details>

### 2.6 Mapper 接口

**① 讲义怎么说** —— 讲义“一、1 核心组件”：**“Mapper 接口（Dao）只定义抽象方法，无实现类；MyBatis 通过动态代理自动生成实现”**；“三、4”讲 `EmployeeMapper` 时又强调硬性绑定规则：**“EmployeeMapper.xml 中 `<select>` 标签的 id 属性必须和方法名完全一致”**。

**② 一句话讲透** —— Mapper 接口是**只有菜名、没有做法的菜单**。大家写 `List<Employee> selectAll(Employee employee);`，等于在菜单上印了一道“全家福”；后厨怎么做，写在 XML 那个配方柜里。接口和 XML 之间靠两根线拴着：**namespace 拴接口全名，id 拴方法名**。MyBatis 在启动时给每个接口发一个“替身”（动态代理），大家调接口，替身替大家去 XML 找 SQL、去数据库取数据，所以接口**永远不需要实现类**。还有一条隐形规则：同一个 namespace 里方法名必须唯一，不能靠重载区分——因为 XML 的 id 只能有一个。记不住就记一句话：**接口管签名，XML 管实现**。

**③ 示例代码** ——

```java
package com.example.mapper;

import com.example.entity.Employee;
import org.apache.ibatis.annotations.Delete;
import org.apache.ibatis.annotations.Mapper;
import org.apache.ibatis.annotations.Select;

import java.util.List;

@Mapper
public interface EmployeeMapper {

    List<Employee> selectAll(Employee employee);

    @Select("SELECT * FROM employee WHERE id = #{id}")
    Employee selectById(Integer id);

    @Select("SELECT * FROM employee WHERE id = #{id}")
    Employee selectByIdWithAnnotation(Integer id);

    void insert(Employee employee);

    void updateById(Employee employee);

    @Delete("DELETE FROM `employee` WHERE id = #{id}")
    void deleteById(Integer id);
}
```

**④ 逐行拆解** ——
- `@Mapper` 是给这个接口贴的“我是 MyBatis 接口”标签，Spring 扫描到它会生成代理 Bean；仓库同时在启动类写了 `@MapperScan`，两者作用重叠但**不冲突**。
- `selectAll(Employee employee)` 的参数不是摆设：XML 里用 `<if test="name != null">` 按姓名模糊查询，前端传 `?name=张` 时这个对象就派上用场；不传就是查全部。
- `@Select(...)` 是**注解方式**写 SQL，适合这种一两行的简单查询；复杂 SQL（动态条件、多表）仍然要放 XML。仓库里 `selectById` 和 `selectByIdWithAnnotation` 故意写成同一句 SQL，是为了对比“XML 方式”和“注解方式”两种写法。
- `insert` / `updateById` 返回 `void`：新增时自增 id 由 XML 的 `useGeneratedKeys` 回填到对象里，不需要返回值；想看影响几行可以改成 `int`。
- `deleteById` 的 SQL 里表名加了反引号：`employee` 不是保留字，但养成习惯，遇到 `order`、`user` 这类表名就不会翻车。
- **方法名 = XML 的 id**，这是硬规则；参数名和 `#{}` 里的名字也要对得上（`#{name}` 对应 `getName()`）。

**⑤ 在你仓库里** —— `D:\my-project\xm-pro\springboot\src\main\java\com\example\mapper\EmployeeMapper.java` 第 10~27 行是完整接口：第 13 行 `selectAll`、第 15~16 行注解版 `selectById`、第 25~26 行 `deleteById`；`D:\my-project\xm-pro\springboot\src\main\resources\mapper\EmployeeMapper.xml` 第 8~16 行是 `selectAll` 的实现；`D:\my-project\xm-pro\springboot\src\main\java\com\example\service\EmployeeService.java` 第 15~20 行演示了怎么注入并调用它。

**⑥ 常见坑** —— ① 方法名 `selectAll`，XML 里 id 写成 `selectAllList` → 启动不报错，一访问就 `Invalid bound statement (not found): com.example.mapper.EmployeeMapper.selectAll` → 两边改成完全一致。② 方法有多个参数却直接写 `#{name}`、`#{age}` → 报 `Parameter 'name' not found. Available parameters are [arg0, arg1, param1, param2]` → 每个参数加 `@Param("name")`，或干脆封装成一个实体对象。③ 返回 `List<Employee>`，XML 却写 `resultType="java.util.List"` → 每行被当成一个 List，类型转换失败 → `resultType` 写**集合里的元素类型** `com.example.entity.Employee`。

**⑦ 自测** —— 接口里一个方法体都没有，Spring 注入进来的到底是什么对象？

<details><summary>展开解析</summary>

是 MyBatis 用 **JDK 动态代理**生成的 `MapperProxy` 代理对象，它在启动时被注册成 Spring Bean。代理类实现了 `EmployeeMapper` 接口，所以类型能对上；调用任何方法都会被 `MapperProxy` 拦截，转成“namespace + 方法名”去找 XML 里的 SQL 并执行。**接口只是契约，代理才是干活的。**

</details>

### 2.7 Mapper XML

**① 讲义怎么说** —— 讲义“三、4”逐行讲 `EmployeeMapper.xml`：根标签 **`<mapper namespace="com.example.mapper.EmployeeMapper">`**，**“namespace 属性（核心绑定）……必须填写接口的完整全限定类名”**；`<select id="selectAll" resultType="com.example.entity.Employee">` 中，**“id 值必须和 EmployeeMapper 接口中的方法名完全一致”**，`resultType` **“指定 SQL 查询结果封装的 Java 实体类”**。

**② 一句话讲透** —— XML 是**后厨的配方柜**：`namespace` 是柜子的编号（接口全名），`id` 是抽屉的编号（方法名），`resultType` 是“装盘要求”（每行数据装成什么对象）。三者对上，服务员（MyBatis）才能一拉抽屉就找到配方。XML 里写的仍然是 SQL，但多了**动态标签**这个本事：`<if>` 能按条件拼 WHERE，`<where>` 能自动处理多余的 AND——这是手写 JDBC 拼字符串做不到的，也是企业里仍然大量用 XML 的原因。另一个好处是可读性：几十行动态 SQL 摊开在文件里，DBA 能直接看、能直接拿去客户端跑；写成注解就会变成一长串字符串，改一个条件都费劲。

**③ 示例代码** ——

```xml
<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE mapper
        PUBLIC "-//mybatis.org//DTD Mapper 3.0//EN"
        "http://mybatis.org/dtd/mybatis-3-mapper.dtd">

<mapper namespace="com.example.mapper.EmployeeMapper">

    <select id="selectAll" resultType="com.example.entity.Employee">
        SELECT * FROM employee
        <where>
            <if test="name != null and name != ''">
                employee.name LIKE CONCAT('%', #{name}, '%')
            </if>
        </where>
        ORDER BY employee.id DESC
    </select>

</mapper>
```

**④ 逐行拆解** ——
- 第一行 `encoding="UTF-8"` 不能省：XML 里有中文注释或中文字符串时，编码不对会报 `Invalid byte 1 of 1-byte UTF-8 sequence`。
- `DOCTYPE` 那三行是 MyBatis 的“语法说明书”，少了它 IDEA 会标红、标签也失去校验；照着模板保留即可。
- `namespace` 必须是**接口的全限定名**（包名 + 类名），只写 `EmployeeMapper` 或只写包名都绑不上。
- `<select id="selectAll">` 的 id 与方法名一一对应；**同一个 namespace 下 id 不能重复**，否则启动报 `Mapped Statements collection already contains value`。
- `<where>` 会智能处理开头的 `AND`/`OR`：如果 `<if>` 不成立，它不会留下一个孤零零的 `WHERE`；成立时也不会多出一个 `AND`。
- `#{name}` 是**预编译占位符**，最终变成 `?`，由 `PreparedStatement` 设值，能防 SQL 注入；`${}` 是字符串直接拼接，除动态表名/列名外不要用。
- `ORDER BY employee.id DESC`：新增的员工 id 最大，排最前面，前端一刷新就能看到刚加的人。

**⑤ 在你仓库里** —— `D:\my-project\xm-pro\springboot\src\main\resources\mapper\EmployeeMapper.xml` 第 6 行是 namespace、第 8~16 行是 `selectAll`（含 `<where>` 动态条件）、第 18~21 行是 `insert`、第 23~31 行是 `updateById`；`D:\my-project\xm-pro\springboot\src\main\java\com\example\mapper\EmployeeMapper.java` 第 13 行的方法名与第 8 行的 id 必须保持一致；XML 能被找到，靠的是 `D:\my-project\xm-pro\springboot\src\main\resources\application.yml` 第 14 行的 `mapper-locations`。

**⑥ 常见坑** —— ① `namespace` 写成 `com.example.mapper`（只到包）→ 启动可能不报错，调用时报 `Invalid bound statement` → 补成 `com.example.mapper.EmployeeMapper`。② XML 放在 `src/main/java/com/example/mapper/` 下 → Maven 默认**不复制 java 目录里的 xml**，运行时找不到 → 放到 `src/main/resources/mapper/`，或在 pom 里配 `<resources>`。③ SQL 里写 `age < 30` → `<` 被当成标签开头，XML 解析失败 → 写成 `&lt;` 或用 `<![CDATA[ ... ]]>` 包起来。

**⑦ 自测** —— `#{}` 和 `${}` 都能把参数放进 SQL，为什么老师反复强调优先用 `#{}`？

<details><summary>展开解析</summary>

`#{}` 会生成 `?` 占位符，走 `PreparedStatement` 预编译，参数只当“值”，**不参与 SQL 语法解析**，天然防注入；`${}` 是**字符串直接替换**，用户传 `1 OR 1=1` 就会变成 SQL 的一部分。只有动态表名、排序列这种“必须是 SQL 结构”的地方才用 `${}`，而且要做白名单校验。

</details>

### 2.8 @MapperScan

**① 讲义怎么说** —— 讲义“二、6”只有一句话：**“告诉 SpringBoot 如何扫描 mapper 包”**，对应启动类上那行 `@MapperScan("com.example.mapper")`；前面第 4、5 步刚建完 `mapper` 包和接口，第 6 步就是让 Spring 认识它们。

**② 一句话讲透** —— 如果把 Mapper 接口比作一排**上了锁的房间**，`@MapperScan` 就是交给 Spring 的**总钥匙 + 房间名单**：它告诉 Spring“`com.example.mapper` 这个包下面的所有接口，都是 MyBatis 的 Mapper，启动时逐个给它们生成代理、注册成 Bean”。没有这张名单，Spring 根本不知道这些接口的存在，`@Resource` 注入时就会说“找不到这个类型的 Bean”。它和每个接口上的 `@Mapper` 是两条路：`@Mapper` 是**逐个贴标签**，`@MapperScan` 是**整包批发**。项目里接口一多，后者更省事，也不容易漏。扫描范围写到接口所在包最准；写到 `com.example` 也行，会连子包一起扫，但范围越大启动越慢。

**③ 示例代码** ——

```java
package com.example;

import org.mybatis.spring.annotation.MapperScan;
import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;

@SpringBootApplication
@MapperScan("com.example.mapper")
public class SpringbootApplication {

    public static void main(String[] args) {
        SpringApplication.run(SpringbootApplication.class, args);
    }

}
```

**④ 逐行拆解** ——
- `@SpringBootApplication` 是组合注解，本身包含 `@Configuration`、`@EnableAutoConfiguration`、`@ComponentScan`；它只扫**当前包及子包**里的 `@Component/@Service/@Controller`，**不会**自动把 Mapper 接口注册成 Bean——这正是要 `@MapperScan` 的原因。
- `@MapperScan("com.example.mapper")` 的包名必须写到**接口所在的包**，写到 `com.example` 也行（会连子包一起扫），但范围越大启动越慢。
- 这个注解通常放在**启动类**上；放在一个普通的 `@Configuration` 类上也行，但那个类必须能被组件扫描到，否则等于没写。
- 多个包用数组：`@MapperScan({"com.example.mapper", "com.example.dao"})`，不要写两个 `@MapperScan`（重复注解会报错）。
- 仓库里 `EmployeeMapper` 上还有 `@Mapper`，与 `@MapperScan` 重复；**重复不会报错**，MyBatis 会去重，但初学阶段建议只留一种，避免“到底是谁注册的”说不清。

**⑤ 在你仓库里** —— `D:\my-project\xm-pro\springboot\src\main\java\com\example\SpringbootApplication.java` 第 8 行就是 `@MapperScan("com.example.mapper")`，第 7 行是 `@SpringBootApplication`；被扫描的接口在 `D:\my-project\xm-pro\springboot\src\main\java\com\example\mapper\EmployeeMapper.java` 第 10~11 行；注入点在 `D:\my-project\xm-pro\springboot\src\main\java\com\example\service\EmployeeService.java` 第 15~16 行。把第 8 行注释掉、同时把接口上的 `@Mapper` 也去掉，第 16 行的 `@Resource` 才会在启动时报“找不到 Bean”；只去掉其中一个，另一个仍能兜底。

**⑥ 常见坑** —— ① 启动报 `No qualifying bean of type 'com.example.mapper.EmployeeMapper' available` → `@MapperScan` 包名写错，且接口上也没贴 `@Mapper` → 对照接口所在包改成 `com.example.mapper`，或补上 `@Mapper`。② 把 `@MapperScan` 写在 `controller` 包下的某个类上 → 那个类本身没被扫描到，注解不生效 → 挪到启动类。③ 以为加了 `@MapperScan` 就可以删掉 `mybatis-spring-boot-starter` → 编译阶段就报“程序包 org.mybatis.spring.annotation 不存在” → 注解是 starter 提供的，依赖不能删。

**⑦ 自测** —— 只给接口写 `@Mapper`、启动类不写 `@MapperScan`，项目能不能跑？

<details><summary>展开解析</summary>

**通常能**：`mybatis-spring-boot-starter` 在没有发现 `@MapperScan` 时，会自动扫描启动类所在包及子包下带 `@Mapper` 的接口。但如果接口在**启动类包之外**（比如公共模块），自动扫描就够不着，必须显式写 `@MapperScan`。仓库两者都写，属于“双保险”，不冲突。

</details>

### 2.9 Service 业务层

**① 讲义怎么说** —— 讲义“二、7”：**“新建 service 包：在 com.example 下创建 service 分层包，用于存放业务逻辑类”**，新建 **“EmployeeService 业务类：处理员工相关业务代码”**，并加 `@Service`：**“将该类注册为 Spring 容器 Bean，供 Controller 自动注入使用”**；后面又强调 **“Service 层不能直接操作数据库，必须调用 Mapper 持久层”**。

**② 一句话讲透** —— Service 是**店长**：Controller 是前台接待，只负责收单；Mapper 是后厨，只会做菜；店长站在中间，接前台的订单、决定先做什么后做什么、要不要加料、出问题怎么补救。现在 `selectAll` 只是原样转发，看起来“多此一举”，但以后要加分页、按姓名过滤、删除前检查、事务回滚，全都会落在这个方法里——**Controller 不用改，Mapper 也不用改**。这就是分层最值钱的地方：改一处，不动全身。判断一个方法该不该放 Service，有个简单标准：**如果这段逻辑换个入口（定时任务、另一个 Controller）也要用，它就不属于 Controller**；只有取 header、设状态码这种纯 HTTP 的事，才留在 Controller。

**③ 示例代码** ——

```java
package com.example.service;

import com.example.entity.Employee;
import com.example.mapper.EmployeeMapper;
import com.github.pagehelper.PageHelper;
import com.github.pagehelper.PageInfo;
import jakarta.annotation.Resource;
import org.springframework.stereotype.Service;

import java.util.List;

@Service
public class EmployeeService {

    @Resource
    private EmployeeMapper employeeMapper;

    public List<Employee> selectAll(Employee employee) {
        return employeeMapper.selectAll(employee);
    }

    public PageInfo<Employee> selectPage(Employee employee, Integer pageNum, Integer pageSize) {
        PageHelper.startPage(pageNum, pageSize);
        List<Employee> list = employeeMapper.selectAll(employee);
        return PageInfo.of(list);
    }
}
```

**④ 逐行拆解** ——
- `@Service` 是 `@Component` 的特化版，作用一样：把类交给 Spring 容器，启动时创建**单例**对象；名字叫 Service 只是语义上标明“我是业务层”。
- `@Resource` 默认**按名字**注入，名字对不上再按类型；这里字段名 `employeeMapper` 和 Bean 名一致，直接注入成功。用 `@Autowired` 也能注入，两者在只有一个实现时效果一样。
- `selectAll` 现在只有一行：`return employeeMapper.selectAll(employee);`——**不要在这里 new Mapper**，Mapper 是代理对象，new 出来没有 SqlSession，调用必空指针。
- `selectPage` 里三行是一个固定套路：`PageHelper.startPage(...)` 开分页 → **紧接着**执行查询 → `PageInfo.of(list)` 收结果。顺序错了分页就失效（见 2.11）。
- 方法返回值用 `List<Employee>` / `PageInfo<Employee>`，**不要返回 `Result`**：`Result` 是给前端看的包装，属于 Controller 的职责，Service 保持“纯业务”。
- 以后加事务，会在方法上写 `@Transactional`；加校验，会在方法开头判断参数——这些位置现在空着，但已经预留好了。

**⑤ 在你仓库里** —— `D:\my-project\xm-pro\springboot\src\main\java\com\example\service\EmployeeService.java` 第 12~13 行是 `@Service`，第 15~16 行注入 Mapper，第 18~20 行是 `selectAll`，第 30~34 行是 `selectPage`；调用方在 `D:\my-project\xm-pro\springboot\src\main\java\com\example\controller\EmployeeController.java` 第 16~26 行；真正执行 SQL 的接口在 `D:\my-project\xm-pro\springboot\src\main\java\com\example\mapper\EmployeeMapper.java` 第 13 行。

**⑥ 常见坑** —— ① 在 Service 里写 `EmployeeMapper mapper = new EmployeeMapper();` → 接口不能实例化，编译就报错；就算用匿名类，也没有 SqlSession → 一律用 `@Resource` 注入。② 忘了写 `@Service` → Controller 启动时报 `No qualifying bean of type 'EmployeeService'` → 补注解，并确认类在启动类包及子包下。③ 把 `Result.success(...)` 写在 Service 里 → 业务层与 Web 层耦合，换一个客户端（比如定时任务）就用不了 → Service 只返回业务对象，包装交给 Controller。

**⑦ 自测** —— 现在 Service 只是把 Mapper 的调用原样转发，能不能删掉这一层，让 Controller 直接调 Mapper？

<details><summary>展开解析</summary>

**技术上能跑，但工程上不建议。** 分层不是为了现在多写几行，而是为了以后：分页、条件过滤、删除前校验、事务（一个方法里改两张表）、权限判断，都应该放在 Service；Controller 只关心 HTTP，Mapper 只关心 SQL。删掉 Service，这些逻辑就会塞进 Controller，接口一多就重复、难维护。**现在多一层，以后少改十处。**

</details>

### 2.10 Controller 接口层

**① 讲义怎么说** —— 讲义“二、11”给出 `EmployeeController` 完整代码，并在“三、4”逐行解释：**“@RestController 组合注解 = @Controller + @ResponseBody”**；`@RequestMapping("/employee")` **“给当前类下所有接口统一添加访问前缀”**，**“当前接口完整地址 = 前缀 + 方法上的路径”**；`@Resource` 则是**“从 Spring 容器中找到 EmployeeService 对象，自动赋值给变量”**。

**② 一句话讲透** —— Controller 是公司的**前台**：客人（浏览器）拿着 URL 进来，前台先看“找哪个部门”（`@RequestMapping` 前缀）、办什么事（`@GetMapping` 子路径）、带什么材料（方法参数），然后转给店长（Service），最后把结果装进统一信封（`Result`）递回去。前台**不碰数据库、不写业务规则**，只做三件事：**收请求、调 Service、包 Result**。这套动作每天重复，所以 Spring 用注解把它压到几行。它和 Service 的分工可以用一句话记：**Controller 懂 HTTP，Service 懂业务，Mapper 懂 SQL**；出了问题时看报错落在哪一层，定位会快很多。记住：**Controller 里不应该出现 SQL，也不应该出现 `new` 出来的 Service**。

**③ 示例代码** ——

```java
@RestController
@RequestMapping("/employee")
public class EmployeeController {

    @Resource
    private EmployeeService employeeService;

    @GetMapping("/selectAll")
    public Result selectAll(Employee employee) {
        List<Employee> list = employeeService.selectAll(employee);
        return Result.success(list);
    }

    @GetMapping("/selectPage")
    public Result selectPage(Employee employee,
                             @RequestParam(defaultValue = "1") Integer pageNum,
                             @RequestParam(defaultValue = "10") Integer pageSize) {
        PageInfo<Employee> pageInfo = employeeService.selectPage(employee, pageNum, pageSize);
        return Result.success(pageInfo);
    }
}
```

**④ 逐行拆解** ——
- `@RestController` = `@Controller` + `@ResponseBody`：前者把类交给 Spring，后者让**方法返回值直接序列化成 JSON**，而不是去找一个 JSP 页面。前后端分离项目里，Controller 基本都用它。
- `@RequestMapping("/employee")` 是类级前缀，`@GetMapping("/selectAll")` 是方法级路径，拼起来才是 `http://localhost:8080/employee/selectAll`；前缀写错一个字母，前端就是 404。
- `@GetMapping` 只接收 **GET**；新增用 `@PostMapping`、修改用 `@PutMapping`、删除用 `@DeleteMapping`，方法不对会返回 **405 Method Not Allowed**。
- `selectAll(Employee employee)` 没有 `@RequestParam`，Spring 会按**同名属性**把查询参数 `?name=张&sex=男` 装进 `Employee` 对象，这叫“对象参数绑定”。
- `@RequestParam(defaultValue = "1")`：前端不传 `pageNum` 时给默认值 1，不传 `pageSize` 时给 10，避免 `null` 传进 `PageHelper` 报错。
- `Result.success(list)` 把数据装进 `data`，配合上一讲的 `code/msg`，前端才能统一用 `res.code === '200'` 判断。

**⑤ 在你仓库里** —— `D:\my-project\xm-pro\springboot\src\main\java\com\example\controller\EmployeeController.java` 第 12~13 行是类注解，第 16~17 行注入 Service，第 22~26 行是 `selectAll`，第 43~49 行是 `selectPage`；前端调用在 `D:\my-project\xm-pro\vue\src\views\Employee.vue` 第 104~115 行，`request.get('/employee/selectPage', { params: {...} })` 传的正是 `pageNum/pageSize/name`；这个请求能发到 8080，靠的是 `D:\my-project\xm-pro\vue\src\utils\request.js` 第 5 行的 `baseURL: 'http://localhost:8080'`。

**⑥ 常见坑** —— ① 浏览器访问报 404 → 类上 `/employee` 和方法上 `/selectAll` 拼错，或 Controller 不在启动类包及子包下 → 对照 `http://localhost:8080/employee/selectAll` 一个字母一个字母核。② 报 405 Method Not Allowed → 用浏览器地址栏（GET）访问了 `@PostMapping("/add")` → 用 Postman 或前端发 POST，或临时改成 `@GetMapping` 测试。③ 前端报跨域 `has been blocked by CORS policy` → 前后端端口不同（5173 调 8080）且没配跨域 → 加 `@CrossOrigin` 或全局 `CorsConfig`（仓库在 `common/CorsConfig.java`）。

**⑦ 自测** —— 同一个 `/employee` 前缀下，`selectAll` 能用浏览器地址栏直接访问，`add` 为什么不行？

<details><summary>展开解析</summary>

因为浏览器地址栏发起的是 **GET** 请求，而 `add` 方法标的是 `@PostMapping`，Spring 找不到匹配的 GET 处理器，返回 **405 Method Not Allowed**。GET 适合查询（参数在 URL 上），POST 适合提交数据（参数在请求体里）。测试 POST 要用 Postman、Apifox 或前端页面。

</details>

### 2.11 分页 PageHelper

**① 讲义怎么说** —— 讲义“五、1 在项目的 pom.xml 文件里，引入分页插件”，给出 `pagehelper-spring-boot-starter:2.1.0` 的完整坐标，并解释 **“Maven 通过 groupId + artifactId + version 三维定位一个 jar 包”**；第 3 步给代码，第 4 步展示分页效果——**“数据库里的记录增加一些，以供查看分页效果”**。

**② 一句话讲透** —— PageHelper 是一台**会自动切页的复印机**：大家仍然只写 `SELECT * FROM employee`，它在 SQL 执行前偷偷改成 `SELECT ... LIMIT 0,10`，同时再发一条 `SELECT COUNT(*)` 算总条数；查完之后把“当前页数据 + 总数 + 页码 + 每页条数”一起装进 `PageInfo`。就像点外卖说“第 2 页、每页 10 条”，店家不用大家自己数到第 11 条——**大家只管写查询，切页交给它**。原理是把分页参数存进 `ThreadLocal`，所以它只对**紧接着的那一次查询**生效。它最大的好处是**不改 SQL**：原来怎么写还怎么写，只在外面套三行；代价是分页参数依赖当前线程，异步线程、线程池里直接调用会失效。

**③ 示例代码** ——

```java
public PageInfo<Employee> selectPage(Employee employee, Integer pageNum, Integer pageSize) {
    // ① 把“第几页、每页几条”放进当前线程的 ThreadLocal
    PageHelper.startPage(pageNum, pageSize);
    // ② 必须紧接着执行查询，PageHelper 会改写这条 SQL 并额外查一次总数
    List<Employee> list = employeeMapper.selectAll(employee);
    // ③ 用查询结果构造 PageInfo：total、list、pageNum、pageSize、pages 都在里面
    return PageInfo.of(list);
}
```

**④ 逐行拆解** ——
- `PageHelper.startPage(pageNum, pageSize)` 只做一件事：把参数绑到当前线程，**不执行 SQL**；此时数据库毫无动静。
- 下一行 `employeeMapper.selectAll(employee)` 才是真正触发点：PageHelper 的拦截器发现 ThreadLocal 里有分页参数，就把原 SQL 改写成 `LIMIT ?, ?`，再执行一条 `COUNT(*)`。
- **中间不能插别的查询**：ThreadLocal 是“一次性”的，谁先执行谁消耗掉，插一条别的查询，分页就跑到别人身上了。
- `PageInfo.of(list)` 要求传的是 `Mapper` 查出来的原始结果：如果 `list` 真是 PageHelper 返回的 `Page`（它偷偷继承了 `ArrayList`），就能读出真实总数；如果传的是自己 `new` 的 `ArrayList`，`PageInfo` 只能把 `total` 当成当前列表长度、`pages` 恒为 1，分页信息就失真了。
- `PageInfo` 的字段：`total`（总条数）、`list`（当前页数据）、`pageNum`、`pageSize`、`pages`（总页数）、`hasNextPage` 等，前端拿 `res.data.list` 和 `res.data.total` 就够渲染表格和分页条。
- 分页参数从 Controller 的 `@RequestParam(defaultValue = "1")` 来，前端 `el-pagination` 的 `v-model:current-page` 一变就重新请求。

**⑤ 在你仓库里** —— `D:\my-project\xm-pro\springboot\src\main\java\com\example\service\EmployeeService.java` 第 30~34 行就是 `startPage → selectAll → PageInfo.of` 三件套；`D:\my-project\xm-pro\springboot\pom.xml` 第 44~54 行是 `pagehelper-spring-boot-starter:2.1.0`，注意里面排除了 `org.mybatis:mybatis`；Controller 入口在 `D:\my-project\xm-pro\springboot\src\main\java\com\example\controller\EmployeeController.java` 第 43~49 行；前端分页条在 `D:\my-project\xm-pro\vue\src\views\Employee.vue` 第 40~49 行，`@current-change="load"` 会带着新页码重新请求。

**⑥ 常见坑** —— ① `startPage` 之后先执行了别的查询（比如先查用户），再查员工 → 分页参数被前一次查询用掉，员工查询变成全量 → 把 `startPage` 挪到目标查询的**上一行**。② 启动报 `NoSuchMethodError`（比如 `SqlSessionFactoryBean` 相关）或 Mapper 扫描异常 → PageHelper 2.1.0 自带的 mybatis 与项目里的 mybatis-spring 版本冲突 → 按仓库写法加 `<exclusion>` 排除 `org.mybatis:mybatis`。③ 前端总页数一直是 1、`total` 恰好等于当前页条数 → Service 返回的是自己 `new` 的 List，不是 Mapper 查出来的原始结果 → 用 `PageInfo.of(list)` 把 Mapper 的返回值原样包住。

**⑦ 自测** —— `PageHelper.startPage(1, 10)` 之后，先查了一次用户表，再查员工表，员工查询会分页吗？

<details><summary>展开解析</summary>

**不会。** 分页参数存在当前线程的 `ThreadLocal` 里，是“一次性的”，**第一条执行的查询**会把它取走。先查用户表，分页就作用在用户查询上；等查员工时参数已经没了，SQL 原样执行，返回全部数据。所以 `startPage` 必须**紧挨着**目标查询写。

</details>

### 2.12 常见报错排查

**① 讲义怎么说** —— 讲义“二、11”在贴出 Controller 代码后特意提醒：**“此时出现爆红是正常的”**（因为 `Employee`、`EmployeeService` 还没建）；分页一节又提醒**“注意，有的地方需要导入相应的类”**——这两句话背后，是初学阶段最常见的两类“假报错”和“真报错”。

**② 一句话讲透** —— 看报错像**医院分诊**：先别被满屏红字吓住，直接翻到最下面找 `Caused by`，那才是病根；再往上找**第一行出现自己包名**（`com.example`）的位置，那是大家代码里真正出事的地方。MyBatis 的报错基本归四类：**连不上库**（网络/账号/库名）、**找不到 Mapper**（扫描/绑定）、**SQL 写错**（表名列名/语法）、**依赖冲突**（版本打架）。先分类，再对症，比逐行读堆栈快十倍。排查时还要养成一个习惯：**先复现、再动手**，把请求 URL、请求方式、完整报错原文三样凑齐，很多“玄学问题”看一眼就清楚了；只凭一句“报错了”去猜，往往越改越乱。

**③ 示例代码** ——

```bash
# ① 连不上数据库
Caused by: java.net.ConnectException: Connection refused: connect

# ② 接口和 XML 没绑上
org.apache.ibatis.binding.BindingException: Invalid bound statement (not found):
com.example.mapper.EmployeeMapper.selectAll

# ③ Spring 与 MyBatis 版本不兼容（Boot 3.2+ 配了旧版 mybatis-spring）
java.lang.IllegalArgumentException:
Invalid value type for attribute 'factoryBeanObjectType': java.lang.String

# ④ Mapper 没被扫描到，注入失败
No qualifying bean of type 'com.example.mapper.EmployeeMapper' available
```

**④ 逐行拆解** ——
- `Connection refused`：MySQL 服务没启动、端口不是 3306、或者 URL 里主机写错。先在命令行 `mysql -uroot -p123456` 能登进去，再回来看 yml。
- `Invalid bound statement`：九成是**三处没对齐**——`namespace` 不是接口全名、`id` 和方法名不一致、`mapper-locations` 没扫到 XML。启动阶段不报，第一次调用才炸。
- `Invalid value type for attribute 'factoryBeanObjectType'`：这是 **Spring 6.1（Boot 3.2+）与旧版 mybatis-spring 3.0.2 及以下**的已知不兼容；把 `mybatis-spring-boot-starter` 升到 **3.0.5** 即可，仓库就是这个版本。
- `No qualifying bean`：Spring 容器里没有这个 Bean，通常是 `@MapperScan` 包名写错、接口不在扫描范围，或忘了加 `@Mapper`/`@MapperScan`。
- 还有一类**不是报错但很常见**：控制台一片安静，查出来全是 `null`——那要往 `resultType`、字段名、setter 上找，见 2.5。

**⑤ 在你仓库里** —— 连库配置看 `D:\my-project\xm-pro\springboot\src\main\resources\application.yml` 第 1~6 行；绑定关系看 `D:\my-project\xm-pro\springboot\src\main\resources\mapper\EmployeeMapper.xml` 第 6~16 行与 `D:\my-project\xm-pro\springboot\src\main\java\com\example\mapper\EmployeeMapper.java` 第 13 行；扫描配置看 `D:\my-project\xm-pro\springboot\src\main\java\com\example\SpringbootApplication.java` 第 8 行；版本冲突看 `D:\my-project\xm-pro\springboot\pom.xml` 第 30~34 行和第 44~54 行。

**⑥ 常见坑** —— ① 启动报 `Failed to configure a DataSource: 'url' attribute is not specified` → yml 缩进错了，`url` 没挂在 `datasource` 下，或文件名写成了 `application.yaml` 之外的拼写 → 检查缩进和文件名，四个数据源属性左对齐。② 报 `Port 8080 was already in use` → 上一次启动的进程没关，或别的软件占了 8080 → 任务管理器结束 `java.exe`，或在 yml 里改 `server.port`。③ 报 `Unknown column 'xxx' in 'field list'` → XML 里的列名和表结构不一致（比如把 `no` 写成 `number`）→ 用 `DESC employee;` 对一遍列名，或直接 `SELECT *` 先跑通再优化。

**⑦ 自测** —— 控制台打了一大段堆栈，应该先看哪一行？

<details><summary>展开解析</summary>

先翻到**最下面**看最后一个 `Caused by`（那才是根因），再往上找**第一行带自己包名 `com.example`** 的位置（那是大家代码真正出错的行）。最上面那行通常只是“被谁调用”，信息量最小；`Caused by` 链要从下往上读，越往下越接近病根。

</details>
