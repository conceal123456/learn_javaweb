## 0. 这一讲在整门课里的位置

第 7 讲把工程立起来、把 `Result` 和全局异常装好，第 8 讲接上数据库，第 9 讲把「一张表怎么查、怎么加、怎么改、怎么删」讲成了模板，第 10 讲又用 `user` 表做出了登录。到这一讲，前面散着练的动作要第一次合到一个页面里：管理员列表、新增、改密码、删除，四件事共用一张 `user` 表、一套 `Result`、一个 `UserManage.vue`。

这一讲的分量在于「闭环」：后端从 Controller 一路写到 `UserMapper.xml`，前端从路由、菜单一路写到弹窗和表格，中间没有哪一环是老师替大家写好的。以前写的接口一次只演示一个动作，这次一个页面里四个按钮各自对应一条完整链路，任何一环断了页面都会有反应——这正是最好的调试训练。

再往后看，这一讲的写法会被反复复制：商品管理、订单管理、员工管理，都是「列表 + 弹窗 + 增删改」这同一个骨架；`Result` 的 `code` 约定会成为全站接口的契约；子路由加菜单项这一对写法，是后台每一个新页面的入口。所以这一讲不是多学一个注解，而是学会一套可以照着搬的页面模板。

## 2. 知识点精讲

### 2.1 四层分工：Controller / Service / Mapper 接口 / Mapper.xml

**① 讲义怎么说** —— "一、后端代码"只给了四个文件名：`Mapper/UserMapper.java`、`Mapper/UserMapper.xml`、`service/UserService.java`、`controller/UserController.java`；功能说明里则把要求写成了业务话："后端先判断 username 是否重复"、"后端根据 id 查询数据库，对比旧密码"、"根据管理员唯一 ID 执行删除"。讲义没有解释这四个文件为什么必须分开。

**② 一句话讲透** —— 把一次请求想成去医院看病：`UserController` 是挂号窗口，只管收资料、看单子齐不齐、把结果告诉病人；`UserService` 是医生，懂业务规则——账号重不重、数据存不存在、这条能不能删；`UserMapper` 接口是那张化验单，只写"要查什么"，不写"怎么查"；`UserMapper.xml` 才是化验室里真正操作的仪器，一行行 SQL 由它执行。四层分开的好处是：换数据库只动 XML，改规则只动 Service，加接口只在 Controller 加一个方法，谁也不牵连谁。

**③ 示例代码** ——

```java
public interface UserMapper {                       // 只有方法签名，没有实现

    User selectByUsernameAndPassword(@Param("username") String username,
                                     @Param("password") String password);  // 登录

    List<User> selectAll();                          // 查全部管理员

    User selectByUsername(@Param("username") String username);

    User selectById(@Param("id") Integer id);

    int insert(User user);                           // 返回影响行数

    int updatePassword(@Param("id") Integer id,
                       @Param("newPwd") String newPwd);

    int deleteById(@Param("id") Integer id);
}
```

**④ 逐行拆解** ——
- `public interface UserMapper` 没有实现类也能注入：启动类第 8 行 `@MapperScan("com.example.mapper")` 让 MyBatis 扫描这个包，为每个接口生成 JDK 动态代理对象并注册成 Spring Bean。大家 `@Resource private UserMapper userMapper;` 拿到的是代理，不是接口本身。
- 代理怎么知道该执行哪条 SQL：拿"接口全限定名"去匹配 XML 的 `namespace`，拿"方法名"去匹配标签的 `id`。`UserMapper.java` 第 14 行的 `selectAll` 对应 `UserMapper.xml` 第 13 行 `<select id="selectAll">`，两边差一个字母就报 `Invalid bound statement`。
- `@Param("username")` 是给 `#{username}` 这个名字下定义。只有一个参数时 MyBatis 还能猜，两个以上不写就会报 `Parameter 'id' not found. Available parameters are [arg0, arg1, param1, param2]`。
- 返回 `int` 的方法拿的是**影响行数**：插入 1 行返回 1，更新 0 行返回 0。Service 就是靠这个数字判断"到底有没有动到数据"。
- `List<User>` 与 `User` 的差别只是结果条数；`resultType` 写全限定类名，列名到属性名的对应靠 `application.yml` 第 18 行的 `map-underscore-to-camel-case: true`。
- `UserController` 里看不到一句 SQL，`UserMapper.xml` 里看不到一句 Java 判断——这就是分层的目的：让每一层只回答一个问题。

**⑤ 在你仓库里** ——
- `D:\my-project\xm-pro\springboot\src\main\java\com\example\mapper\UserMapper.java` 第 8~31 行，七个方法签名就是本讲全部数据操作的清单。
- `D:\my-project\xm-pro\springboot\src\main\resources\mapper\UserMapper.xml` 第 5 行是 `namespace`，第 8~40 行是七条 SQL。
- `D:\my-project\xm-pro\springboot\src\main\java\com\example\service\UserService.java` 第 18~65 行：登录、列表、新增、改密、删除的业务判断都在这里。
- `D:\my-project\xm-pro\springboot\src\main\java\com\example\SpringbootApplication.java` 第 8 行的 `@MapperScan` 是整条链的起点。

**⑥ 常见坑** —— ① 启动报 `Invalid bound statement (not found): com.example.mapper.UserMapper.selectAll` → XML 没被扫到（不在 `resources/mapper/` 下、`mapper-locations` 没配）或 `namespace`/`id` 拼错 → 先看 `application.yml` 第 14 行，再逐个核对 namespace 与方法名。② 多参数方法报 `Parameter 'id' not found` → 参数没加 `@Param` → 每个参数都写 `@Param("同名")`，XML 用同名占位。③ 新增成功但返回的 `id` 是 `null` → `<insert>` 少了 `useGeneratedKeys="true" keyProperty="id"` → 补上这两个属性，自增主键才会回写到对象。

**⑦ 自测** —— `UserMapper` 只是一个接口，没有实现类，为什么 `@Resource` 注入后能直接调？

<details><summary>展开解析</summary>

因为注入的不是接口本身，而是 MyBatis 启动时生成的**动态代理对象**。`@MapperScan` 扫描到接口后，代理会按「接口全限定名 = namespace、方法名 = 标签 id」去 XML 里找 SQL，找到就替大家执行，并把结果集映射成 `User`。所以接口和 XML 必须成对出现，缺一个都会在启动或第一次调用时报错。

</details>

### 2.2 管理员列表

**① 讲义怎么说** —— 讲义没有单独列"列表"这一条，但功能说明第 2 条写的是"**选中表格中某管理员**，弹出弹窗"，第 3 条写"删除成功后，**页面自动刷新表格数据**"——表格里的数据从哪来，讲义默认大家已经会了。后端文件清单里的 `UserController` 就是承载这个查询接口的地方。

**② 一句话讲透** —— 列表接口干的事，是把冰箱里的东西全摆到桌上：`select * from user` 一次把整张表捞出来，Service 原样转发，Controller 用 `Result.success(list)` 装进信封，前端 `created()` 里发一次 GET，把 `res.data` 交给 `el-table` 的 `:data`。这条链上任何一环改名，表格就空——所以排查"表格没数据"永远先看 F12 里 `/user/list` 的响应，而不是盯着页面改样式。

**③ 示例代码** ——

```java
// UserController.java 第 34~38 行
@GetMapping("/list")
public Result list() {
    List<User> list = userService.selectAll();
    return Result.success(list);          // data 里装的是一个数组
}

// UserService.java 第 25~27 行
public List<User> selectAll() {
    return userMapper.selectAll();        // 没有业务判断，直接转发
}
```

**④ 逐行拆解** ——
- `@GetMapping("/list")` 与类上的 `@RequestMapping("/user")` 拼起来才是完整地址 `/user/list`；只在方法上写 `/list`，浏览器访问 `/list` 会 404。
- `List<User>` 是泛型，编译后擦除，但 Jackson 序列化时按对象的 getter 输出：`id`、`username`、`password`、`name` 四个字段都会出现。也就是说列表接口把密码也返回给前端了，这是本课程的简化，真实项目要 `@JsonIgnore` 或单独建一个不含密码的 VO。
- `Result.success(list)` 走的是 `success(Object data)` 这个重载，`code` 固定 `"200"`、`msg` 固定 `"请求成功"`，`data` 就是数组。
- `UserMapper.xml` 第 13~15 行的 `select * from user`：`*` 依赖表结构和实体字段一一对应；表里多一个字段、实体没有，MyBatis 默认忽略，不报错，但大家会疑惑"为什么查出来少了"。
- 前端 `loadData()` 放在 `created()` 里调，此时 DOM 还没渲染，但请求回来给 `tableData` 赋值会触发响应式更新，表格自然出现。
- 每次增删改成功后都再调一次 `loadData()`，这叫"重新拉取"而不是"本地删一行"——数据以数据库为准，永远不会出现页面和库里不一致。

**⑤ 在你仓库里** ——
- `D:\my-project\xm-pro\springboot\src\main\java\com\example\controller\UserController.java` 第 34~38 行 `list()` 方法。
- `D:\my-project\xm-pro\springboot\src\main\java\com\example\service\UserService.java` 第 25~27 行 `selectAll()`。
- `D:\my-project\xm-pro\springboot\src\main\resources\mapper\UserMapper.xml` 第 13~15 行 `<select id="selectAll">`。
- `D:\my-project\xm-pro\vue\src\views\UserManage.vue` 第 88~91 行 `created()`、第 94~102 行 `loadData()`。

**⑥ 常见坑** —— ① 表格空白 → `/user/list` 返回的 `data` 是 `null`（表里没数据，或连错了库）→ 先在浏览器直接访问 `http://localhost:8080/user/list` 看原始 JSON。② 有数据但不显示 → `el-table-column` 的 `prop` 写成 `userName`，与后端 `username` 大小写不一致 → 照 `User.java` 第 5 行改回小写。③ 控制台报跨域 → 前端 5173 直接请求 8080，后端跨域没生效 → 确认 `CorsConfig` 已加载，或按实训 6 配 Vite 代理。

**⑦ 自测** —— 列表页每次新增、删除后都重新请求一次 `/user/list`，为什么不直接在 `tableData` 里 `push`、`splice`？

<details><summary>展开解析</summary>

因为数据库才是唯一事实来源。本地改数组看起来更快，但一旦后端有默认值、排序规则，或者别的页面也在改同一张表，本地数组就会和库里不一致。重新拉一次最省心，本讲的数据量完全感觉不到慢，也顺便避免了"删除后下标错位"这类问题。

</details>

### 2.3 新增判重

**① 讲义怎么说** —— 功能说明第 1 条："前端填写账号、密码、姓名，弹窗提交；**后端先判断 username 是否重复，重复返回 400 提示；不重复插入 user 表**。"

**② 一句话讲透** —— 判重像办会员卡：柜员先翻名册看这个名字有没有登记过，有就摇头说"这个名字有人用了"，没有才往上写。顺序必须是"先查后插"，查的字段也必须是 `username` 本身，不是 id、不是密码。还要知道它只防"正常情况下"的重复：两个人同一瞬间提交同一个账号，可能都查到"没有"、都去插入。真正兜底的是数据库给 `username` 加唯一索引，课程数据量小，先查一次够用，但心里要有这根弦。

**③ 示例代码** ——

```java
// UserService.java 第 32~38 行
public int insert(User user) {
    User u = userMapper.selectByUsername(user.getUsername());  // 1. 按账号查
    if (u != null) {
        return 0;                                              // 2. 查到了：已存在
    }
    return userMapper.insert(user);                            // 3. 没查到：真插入
}
```

**④ 逐行拆解** ——
- `selectByUsername` 返回 `User` 而不是 `int`：只要不是 `null` 就说明有记录，比 `count(*)` 更直观，将来想顺手取昵称也方便。
- `return 0` 是这一讲的"暗号"：Service 不抛异常、不返回布尔，用 0 表示"业务上没插入"。Controller 拿 0 去换 `Result.error("400", "账号已存在，新增失败")`，前端只认 `code`。
- `userMapper.insert(user)` 的返回值是影响行数，正常是 1。若它返回 0 却没走判重，说明 SQL 有别的问题（字段没对上、表名错），Controller 照样提示"账号已存在"——这是这套约定的小坑，提示语会误导人。
- XML 第 18~20 行 `useGeneratedKeys="true" keyProperty="id"`：插入后 MySQL 生成的自增 id 会被写回 `user.id`，所以 Controller 第 50 行能 `return Result.success(user)`，前端立刻拿到新记录。
- Controller 用 `@RequestBody User user` 接 JSON，要求请求头是 `Content-Type: application/json`——`request.js` 第 11 行已经统一加好了。
- 前端 `handleAdd()` 先做非空判断再发请求，这只是体验优化，不能替代后端判重：绕过页面直接调接口，一样能提交空账号。

**⑤ 在你仓库里** ——
- `D:\my-project\xm-pro\springboot\src\main\java\com\example\service\UserService.java` 第 32~38 行 `insert()`，判重就这三行。
- `D:\my-project\xm-pro\springboot\src\main\java\com\example\controller\UserController.java` 第 43~51 行 `add()`，0 换 400 的写法在这里。
- `D:\my-project\xm-pro\springboot\src\main\resources\mapper\UserMapper.xml` 第 18~25 行 `<insert>` 和 `selectByUsername`。
- `D:\my-project\xm-pro\vue\src\views\UserManage.vue` 第 111~128 行 `handleAdd()`。

**⑥ 常见坑** —— ① 重复账号还能新增成功 → 判重写在了 `insert` 之后，或者查询条件用错字段 → 把 `selectByUsername` 挪到 `insert` 之前，确认传的是 `user.getUsername()`。② 新增成功但返回的 `id` 是 `null` → XML 的 `<insert>` 没写 `useGeneratedKeys`/`keyProperty` → 补上；换成没有自增的表还要用 `<selectKey>`。③ 报 `Duplicate entry 'admin' for key 'user.username'`，页面却是 500 → 库里已有唯一索引，判重没拦住首尾空格或大小写 → 前端 `trim()`、后端统一去空格，或捕获 `DuplicateKeyException` 转成 400。

**⑦ 自测** —— 判重为什么放在 Service，不放在 Controller？

<details><summary>展开解析</summary>

Controller 的职责是"收参数、调服务、包结果"，不该懂业务规则；判重是业务规则，将来批量导入、注册接口也要用，放 Service 才能复用。放 Controller 会让每个入口都抄一遍，抄漏一个就出脏数据。

</details>

### 2.4 修改密码

**① 讲义怎么说** —— 功能说明第 2 条："选中表格中某管理员，弹出弹窗；传入 **id、旧密码、新密码**；后端根据 id 查询数据库，**对比旧密码，旧密码一致才执行 update 更新密码**。返回格式全部复用项目自带 Result 统一返回类，成功 code=200，业务错误 code=400，前端用 ElMessage 弹窗提示。"

**② 一句话讲透** —— 改密码像在银行改预留密码：先报账号（id）把档案调出来，再报旧密码，柜员在柜台里核对，一致才让你设新密码。关键有两点：一是**比对必须发生在服务端**，旧密码不能发给前端去比，因为前端代码用户想怎么改就怎么改；二是**更新只写新密码**，旧密码只用来校验，不参与 SQL。整个动作就是"查人 → 比旧密码 → 更新"三步，任何一步失败都要给出不同的提示，用户才知道该改哪里。

**③ 示例代码** ——

```java
// UserService.java 第 45~57 行
public int updatePassword(Integer id, String oldPwd, String newPwd) {
    User user = userMapper.selectById(id);          // 1. 按 id 查人
    if (user == null) {
        return -1;                                   // -1：人不存在
    }
    if (!user.getPassword().equals(oldPwd)) {
        return 0;                                    // 0：旧密码不对
    }
    return userMapper.updatePassword(id, newPwd);    // 1：改成功
}
```

**④ 逐行拆解** ——
- `selectById(id)` 而不是 `selectByUsernameAndPassword`：这里还没有新密码，不能拿"账号+密码"去查；先按主键定位人，再单独比密码。
- `return -1`、`return 0`、影响行数：三种结果分别对应"人没了""密码错""改成功"，Controller 第 81~87 行据此返回两条不同的 400 和一条 200。
- `user.getPassword().equals(oldPwd)` 依赖库里密码非空。更稳的写法是把常量放前面：`oldPwd.equals(user.getPassword())`，这样即使查出 `null` 也只返回 `false`，不会抛空指针。
- `updatePassword(id, newPwd)` 的 XML 只有 `set password = #{newPwd} where id = #{id}`，所以 `@Param("newPwd")` 的名字必须和 `#{newPwd}` 一字不差。
- Controller 用 `Map<String, Object>` 接参，是因为前端提交的是 `{id, oldPwd, newPwd}` 三个异构字段，没有对应的实体；用 Map 就得自己做类型转换和空值判断，第 64~74 行就是在补这层防护，避免 `null.toString()` 变成 500。
- 成功后返回 `Result.success()`，没有 `data`；前端只需要知道 `code` 是 200，然后关弹窗、提示成功。

**⑤ 在你仓库里** ——
- `D:\my-project\xm-pro\springboot\src\main\java\com\example\controller\UserController.java` 第 57~88 行 `updatePassword()`，含空值与 id 格式校验。
- `D:\my-project\xm-pro\springboot\src\main\java\com\example\service\UserService.java` 第 45~57 行，三态返回在这里。
- `D:\my-project\xm-pro\springboot\src\main\resources\mapper\UserMapper.xml` 第 28~35 行 `selectById` 与 `updatePassword`。
- `D:\my-project\xm-pro\vue\src\views\UserManage.vue` 第 131~134 行 `openPwdDialog()`、第 137~152 行 `handleUpdatePassword()`。

**⑥ 常见坑** —— ① 点"确定"报 500，控制台是 `NullPointerException` → 前端字段名和 `params.get("oldPwd")` 对不上，取到 `null` 又调 `toString()` → 对齐字段名；后端保留第 64~67 行的空值判断。② 旧密码明明正确却提示"旧密码错误" → 输入框带了首尾空格，或库里存的密码本身带空格 → 提交前 `trim()`，新增时也不要把空格存进去。③ 改完密码新密码登录不上 → XML 的 `where id = #{id}` 漏写，整表密码被改成同一个值 → 先 `select` 看影响行数，确认 `update` 带了主键条件。

### 2.5 删除管理员

**① 讲义怎么说** —— 功能说明第 3 条："**删除操作前弹出确认弹窗，防止误删**；根据管理员唯一 ID 执行删除；删除成功后，**页面自动刷新表格数据**，给出绿色成功提示；**不支持恢复（物理删除）**。"

**② 一句话讲透** —— 删除是从名册上把这一页撕掉，不是打个叉：`delete from user where id = ?` 一执行，这行数据就真没了，没有回收站。所以三道保险缺一不可：前端先弹确认框（防手滑）、后端按主键删（防一次删一片）、删完重新拉列表（防页面还显示已经不存在的人）。id 从当前行的 `row.id` 来，拼在 URL 路径上，后端用 `@PathVariable` 接——这也顺便解释了为什么删除不用 `@RequestBody`。

**③ 示例代码** ——

```java
// UserController.java 第 93~100 行
@DeleteMapping("/delete/{id}")
public Result delete(@PathVariable Integer id) {
    int row = userService.deleteById(id);       // 影响行数
    if (row <= 0) {
        return Result.error("400", "管理员不存在，删除失败");
    }
    return Result.success();
}
```

**④ 逐行拆解** ——
- `@DeleteMapping` 对应 HTTP 的 DELETE 方法，前端必须用 `request.delete(...)`；用 `request.post` 调会得到 405。
- `{id}` 是路径变量占位符，`@PathVariable Integer id` 按名字取值，并把字符串 `"3"` 自动转成数字 `3`；名字不一致时要写 `@PathVariable("id")`。
- `row <= 0` 而不是 `== 0`：影响行数不可能是负数，`<=` 是防御写法；真删掉 1 行返回 1，id 不存在返回 0。
- 物理删除之后没有任何地方能找回数据，所以前端 `$confirm` 的"取消"必须真的能取消——`this.$confirm(...).then(...)` 只有点"确定"才进 then。
- `deleteById` 的 SQL 只有一句 `delete from user where id = #{id}`；`where` 是命门，漏掉就是清空整张表。
- 删除成功后 `loadData()` 重新请求，而不是 `tableData.splice(index, 1)`；后者在分页、排序场景下会错位。

**⑤ 在你仓库里** ——
- `D:\my-project\xm-pro\springboot\src\main\java\com\example\controller\UserController.java` 第 93~100 行 `delete()`。
- `D:\my-project\xm-pro\springboot\src\main\java\com\example\service\UserService.java` 第 62~65 行 `deleteById()`。
- `D:\my-project\xm-pro\springboot\src\main\resources\mapper\UserMapper.xml` 第 38~40 行 `<delete id="deleteById">`。
- `D:\my-project\xm-pro\vue\src\views\UserManage.vue` 第 155~171 行 `handleDelete()`，`$confirm` 与 `.catch(() => {})` 都在这里。

**⑥ 常见坑** —— ① 点"删除"控制台报 `Uncaught (in promise) cancel` → `$confirm` 点取消会 reject，没有 catch → 末尾加 `.catch(() => {})`，仓库第 170 行就是这么写的。② 浏览器报 405 Method Not Allowed → 前端用了 GET，或后端写成了 `@PostMapping` → 前后端统一成 DELETE 加 `/delete/{id}`。③ 提示"删除成功"但表格里还有 → 成功分支忘了调 `loadData()`，或请求还没回来就关了弹窗 → 把刷新放进 `then` 里 `code` 判断之后。

**⑦ 自测** —— 讲义为什么强调"物理删除、不支持恢复"？如果要做"可恢复"，该怎么改？

<details><summary>展开解析</summary>

物理删除是 `delete` 真删行；要做可恢复，就改成逻辑删除——表里加 `deleted` 或 `status` 字段，删除时只 `update` 标记，所有查询都带 `where deleted = 0`。这样"删除"只是隐藏，管理员还能在回收站里恢复。

</details>

### 2.6 UserManage.vue 页面结构

**① 讲义怎么说** —— "二、前端实现 1. 新建 `views/UserManage.vue`【管理员信息页面】"；功能说明里三次提到交互："**弹窗提交**"、"选中表格中某管理员，**弹出弹窗**"、"删除操作前**弹出确认弹窗**"。

**② 一句话讲透** —— 这个页面拆开看就是"一张表 + 两个弹窗 + 一组方法"：表格负责把数据显示出来，弹窗负责收集输入，方法负责把按钮和接口接上。写这类页面的顺序建议是：先在 `data()` 里想清楚有哪几份状态（列表数据、新增表单、改密表单、两个显示开关），再在 `created()` 里把列表拉一次，最后给每个按钮配一个方法。弹窗用布尔值控制显隐，表单对象单独存，打开时重置——否则第二次打开会看到上次的残留。

**③ 示例代码** ——

```vue
<el-card header="管理员信息管理">
  <el-button type="primary" @click="openAddDialog">新增管理员</el-button>

  <el-table :data="tableData" style="width: 100%">
    <el-table-column prop="id" label="ID" width="80" />
    <el-table-column prop="username" label="登录账号" />
    <el-table-column prop="name" label="管理员姓名" />
    <el-table-column label="操作" width="200">
      <template #default="scope">
        <el-button size="small" type="warning" @click="openPwdDialog(scope.row)">修改密码</el-button>
        <el-button size="small" type="danger" @click="handleDelete(scope.row)">删除</el-button>
      </template>
    </el-table-column>
  </el-table>
</el-card>
```

**④ 逐行拆解** ——
- `<el-card header="管理员信息管理">` 只是给页面套个带标题的卡片，不影响逻辑；真正的内容都在卡片里面。
- `:data="tableData"` 的冒号表示绑定的是表达式而不是字符串；`tableData` 一变，表格自动重绘，这就是 Vue 的响应式。
- `prop="username"` 必须和 `User` 实体序列化出来的字段名逐字一致，写错不会报错，只会显示空白列。
- `#default="scope"` 是作用域插槽，`scope.row` 就是当前这一行的对象；`@click="openPwdDialog(scope.row)"` 把整行传进去，方法里再取 `row.id`。
- `data()` 里三份状态各管一件事：`tableData` 只读接口、`addForm` 只给新增弹窗、`pwdForm` 只给改密弹窗；混着用就会出现"取消后数据还在"。
- `openAddDialog()` 每次都重新赋值 `{username:'', password:'', name:''}`，等于手动清空表单；`openPwdDialog(row)` 则把 `row.id` 写进 `pwdForm`，因为提交时已经拿不到 `row` 了。

### 2.7 路由与菜单

**① 讲义怎么说** —— "2. 修改路由 `router/index.js`，把管理员信息加入后台子路由"，并给出在 `path: '/manage'` 的 `children` 数组里加 `{ path: 'userManage', name:'userManage', meta:{title:"管理员信息"}, component: ()=>import('@/views/UserManage.vue') }`；"3. 在 `Manage.vue` 左侧菜单栏，增加菜单项，跳转到 `/manage/userManage`"，代码是 `<el-menu-item index="/manage/userManage">管理员信息</el-menu-item>`。

**② 一句话讲透** —— 路由是"地址 → 组件"的对照表，菜单是照着这张表做的一份目录。子路由写在 `/manage` 的 `children` 里，`path` 不带斜杠，最终地址 = 父路径 + 子路径，也就是 `/manage/userManage`；菜单项的 `index` 要写这个完整地址，`el-menu` 加上 `router` 属性后，点菜单等价于 `router.push(index)`。两处字符串必须一模一样：路由写错，页面 404；菜单写错，点了地址变了内容却不换。

**③ 示例代码** ——

```js
{
  path: '/manage',
  name: 'manage',
  component: () => import('@/views/Manage.vue'),
  children: [
    {
      path: 'userManage',
      name: 'userManage',
      meta: { title: '管理员信息' },
      component: () => import('@/views/UserManage.vue')
    }
    // ... 其他子路由：dashboard、herb、article 等
  ]
}
```

**④ 逐行拆解** ——
- `children` 里的 `path: 'userManage'` 不能写成 `/userManage`：带斜杠会被当成从根开始的绝对路径，父组件 `Manage.vue` 的 `<router-view />` 就不会渲染它。
- `name: 'userManage'` 在全局必须唯一，`router.push({ name: 'userManage' })` 靠它跳转；重名时路由表里会出现两个同名记录，按名字跳转会命中哪一个很难排查。
- `meta: { title: '管理员信息' }` 被 `router/index.js` 第 39~41 行的全局守卫读取，写进浏览器标签页标题；不写就显示默认的"系统登录"。
- `component: () => import('@/views/UserManage.vue')` 是懒加载：只有访问这个地址才下载这个页面的代码，首屏更快。`@` 是 Vite 配的 `src` 别名。
- 父路由 `/manage` 的组件里必须有 `<router-view />`（`Manage.vue` 第 87 行），否则子路由匹配成功也没地方显示。
- 菜单 `<el-menu router :default-active="route.path">`：`router` 让 `index` 当路径用，`:default-active` 绑定当前路径，刷新后还能高亮正确的菜单项。

**⑤ 在你仓库里** ——
- `D:\my-project\xm-pro\vue\src\router\index.js` 第 10~35 行是 `/manage` 与它的 `children`，第 26 行就是 `userManage` 子路由，第 39~48 行是全局守卫。
- `D:\my-project\xm-pro\vue\src\views\Manage.vue` 第 60~68 行"用户管理"子菜单，第 87 行 `<router-view />`。
- `D:\my-project\xm-pro\vue\src\views\Manage.vue` 第 18~23 行 `el-menu` 的 `router` 与 `:default-active` 两个属性。

**⑥ 常见坑** —— ① 访问 `/manage/userManage` 白屏，控制台 `No match found for location` → 子路由 `path` 写成 `/userManage`，或压根没加进 `children` → 改成不带斜杠的相对路径。② 地址对了但右侧还是首页 → `Manage.vue` 的内容区没有 `<router-view />` → 在 `.content` 里补上。③ 点菜单没反应 → `el-menu` 少了 `router` 属性，或 `index` 写的是 `userManage` 而不是 `/manage/userManage` → 补 `router`，`index` 写完整路径。

**⑦ 自测** —— 子路由 `path` 写 `userManage` 和 `/userManage`，最终地址分别是什么？

<details><summary>展开解析</summary>

不带斜杠是相对父路径，得到 `/manage/userManage`，会渲染在 `Manage.vue` 的 `<router-view />` 里；带斜杠是绝对路径，直接就是 `/userManage`，不再受 `/manage` 约束，父组件的出口不会渲染它，通常表现为白屏或 404。

</details>

### 2.8 Result 业务码

**① 讲义怎么说** —— 功能说明第 2 条："返回格式全部复用项目自带 Result 统一返回类，**成功 code=200，业务错误 code=400**，前端用 **ElMessage** 弹窗提示。"

**② 一句话讲透** —— `Result` 是一个统一信封：不管里面装的是列表、一个对象，还是什么都没有，信封上都印着三个格子 `code`、`msg`、`data`。要分清两套"状态"：HTTP 状态码说的是"这封信有没有送到"，业务 `code` 说的是"信里说的事办成没有"。服务器正常收到请求、正常查库、正常告诉你"账号已存在"，这一趟 HTTP 就是 200，只是业务上拒绝，所以 `code` 给 400。前端不看 HTTP，只看 `code` 决定弹绿字还是红字——这就是为什么 F12 里状态列全是 200，页面却一直报错。

**③ 示例代码** ——

```java
public static Result success() {
    Result result = new Result();
    result.setCode("200");
    result.setMsg("请求成功");
    return result;
}

public static Result error(String code, String msg) {
    Result result = new Result();
    result.setCode(code);
    result.setMsg(msg);
    return result;
}
```

**④ 逐行拆解** ——
- `private String code`：注意是字符串，不是 `int`。所以前端写 `res.code === 200` 永远不成立；仓库里写成 `res.code === '200' || res.code === 200`，是为了兼容两种后端写法。
- `private String msg`：讲义正文写的是 `message`，但代码和所有实测响应里都是 `msg`，前端取 `res.msg`；照讲义文字写 `message`，弹窗会显示 `undefined`。
- `private Object data`：用 `Object` 才能同时装 `List<User>`、`User`、`String`，也能什么都不装。
- `success()` 不传参：只置 `code` 和 `msg`，`data` 留空；`success(Object data)` 先调 `success()` 再塞数据——两个重载省得调用方每次自己 `new`。
- `error(String code, String msg)`：业务错误统一传 `"400"`，`msg` 写人话，比如"旧密码错误，修改失败"，这句话会原样弹到用户眼前。
- Jackson 按 getter 输出字段，字段名就是 `code/msg/data`；三个 getter 少一个，响应里就少一个字段。

**⑤ 在你仓库里** ——
- `D:\my-project\xm-pro\springboot\src\main\java\com\example\common\Result.java` 第 6~8 行三个字段，第 10~35 行四个工厂方法。
- `D:\my-project\xm-pro\vue\src\views\UserManage.vue` 第 96、119、144、163 行，四处 `res.code === '200' || res.code === 200` 的判断。
- `D:\my-project\xm-pro\vue\src\views\Login.vue` 第 36~44 行，登录也靠同一套 `code` 与 `msg`。
- `D:\my-project\xm-pro\vue\src\utils\request.js` 第 19~27 行，拦截器把响应体直接交给页面，所以页面拿到的就是 `Result` 对象。

**⑥ 常见坑** —— ① 前端 `if (res.code === 200)` 永远进 else → 后端 `code` 是字符串 `"200"` → 改成 `=== '200'`，或像仓库一样两种都判。② 弹窗显示 `undefined` → 后端字段叫 `msg`，前端读了 `res.message` → 统一用 `res.msg`，见 `Result.java` 第 45 行。③ 业务错误却弹"系统错误" → Controller 里直接 `throw new RuntimeException(...)`，被全局异常处理器兜成 500 → 可预期的业务失败用 `Result.error("400", ...)` 返回，别抛异常。

**⑦ 自测** —— 接口返回 HTTP 200，页面却弹出红色"账号已存在"，这是 bug 吗？

<details><summary>展开解析</summary>

不是。HTTP 200 只说明请求被服务器正常处理并返回了响应；`code=400` 是业务层的拒绝。前端按 `res.code` 判断并 `ElMessage.error(res.msg)`，这正是统一返回设计的目的——把"传输成功"和"业务成功"分开。

</details>
