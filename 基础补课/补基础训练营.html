Diagnosis

先承认三个错觉

你不是不努力，你是一直在做"识别"，没做过"生成"。大脑识别一段代码很容易，凭空生成一段代码才叫会。

1读代码 = 学会了？

看别人的代码时，大脑做的是识别——顺着作者的思路往下走，每一步都"看得懂"。 但写代码需要的是生成——面对空白文件，决定下一行写什么。 这是两种完全不同的能力，识别好不代表生成好。

解药：合上讲义，从空文件开始写。卡住 5 分钟再看，看完立刻关掉重写。

2跟着敲 = 学会了？

跟着老师敲的时候，你在做抄写。最关键的那个决策——"下一步该写什么、为什么是它"—— 已经由老师替你做完了。你练的是打字速度，不是编程。

解药：先只看需求，把功能自己实现一遍，再去对讲义。差异之处就是你的知识缺口。

3报错就搜答案 = 学会了？

报错信息是编程里唯一免费、即时、还百分百针对你当前问题的老师。 搜到答案粘贴过去，错误消失了，但你把这个老师永久关掉了——下次同样的错你依然不会。

解药：报错先自己读 30 秒，说出"哪一行、什么类型、期望什么、实际什么"，再去搜。
所以你问"要不要看网课"——不用。 你的仓库里躺着 8 份老师讲义、7 份《实验过程》、6 份《讲义勘误》，覆盖了网课能给你的一切知识点。 再看一遍网课，只是换个人替你敲代码，第 2 个错觉会原封不动地重演一遍。 你现在缺的不是输入，是输出。

验收（全勾才算过）

三个必踩的坑，提前告诉你现象、不告诉你答案：
① Result 里的 code 是字符串 "200"，你写 code === 200 永远不成立。自己打印 typeof 验证一次。
② fetch 在接口返回 500 的时候不会 reject——它只对网络层面的失败 reject。所以"接口报错了但我的 catch 没进去"，这是设计如此，不是 bug。

④ 最阴的一个坑：/map 接口没有被 Result 包装——它返回的是裸的 {"name":...,"age":...}，没有 code 字段。 于是"5 个按钮共用一个请求函数"会出现矛盾：四个接口要判断 code，这一个没有 code。 这个矛盾不是 bug，它恰恰说明了"统一返回"的价值——你要么在封装函数里兼容这种特例，要么就理解了为什么真实项目里所有接口都必须走统一结构。 想清楚这一条，你对"统一返回"的理解就超过大多数同学了。

02两层状态码：为什么异常了还是"成功"

这是前后端联调里最容易翻车、也最容易被学生忽略的一点：你的项目里同时存在两套"状态码"，它们各说各的。

层次谁产生的取值谁在看
第一层
HTTP 状态码		Tomcat / 协议层200 / 404 / 500浏览器、运维、监控系统
第二层
响应体里的 code		你的 Result 类"200" / "400" / "500"你的前端代码
关键事实：你的后端把异常"吃掉"了 WebController.number() 里那句 int a = 1 / 0; 确实抛了 ArithmeticException， 但 GlobalExceptionHandler 用 @ExceptionHandler(Exception.class) 把它接住， 然后正常返回了一个 Result.error()。 对 HTTP 协议来说，这是一次完全正常的响应——所以 HTTP 状态码是 200，只有响应体里的 code 是 "500"。

于是前端会看到这些组合，判断逻辑必须写对：

现象HTTP 状态码响应体 code前端该做什么
正常200"200"用 data 渲染
业务异常（用户名已存在）200"400"弹 msg 提示用户

所以千万不要这样写 if (response.ok) { 当作成功 } —— 在你这套后端里，除以 0 的接口 response.ok 也是 true。 真正该判断的是响应体里的 code，而且它是字符串，比较时必须写 === '200'。

三个必须看出来的点：

② /number 的响应体里没有 data 字段（不是 data: null，是压根没有这个 key）——这就是 @JsonInclude(NON_NULL) 的效果，对应 C 组第 C2 题。
③ /map 根本没有被 Result 包装，它是裸的 Map，连 code 字段都没有——这会在 L7 炸掉你的"统一请求函数"，见那一关的坑④。
为什么这样设计？这样对吗？
这是国内教学项目里非常常见的一种约定：HTTP 状态码只表示"这次通信本身成不成功"，业务成不成功放在响应体里说。 好处是前端只需要解析一种数据结构（永远是 {code, msg, data}），写一个统一的请求封装就能处理所有接口。

但它也有代价：监控系统看 HTTP 200 会以为一切正常，实际上业务在报错。工业界更规范的做法是业务异常也返回对应的 HTTP 状态码（400/500）。 你现在先学会用这套约定，再知道它的取舍——这就是"会写"和"懂"的区别。

03Promise：程序为什么不等你

L4 那一关的理论基础。搞不懂这个，L7 的代码你只能靠抄。

JavaScript 只有一个线程。如果发请求的时候它傻等着，页面就会卡死——按钮点不动、动画停住。所以它选择"不等待"：发请求这个动作立刻返回一个 Promise（承诺），等数据真的回来了，再回头执行你交代好的那段代码。

Promise 的三种状态

  • pending 进行中——请求已发出，还没回来
  • fulfilled 成功——用 .then() 或 await 取结果
  • rejected 失败——用 .catch() 或 try/catch 接错误

状态一旦改变就不可逆，也不会再变第二次。

fetch 的反直觉之处

fetch 只在网络层面失败时才 reject（断网、后端没起、域名解析不了）。 如果服务器正常响应了，哪怕响应是 404 或 500，fetch 也认为这次调用成功了。

这就是为什么 L7 里必须自己判断 code——没有人替你判断。

一句话记法 await 拿到的是"货"，Promise 是"提货单"。 const r = fakeServer() 拿到的是提货单，所以 console.log(r) 看不到数据——这就是 L4 第 1 题的现象。

04跨域：到底是谁在拦你

L6 那一关的理论基础。想清楚这一节，你就不会再瞎搜"CORS 怎么解决"了。

同源的判定看三个东西，必须全部相同：

地址组合同源？原因
localhost:5173 ↔ localhost:5173同源三项全同
localhost:5173 ↔ localhost:8080跨域端口不同（你的项目就是这种情况）
localhost:8080 ↔ 127.0.0.1:8080跨域域名不同（虽然是同一台机器，但浏览器不认）
http://a.com ↔ https://a.com跨域协议不同
最关键的一个认知：拦人的是浏览器，不是服务器 跨域请求已经发出去了，后端也处理完了、也把响应发回来了。 浏览器拿到响应后，发现"这个响应的来源和当前页面不同源，而且响应头里没有 Access-Control-Allow-Origin 允许我"， 于是把响应丢掉了，不交给你的 JS，并在 Console 里报一条 CORS 错误。

证据你可以自己找：L6 里故意制造 CORS 报错的时候，去后端控制台看——后端照样打印了访问日志，说明请求确实到了。

两种解法，各自的适用场景完全不同：

方案怎么做能用在哪评课/上线时的说法
后端开 CORS 后端加一个配置类，给响应头加 Access-Control-Allow-Origin 开发、生产都行 正规做法，但要在后端写代码
前端代理 proxy
推荐先学这个		 Vite 开发服务器把 /api 转发到后端 只在开发期有效 开发期最省事；打包上线后失效，得换方案
代理为什么能绕过跨域？ 因为浏览器眼里根本没有发生跨域：你的页面向 localhost:5173/api/hello 发请求，同源，放行。 然后 Vite 的开发服务器（跑在 node 里，是个后端程序，不受浏览器的同源策略管）替你把这个请求转发给 localhost:8080， 拿到结果再原样回给浏览器。

所以：跨域限制只存在于浏览器里，两个后端之间互相调用从来不跨域。记住这句话，你就懂了。

A 组 JS 语法与数据

12 题 · 对应关卡 L1–L3
A1const obj = {a: 1} 之后，obj.a = 2 能成功吗？obj = {a: 3} 呢？
obj.a = 2 可以；obj = {a: 3} 不行，会抛 TypeError: Assignment to constant variable。
为什么：const 锁的是"这个变量名不能再指向别的值"，不是"这个对象不能改"。对象内部随便改，但你不能把 obj 这个名字重新指向一个新对象。想两种都不许改，用 Object.freeze()。
A2'1' == 1 和 '1' === 1 的结果分别是什么？前端代码里该用哪个？
true 和 false。
为什么：== 会先做类型转换再比较（把字符串转成数字），=== 要求类型和值都相同。一律用 ===，因为隐式转换制造过无数事故。
这正是 L7 里 code === '200' 必须带引号的原因：后端给的是字符串。
A3typeof null 等于什么？这说明判断类型时要注意什么？
等于 "object"。
为什么：这是 JavaScript 最早期实现里的一个历史遗留 bug，因为要兼容老网站所以一直没改。
所以判断数组要用 Array.isArray(x)，判断 null 要直接写 x === null，都不能靠 typeof。
A4map 和 forEach 最本质的区别是什么？
map 有返回值（一个长度相同的新数组），forEach 返回 undefined。
为什么：想"把数组变形再拿去用"就用 map；只想"遍历一遍做点副作用"（比如打印）才用 forEach。写成 const x = arr.forEach(...) 是最常见的低级错误之一——x 会是 undefined。
A5用 find 找"价格最高的商品"，为什么是错的？正确思路是什么？
find 返回的是第一个满足条件的元素，不是"条件最好的那个"。你得先知道最高价是多少，才能拿它去 find。
正确思路：先 reduce（或先 sort 再取第 0 个，但注意 sort 会改原数组）求出最大值，或者直接用 reduce 一趟同时比较并保留当前最大项。
对应 L2 第 3 题——这道题是故意设计来让你撞 find 的语义的。
A6{...person, age: 20} 会修改原来的 person 吗？
不会。它产生一个全新对象，只有新对象上的 age 是 20。
为什么重要：在 Vue 里，"改原对象"和"换一个新对象"对响应式的影响不一样（尤其是数组和嵌套对象）。养成"要改就造一个新的"的习惯，能避开一大批"数据变了但页面不刷新"的疑难杂症。
A7a?.b?.c 里的 ?. 解决什么问题？
解决"访问一个可能不存在的对象属性导致报错"的问题：中间任何一环是 null 或 undefined，整个表达式直接返回 undefined，不报错。
为什么需要：接口数据还没回来时，user.info.name 里 user.info 是 undefined，直接写就是 Uncaught TypeError: Cannot read properties of undefined——这正是 D 组第 7 题的现象。
A8?? 和 || 有什么区别？
?? 只在左边是 null 或 undefined 时才取默认值；|| 在左边是任何"假值"（0、''、false、NaN）时都会取默认值。
典型 bug：商品数量允许是 0，写 count || 10 会把 0 变成 10；写 count ?? 10 才会正确保留 0。
A9数组去重，最短的写法是什么？
[...new Set(arr)]
拆开看：Set 是"不重复集合"，new Set(arr) 自动去重，但它不是数组；前面加 [...] 展开回数组。这一行同时用到了 Set 和展开语法。
A10解构时想给变量改名，怎么写？
const { name: n, age: a } = person
注意读法：冒号左边是原属性名，右边是你要的新变量名——很多人会记反。这和 import 的花括号写法是一个道理。
A11箭头函数和普通 function 在 this 上有什么不同？
箭头函数没有自己的 this，它用外层作用域的 this；普通函数的 this 取决于怎么被调用。
为什么这么设计：回调函数里经常需要访问外层的 this，箭头函数天然满足，省掉了老代码里 const that = this 那种写法。
A12模板字符串里怎么嵌入 JS 表达式？普通字符串拼变量为什么容易被骂？
用反引号和 ${表达式}，比如 `共 ${list.length} 条`。
为什么：字符串拼接 '共 ' + list.length + ' 条' 容易漏空格、引号套错，一个变量多了以后几乎无法阅读。模板字符串还支持直接换行。

B 组 HTTP 与前后端

12 题 · 对应关卡 L5–L7
B1一个 HTTP 请求由哪几部分组成？
请求行（方法 + 路径 + 协议版本）、请求头（一堆 key: value）、请求体（GET 通常没有，POST 有）。
在哪看：F12 → Network → 点开任意请求，Request Headers 和 Payload 两块就是它。
B2GET 和 POST 至少说三个区别。
① 参数位置不同：GET 在 URL 里（查询字符串），POST 在请求体里；
② 语义不同：GET 是"取数据"（幂等、可缓存、能被收藏），POST 是"提交数据"（会改变服务器状态）；
③ 长度限制：URL 有长度上限，请求体基本没有；
④ 安全性：GET 的参数会留在浏览器历史、服务器日志里，所以密码永远不能放 URL。
B3说出这几个状态码的意思：200 / 301 / 400 / 401 / 403 / 404 / 500。
200 成功； 301 永久重定向； 400 请求参数有问题（客户端错）； 401 未登录/未认证； 403 登录了但没权限； 404 找不到资源（路径写错）； 500 服务器内部错误。
记法：4 开头是"你（客户端）的错"，5 开头是"我（服务器）的错"。401 和 403 的区别是考试常考：401 = 你是谁我不知道，403 = 我知道你是谁但你不许进。
B4Content-Type: application/json; charset=UTF-8 里两部分各是给谁看的？
application/json 告诉对方"我发的是 JSON 格式"；charset=UTF-8 告诉对方"请用 UTF-8 来解码这些字节"。
为什么你的项目要专门写代码管这个：Spring 默认用 ISO-8859-1 处理字符串响应，中文会乱码，所以仓库里才有 WebConfig.java 这个类专门把所有响应的字符集统一成 UTF-8。
B5JSON 和 JS 对象字面量有什么区别？（至少三点）
① JSON 的 key 必须用双引号包起来，JS 对象可以不写引号；
② JSON 不能有函数、不能有 undefined、不能有注释；
③ JSON 里字符串只能用双引号，不能用单引号；
④ JSON 本质是字符串，JS 对象是内存里的数据结构——这就是为什么需要 JSON.parse() 来转换。
B6同源策略看哪三个要素？
协议、域名、端口——三者必须全部相同。
注意：路径、查询参数不参与判断。localhost:5173/a 和 localhost:5173/b 是同源的。
B7http://localhost:5173 和 http://localhost:8080 同源吗？为什么？
不同源——端口不同（5173 vs 8080）。
为什么端口也算：端口代表不同的服务进程。同一台机器上跑着你的前端和后端两个完全独立的程序，浏览器必须把它们当成两个不同的"源"，否则一个网站就能随便读另一个网站的接口了。
B8跨域请求被拦的时候，请求到底发出去没有？是谁拦的？证据是什么？
发出去了，也被服务器处理了、响应也回来了。拦的是浏览器——它在把响应交给你的 JS 之前丢掉了它。
证据：制造 CORS 报错时去看后端控制台／日志，能看到这次请求的访问记录。如果请求根本没发出去，后端不可能有日志。这是 L6 第 3 题要你亲手确认的。
B9Vite 的开发代理为什么能解决跨域？它在生产环境还有效吗？
原理：浏览器请求的是 localhost:5173/api/...（同源，放行），Vite 的 node 服务器再替你转发到 8080。node 是服务端程序，不受浏览器同源策略约束，所以转发不受限制。
生产环境无效：vite.config.js 只在 npm run dev 时起作用。npm run build 出来的静态文件不包含这个代理，得靠 Nginx 转发或后端开 CORS。这是很多人"本地好好的、一上线就 404"的原因。
B10JSON.parse 和 JSON.stringify 分别干什么？
JSON.parse(字符串) → 变成 JS 对象；JSON.stringify(对象) → 变成 JSON 字符串。
在请求里的位置：发请求时要把对象 stringify 成字符串放进 body；收到响应时 response.json() 内部就是帮你做 JSON.parse（所以它返回的也是 Promise）。
B11URL 里的查询参数长什么样？在 Vue 里怎么取？
形如 ?id=2&name=abc，用 & 分隔多个。
怎么取：原生用 new URLSearchParams(location.search).get('id')；Vue 里用 useRoute().query.id——你的 04/vue-router 讲的就是这个（query 传参）。
B12为什么后端要统一返回 {code, msg, data}，而不是五花八门地返回？
因为前端只需要写一套处理逻辑：解包看 code，200 就取 data 渲染，否则弹 msg。
反例：如果有的接口返回字符串、有的返回数组、有的返回对象，前端每调一个接口都得写一遍判断，代码里会到处是 if。这正是你仓库里 Result.java 存在的意义——它的注释就写着这一点。

C4WebConfig.java 解决的是什么问题？如果把这个类删掉，会出现什么现象？
把所有响应的字符集统一成 UTF-8。删掉后，返回中文字符串的接口会乱码（变问号或奇怪符号）。
读代码提示：这个类的注释写得非常详细，直接读最上面那段 javadoc 就懂了。它同时处理了两个转换器：StringHttpMessageConverter（返回字符串时用）和 MappingJackson2HttpMessageConverter（返回对象时用）。
C5GlobalExceptionHandler 里有两个 @ExceptionHandler，一个接 Exception、一个接 CustomException。为什么 CustomException 不会被第一个"吃掉"？
因为 Spring 会优先匹配最具体的异常类型。
为什么重要：如果顺序反过来（或者只留了 Exception 那个），业务异常就会被当成系统错误，返回 500 而不是 400，前端也就没法区分"用户操作有问题"和"服务器挂了"。这正是 CustomException 这个类存在的全部意义。
C6CustomException 为什么要 extends RuntimeException，而不是 extends Exception？
因为 RuntimeException 是非受检异常，抛它不需要在方法签名上写 throws，也不用每层都 try/catch。
对比：如果继承 Exception（受检异常），WebController.businessTest() 就必须声明 throws CustomException 或者就地 try/catch，否则编译不过。业务异常本来就是"设计好的流程分支"，不该污染每一层的方法签名。
C707/xm-pro/vue/src/main.js 第 15–17 行那个 for 循环在干什么？

C10如果有一天把 application.yml 里的端口从 8080 改成 9090，前端哪里要跟着改？配了代理以后呢？
没配代理时：前端所有写死 http://localhost:8080 的地方都得改——如果散落在十个文件里，就是改十处。
配了代理之后：只改 vite.config.js 里 proxy 的 target 一处，页面代码一个字都不用动（它们请求的是 /api/...，压根不知道后端在哪个端口）。
这才是代理最值钱的地方——不只是绕过跨域，更是把"后端地址"这件事收拢到了一个配置点上。这也解释了为什么真实项目里前端永远请求相对路径。

D 组 现象 → 原因（排错）

8 题 · 全部是真实见过的报错。这一组最值钱：会排错 = 能独立干活
D1页面上的中文显示成 ?????? 或者 å®‰å¾½。最可能是什么问题？
编码问题——字节用 UTF-8 编码了，解码时却按别的字符集（ISO-8859-1 / GBK）读。
排查顺序：① 响应头有没有 charset=UTF-8；② HTML 里有没有 <meta charset="UTF-8">；③ 源文件本身是不是 UTF-8 保存的；④ 数据库连接串有没有 characterEncoding=utf-8。
你的项目里：WebConfig.java 就是为第 ① 步存在的；application.yml 的 JDBC URL 里那串 useUnicode=true&characterEncoding=utf-8 是第 ④ 步。
D2Console 报 Access to fetch at 'http://localhost:8080/hello' from origin 'http://localhost:5173' has been blocked by CORS policy。怎么解？
这是跨域：端口不同（5173 → 8080）。
开发期首选：配 Vite 代理（L6）。次选：后端加 CORS 配置类。别去搜"关闭浏览器跨域检查"那种歪招——它只在你自己机器上有效，一换机器/一上交作业就露馅。
D3Console 报 Failed to fetch 或 net::ERR_CONNECTION_REFUSED。跟 D2 有什么区别？
D2 是"请求到了、响应被浏览器拦了"；D3 是根本没连上——后端没启动、端口写错、地址写错。
怎么快速区分：看 Network 面板。D3 的请求通常状态显示 (failed) 或 (canceled)，压根没有状态码；D2 能看到状态码，只是 Console 里有 CORS 红字。
这也解释了 L7 的坑③：只有 D3 这种情况 fetch 才会 reject。
D4IDEA 启动报 Port 8080 was already in use。为什么会出现？怎么办？
上一次的后端进程没被真正杀掉，还占着 8080 端口。
怎么办：netstat -ano | findstr :8080 找到最后一列的 PID，再 taskkill /PID 那个号 /F 收掉。
为什么会没杀掉：IDEA 里点了停止但进程卡住、或者开过两个运行配置、或者命令行 java -jar 起的忘了关。仓库 07/实验过程_实训7.md 里就记录过这个坑。
D5点左侧菜单没反应，地址栏不变，Console 里一串 Missing required prop: "index"。什么原因？
<el-menu-item> 少了必填的 index 属性，Element Plus 不知道点它该跳到哪个路径。
真实出处：这是实训6 讲义里被记下来的一个真实错误（见 README.md 的"严重"级勘误）。启示：组件库的"必填 prop"告警不是建议，是"这个组件不会工作"的意思——所以 Console 里的黄字也别无视。
D6改了 vite.config.js（比如加了代理），刷新页面完全没变化。为什么？
配置文件只在 dev server 启动时读一次，必须重启 npm run dev。
推广一下：Vite 能热更新（HMR）的是 src 里的代码；vite.config.js、package.json、环境变量文件都不在热更新范围内。以后凡是"改了配置没生效"，第一个反应就是重启。
D7Console 报 Uncaught (in promise) TypeError: Cannot read properties of undefined (reading 'name')。典型成因是什么？
在读一个 undefined 的属性。最常见于：接口数据还没回来，模板就已经渲染了，此时对象是空/未定义。
为什么"还没回来"就会执行：因为 JS 不等异步结果（L4 / 原理 3）。
两种修法：① 模板里用 ?. 或 v-if 兜住；② 数据初始化时给一个合理的默认值（空对象/空数组），而不是 null。
D8表格有 9 行数据，点"第 2 页"页码变了，但 9 行数据一模一样。为什么？
只改了页码变量，没有真的对数据做切片——页面上永远渲染的是完整数组。
真实出处：实训4 和实训6 讲义里都有这个问题（README 记为"一般"级）。
正确思路：渲染的应该是 allData.slice((pageNum-1)*pageSize, pageNum*pageSize) 的结果，而不是 allData。这也是前端分页和后端分页的分界点：数据量大时应该把页码传给后端，让 SQL 做 LIMIT。

怎么用这套东西

一次 30 分钟，别贪多。方法比时长重要——用错方法，坐着学三小时的效果不如这样半小时。

15'盲写

只看任务卡，不看任何示例，自己敲。允许查语法，不允许抄整段代码。

10'对照

跑通之后再去翻讲义 / 仓库里的现成实现，找出你的写法和它的差别。差别就是知识点。

5'口述

合上屏幕，用自己的话说一遍"刚才这段代码为什么这么写"。说不顺的地方，就是没懂的地方。

每关结束时问自己三句话

  • 我能不能不看任何示例把它写出来？
  • 我能不能说出为什么要这么写，而不是那么写？
  • 如果我把这里改一下，能不能预判会出什么效果？

三句全是"能"，这关才算过——比勾选验收项更严格，也更有用。

明确不要做的事

  • 先看答案再动手（等于自己骗自己）
  • 整段复制粘贴（复制的是结果，不是能力）
  • 报错 3 秒就搜/就问（先把报错读完）
  • 一卡住就找 AI 要代码（要提示可以，要代码不行）
  • 同时开三个教程来回看（这是焦虑，不是学习）
怎么让我（AI）继续帮你——这是效率最高的一种用法 做完一关，把这三样发我：①你的代码、②报错原文（原样粘贴，别转述）、③你已经试过什么。 我会告诉你错在哪、为什么错，但不会直接把正确答案贴给你——那正是这份训练营存在的理由。
反过来，如果你只说"帮我写一下"，那我就是在帮你把第 2 个错觉再演一遍。
