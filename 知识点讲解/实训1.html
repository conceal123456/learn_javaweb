2. 知识点精讲

2.1

Node.js 是什么、为什么前端要装它

①讲义要点

"Node.js部分"开头直接让大家双击 node-v20.15.1-x64.msi 一路 Next，没解释 Node 是干什么的，属于只给动作不给原理。

②核心讲解

Node.js 不是一门新语言，它就是 JavaScript，只是配了个"离开浏览器也能跑的发动机"（V8 引擎 + 文件读写 + 网络能力）。前端非装不可的原因：浏览器只认 HTML/CSS/普通 JS，而写的 .vue、import、ES6+ 它一个都不认识，必须先在本地编译；干这活儿的 Vite 是 JS 程序，得靠 Node 跑。类比：Node 是灶台，Vite 是厨师，.vue 是生食材——没灶台，厨师再厉害也做不出菜。

③示例演示
js9 行
1 2 3 4 5 6 7 8 9
// hello-node.js —— 存到 D:\course\Javaweb\基础补课\js练习\ 下，用 node hello-node.js 跑
const os = require('node:os')   // Node 内置模块，浏览器里没有这个东西
const fs = require('node:fs')

console.log('我在 Node 里跑，版本：' + process.version)
console.log('这台机器叫：' + os.hostname())

fs.writeFileSync('hello-node-output.txt', '这行字是 Node 写进硬盘的\n', 'utf8')
console.log('已经把结果写进 hello-node-output.txt 了')
bash1 行
1
node hello-node.js
④代码解读
  • require('node:os')：require 是 Node 的取模块语法；node: 前缀表示内置模块，不用 npm install。不写这行就用不了 os，直接 ReferenceError。
  • process.version：process 是 Node 自动给的全局对象。浏览器里根本没有 process，写了就是 process is not defined——这也是判断"这段代码在哪跑"最快的办法。
  • fs.writeFileSync(...)：Sync 结尾＝同步，这一行不返回程序就在这等着。浏览器里的 JS 永远没权限直接写硬盘，Node 有。这就是"前端要装 Node"的根。
  • 最后的 console.log 一定在文件写完之后才执行。换成 fs.writeFile（异步）就可能先打印——异步到训练营 L4 专门练。
⑤工程对照

实训1_软件安装及创建Vue项目/工程/hello-vue/package.json:20-22 的 "engines": { "node": "^20.19.0 || >=22.12.0" } 就是工程对 Node 的约束。本机实测 node -v → v24.17.0，node -p "process.execPath" → D:\software\nodejs\node.exe。

⑥易错提醒

现象：node -v 报"不是内部或外部命令"。原因：装的时候没勾 Add to PATH，或者装了没重开命令行窗口（旧窗口拿的是旧 PATH）。怎么改：重装勾上 Add to PATH，或手动把 D:\software\nodejs 加进 Path 后关掉所有命令行窗口重开。另一易错点：装了讲义的 20.15.1 后 npm install 报 EBADENGINE，因为 20.15 < 20.19 下限——装 20.19+ 或 22.x/24.x。

⑦课堂思考

Node.js 和 JavaScript 是什么关系？为什么"前端开发"反而要先装一个"服务端运行时"？

展开解析

Node.js 不是新语言，是 JavaScript 的运行时（执行环境），用和 Chrome 同一个 V8 引擎，额外给了文件读写、网络、进程能力。

前端要装它，是因为 .vue、import、ES6+ 浏览器都不认识，必须先编译；干这活儿的 Vite 是 JS 程序，只能在 Node（或浏览器）里跑。所以 Node 不是给浏览器装插件，而是给构建工具提供落脚点，顺带兼任依赖下载器（npm）和本地服务器。

2.2

npm 是什么、和 Node 什么关系

①讲义要点

第3条原话："nodejs 里面默认的会带一个 npm……它会跟随这个 NodeJS 一起安装的，不需要单独安装，它是在 NodeJS 里面内置的"。这个说法是对的，讲义这里没讲错。

②核心讲解

npm = Node Package Manager，仓库管理员＋搬运工：去 registry 把别人写好的包下下来放进 node_modules，并记住版本。"内置"的意思是装不了单独的 npm，也不需要装。类比：手机自带的应用商店——大家不会"再装一个商店来装应用"，它是系统的一部分。可以升级它，但不能让它脱离 Node 存在。

③示例演示
bash5 行
1 2 3 4 5
npm -v                              # 看 npm 自己的版本
where npm                           # 看它躺在哪（Windows 的 which）
npm config get registry             # 看它从哪个仓库下单
npm view create-vue version engines # 只问价不下载，看包要求的 Node 版本
npm install --dry-run               # 模拟装一遍，只报告不动硬盘
④代码解读
  • npm -v → 本机 11.13.0，验证的是"npm 的启动脚本在不在 PATH 里"。
  • where npm → 会列出 D:\software\nodejs\npm 和 npm.cmd。它们躺在 Node 安装目录里，这就是"npm 是 Node 附属品"最直接的证据。
  • npm view create-vue version engines → 实测 version = '3.21.0'、engines = { node: '^20.19.0 || >=22.12.0' }。view 是只读查询，不下载不安装，用它不必瞎猜自己的 Node 够不够。
  • npm install --dry-run → 报告"会装什么"，一个文件都不动。
⑤工程对照

实训1_软件安装及创建Vue项目/工程/hello-vue/package-lock.json:25 是 "resolved": "https://registry.npmmirror.com/@babel/code-frame/-/code-frame-7.29.7.tgz"，这条 URL 就是镜像源真生效的铁证；:1 是 lockfileVersion: 3；:2598/:2787/:2808 分别锁住 vite / vue / vue-router 的实际版本。

⑥易错提醒

现象：node -v 正常但 npm -v 报错。原因：Node 在 PATH 里，npm 的 npm.cmd 不在（多半有多个 Node 安装，被 nvm 或旧版覆盖）。怎么改：where node 看 node 在哪个目录，npm.cmd 必须和它在同一个目录；不在就卸掉多余的 Node，或调 PATH 顺序。

⑦课堂思考

讲义说"npm 不需要单独安装"，为什么？把 Node 卸了 npm 还能用吗？

展开解析

npm 的代码就在 Node 安装目录里（D:\software\nodejs\node_modules\npm），npm 命令只是个调用它的批处理脚本，它是 Node 发行包的一部分，不是独立软件。

卸掉 Node，脚本和代码一起被删，npm 自然也没了。而且 npm 本身就是 JS 写的、靠 node.exe 执行——没有 node，npm 连启动都启动不了。

2.3

node -v / npm -v 验证的到底是什么

①讲义要点

"打开命令提示符，输入 node -v，看是否输出版本号"，以及"检测一下 npm 有没有安装好"。只说了做什么，没说验证的到底是什么。

②核心讲解

-v 是 --version 的缩写，"报版本号然后退出"。它验证的不是"文件在不在硬盘上"，而是"系统能不能按名字把程序叫起来"——这两件事完全不同。类比：书在图书馆里（文件存在）≠ 可以按书名一次借到（PATH 里有它）。

③示例演示
bash5 行
1 2 3 4 5
node -v          # v24.17.0
npm -v           # 11.13.0，注意 npm 不打印 v 前缀
node --version   # 和 node -v 完全等价
where node       # 真正定位问题的诊断命令
where npm
④代码解读
  • node -v 输出的那个 v（v24.17.0）是版本号的一部分，不是命令的一部分，不要写成 node -v v24.17.0 去搜。
  • npm -v 输出 11.13.0，没有 v 前缀。
  • where node 返回 D:\software\nodejs\node.exe 说明 PATH 配对了；返回"信息: 用提供的模式无法找到文件"说明 PATH 没配好。node -v 只是最终结论，where 才是诊断工具。
  • 两个命令的组合意义：node -v 成功只证明 Node 本体 OK；npm -v 成功才证明"Node + npm 这一对"都就位。
⑤工程对照

本机实测 node -v → v24.17.0、npm -v → 11.13.0、node -p "process.execPath" → D:\software\nodejs\node.exe；与 实训1_软件安装及创建Vue项目/实验过程_实训1.md:10-11 环境表里记的值一致。

⑥易错提醒

现象：系统 cmd 里正常，IDEA 内置终端里 node -v 报错。原因：IDEA 是在修改 PATH 之前启动的，继承的是旧环境变量。怎么改：完全退出 IDEA（File → Exit，不是关窗口）再打开。现象：版本号和以为装的不一样。原因：机器上有多个 Node。怎么改：where node 按 PATH 顺序列出所有候选，排最前面的才真正生效。

⑦课堂思考

node -v 正常但 where node 无输出，可能吗？为什么？

展开解析

几乎不可能同时成立。where 和 node 都靠 PATH 查目录，只是 where 是独立程序（C:\Windows\System32\where.exe）。如果 where 自己不在 PATH 里，那它压根跑不起来（报"不是内部或外部命令"），而不是"无输出"。

真正会遇到的是反过来：where node 能列出路径，但 node -v 报错——那说明文件在 PATH 目录里，但文件本身坏了或被安全软件拦了。所以诊断顺序是：先 where 看找没找到 → 再 node -v 看能不能跑。

2.4

PATH 环境变量

①讲义要点

"同时观察环境变量，会有下图所示"。只让请看一眼截图，没说 PATH 是什么、为什么必须有它。

②核心讲解

PATH 是系统的"程序搜索通讯录"。大家敲 node，系统不知道去哪找，就拿这个名字去 PATH 里列的目录一个一个试，找到第一个叫 node.exe 的就执行；全找完还没有，就报那句经典错误。类比：大家打电话找"张伟"，通讯录里没这个人就打不出去——不是张伟不存在，是通讯录里没他。

③示例演示
bash2 行
1 2
echo %PATH%          # cmd：打印整份"通讯录"，分号分隔
where node           # 比上面更好用：直接告诉你最终命中的是哪个文件
powershell1 行
1
$env:Path -split ';'  # PowerShell：按分号切成一行一条，便于逐行检查
④代码解读
  • echo %PATH% 里 %NAME% 是 cmd 读环境变量的语法。会在输出里看到 D:\software\nodejs\——这一条就是 node 命令能被找到的全部原因，删掉它 node -v 立刻失效。
  • where node 省得在一堆路径里肉眼比对。
  • PATH 分"用户变量"和"系统变量"两份：改用户变量只影响当前用户，改系统变量影响所有用户。装 Node 时一般写系统变量。
⑤工程对照

本机 where node 命中 D:\software\nodejs\node.exe，说明 D:\software\nodejs 在 PATH 中。对照 实训1_软件安装及创建Vue项目/实验过程_实训1.md:51："是 PATH 没写上，重装时勾上 Add to PATH，或手动把 Node 安装目录加进环境变量后重开命令行窗口"——最后这半句是最容易漏、也最容易反复折腾半小时的一步。

⑥易错提醒

现象：明明加进 PATH 了，node -v 还报错。原因：加完没重开窗口——已经开着的 cmd / IDEA 终端在启动那一刻就拍了个 PATH 快照，后续改了它不知道。怎么改：关掉所有命令行和 IDEA 重开，在新窗口 echo %PATH% 确认能看到刚加的目录。另一易错点：where node 列出两条、排第一的是个不认识的旧目录——那是以前装过 Node 或 nvm，要去删掉旧的那条或把它下移，而不是把新目录再加一遍（加两遍不改变顺序）。

⑦课堂思考

装 Node 时没勾 Add to PATH，但双击 D:\software\nodejs\node.exe 能打开。这时 cmd 里敲 node -v 会怎样？

展开解析

会报"node 不是内部或外部命令，也不是可运行的程序或批处理文件。"

因为双击是大家亲手告诉系统"运行这个文件"，路径是大家给的；而敲 node 是让系统自己猜文件在哪，它只能查 PATH，查不到就找不到。

一个是"走直接路径"，一个是"走搜索"，完全不是一回事。

2.5

npm 镜像源 registry 的作用

①讲义要点

"因为 NPM 默认是从国外的下载依赖的，速度很慢，所以呢，要配置一个国内的淘宝镜像"，命令写的是 npm config set registry http://registry.npmmirror.com。注意讲义用的是 http，勘误第 2 条已指出应改成 https。

②核心讲解

registry 就是 npm 的"进货地址"。默认的 https://registry.npmjs.org 在美国，国内经常几十 KB/s 甚至超时；npmmirror 是国内把同一份包完整同步了一份的副本服务器，换过去就是"从隔壁仓库拿货"。关键认知：镜像是只读副本，不是另一个世界——内容逐字节相同（靠哈希校验），所以换源是纯速度优化，不改变工程行为。

③示例演示
bash2 行
1 2
npm config set registry https://registry.npmmirror.com
npm config get registry        # 回显和刚设的一模一样才算成功
④代码解读
  • config set 是"写配置"，不下载任何东西，只往一个配置文件里写一行。
  • 地址必须写全 https://。漏掉协议头只写 registry.npmmirror.com，npm 会当相对路径解析，报 Invalid registry 之类的错。
  • 讲义的 http:// 现在会被 301 跳转到 https，多一次往返，改成 https://registry.npmmirror.com。本机实测 npm config get registry 回显 http://registry.npmmirror.com（历史设置，能用，只是多一跳）。
  • 换源后不用重装 Node，但建议删掉 node_modules 和 package-lock.json 再 npm install，让锁文件里的 resolved 地址统一到新源。
⑤工程对照

实训1_软件安装及创建Vue项目/工程/hello-vue/package-lock.json:25 的 resolved 指向 npmmirror，实证生效。实训1_软件安装及创建Vue项目/实验过程_实训1.md:50 也记了"用 https 更稳妥，http 会多一次重定向"。

⑥易错提醒

现象：设完了 npm install 还是慢，锁文件里仍出现 registry.npmjs.org。原因：旧锁文件里已写死 resolved 地址，npm 优先按锁文件下载，大家们的 registry 配置被锁文件"越过"了。怎么改：删掉 node_modules 和 package-lock.json 重新 npm install。另一易错点：公司/学校内网要走代理，npm config set proxy http://地址:端口，排查完记得 npm config delete proxy 清掉，否则回家又连不上。

⑦课堂思考

换淘宝镜像会不会导致大家装到的 Vue 和别人装的不一样（被改过、少文件）？

展开解析

不会。npmmirror 是官方 registry 的完整只读同步镜像，内容逐字节相同。

校验靠 package-lock.json 里每个包的 integrity 字段（sha512 哈希）。npm 下载完算一遍哈希去比对，对不上直接报错拒绝安装。镜像站想偷偷改内容是不可能的——哈希一变，全世界的安装都会失败。

这正是 package-lock.json 必须提交进 Git 的原因之一。

2.6

npm config set registry 改的是哪个文件

①讲义要点

"输入 npm config set registry ... 按回车，直接跳到下一行代表执行正确"。完全没说这行命令写了哪个文件——这是本讲最容易被跳过、排查问题时又最要命的一环。

②核心讲解

⑦课堂思考

在 实训1_软件安装及创建Vue项目/工程/hello-vue 里执行 npm config set registry https://registry.npmmirror.com，这会影响大家新建的另一个工程 D:\other\demo 吗？

展开解析

会。 因为不带 --location=project 时写的是用户级 C:\Users\你的用户名\.npmrc，和当前目录无关，跑到任何目录都生效。

npm create vue@3.21.0 脚手架做了什么

①讲义要点

"打开官网 https://cn.vuejs.org/，找到这条命令，并进行复制"，然后在 xm-pro 目录里"输入命令：npm create vue@3.21.0 按回车"。没说这条命令背后发生了什么。

②核心讲解

脚手架就是"毛坯房 + 标准水电"：不用从零一砖一瓦搭目录、写配置文件，一条命令下来整套能跑的骨架就躺在大家目录里了。它具体干三件事：① 去 registry 查 create-vue 的 3.21.0 版本；② 下载到 npm 临时缓存；③ 用 npx 的方式临时执行它。 它不会把 create-vue 装进全局环境，干完活就走人。

⑦课堂思考

npm create vue@3.21.0 里的 vue@3.21.0，下载的到底是哪个包？

展开解析

下载的是 create-vue@3.21.0，不是 vue@3.21.0。

真正的 vue 包（框架本体）不在这里下载——它是脚手架根据模板生成 package.json，等大家 npm install 时才真正下载的。这就是为什么 3.21.0 和 Vue 的版本号毫无关系。

2.8

版本号 3.21.0 是脚手架的版本，不是 Vue 的版本

①讲义要点

正文写 npm create vue@3.21.0，截图里却出现 npm create vue@latest，前后不统一；两处都没解释这个 3.21.0 到底是什么的版本（勘误第 6 条已指出）。

②核心讲解

一条命令里有两个完全独立的版本号：create-vue@3.21.0 是"发模板的生成器"的版本，只在建工程那一刻用一次，用完就和工程再无关系；vue@3.5.x 是框架本体的版本，由生成器写进 package.json，之后跟着工程一辈子。类比：3.21.0 是装修公司的工牌号，3.5.x 是大家家墙漆的品牌型号——工牌号变了不代表墙漆换牌子。

npm pkg get dependencies.vue                                        # package.json 里声明的区间
④代码解读

⑦课堂思考

大家同学执行 npm create vue@3.24.0，大家执行 3.21.0，最后装的 Vue 版本会不一样吗？

展开解析

可能一样也可能差一点，但跟 3.21.0/3.24.0 没有直接因果关系。

create-vue 的模板里写的是区间（^3.5.x），具体装到哪个版本由"大家执行 npm install 那一刻 registry 上的最新版"决定。所以两个人哪怕用同一个生成器版本，隔一周跑也可能装到不同的 Vue。

想和同学完全一致，要对照的不是 create-vue 版本，而是 package-lock.json——它锁死了每个包的确切版本和哈希。这也是它必须提交进 Git 的原因：它才是"版本一致性"的唯一保证。

2.10

npm install 与 npm run dev 分别干了什么

①讲义要点

"接着我们要依次执行 1、2、3 个命令：cd vue / npm install / npm run dev"。没解释两条命令各自的职责，也没说为什么必须按这个顺序。

②核心讲解

这是两个完全不同阶段的事：npm install 是照菜谱买菜——读 package.json 的依赖清单，去 registry 把 vue、vite、vue-router 等所有包（连同它们的依赖）下下来塞进 node_modules，并生成 package-lock.json，和大家们的业务代码毫无关系；npm run dev 是下锅炒菜——启动 Vite 开发服务器，读 vite.config.js 和 index.html，实时编译 src/ 下的代码，起一个本地 HTTP 服务等大家访问。顺序不能颠倒：没有 node_modules 就没有 Vite。

③示例演示
bash3 行
1 2 3
cd vue           # 进工程目录（脚手架把文件放在子目录里）
npm install      # 装依赖
npm run dev      # 启动开发服务器
④代码解读
  • cd vue 为什么必须？因为 npm install 在当前目录里找 package.json。大家站在 xm-pro 敲而它下面没有 package.json，npm 会一路向上找父目录，最后报 ENOENT: no such file or directory, open '...\package.json'。
  • npm install（简写 npm i）四步：① 读 package.json 的 dependencies 和 devDependencies；② 有 package-lock.json 就严格按它锁定的版本装（保证和别人一致），没有就按 ^ 区间解析最新可用版并生成锁文件；③ 下载解压到 node_modules；④ 执行有 postinstall 脚本的包。
  • 本机实测：实训1_软件安装及创建Vue项目/工程/hello-vue/node_modules 下最终有 3262 个文件，而 package.json 里只声明了 5 个包——这就是"依赖树"的直观体量。
  • npm run dev 会去找 scripts.dev 的值 "vite" 并执行。终端里回显的 > 01@0.0.0 dev / > vite 就是 npm 在告诉大家"我实际跑的是这个"。01@0.0.0 来自 package.json:2-3。

现象：npm run dev 报 'vite' 不是内部或外部命令。原因：没先跑 npm install，node_modules/.bin/vite 不存在。怎么改：先装；装过还报就删 node_modules 重装。现象：npm install 刷一堆 npm warn deprecated。原因：正常现象，包多、有些包作者已停止维护。怎么改：deprecated 是警告不是错误，只要最后没有 npm ERR! 就是成功。

⑦课堂思考

npm install 之后修改了一行 src/App.vue，需要重新 npm install 吗？需要重新 npm run dev 吗？

展开解析

两个都不需要。

npm install 管的是"第三方包"，修改自己的业务代码它完全不关心。

npm run dev 起的 Vite 服务器带热更新（HMR）：保存 App.vue 的瞬间 Vite 只把改动的那个模块推给浏览器，页面自动刷新且不丢状态（这是它比 webpack 快的原因——按需编译，不是全量重编）。

唯一必须重跑 npm run dev 的情况是改了 vite.config.js——那是服务器自己的配置，得重启才生效。

2.11

①讲义要点

只说要"依次执行 1、2、3 个命令"，把 npm run dev 当成一个要背的咒语，没提 scripts 这个字段的存在，也没说 dev 是谁定义的。

2.12

Vite 开发服务器：为什么关掉命令行窗口就打不开了

①讲义要点

"此时是在命令行打开的项目，如果把命令行关闭，则 http://localhost:5173 无法访问。"——现象说出来了，但没解释为什么。

②核心讲解

因为 http://localhost:5173 这个网站根本不在互联网上，它就在自己的电脑里。npm run dev 在大家机器上起了一个小程序（Vite 开发服务器），它监听 5173 端口、随时把编译好的文件发给浏览器。关掉命令行窗口就等于把这个程序杀了，网站自然就没了。 类比：在家里开了个小型展览，门牌号是"我家 5173 房间"；大家人走了、门锁了，别人拿这个门牌号当然进不去——这个地址从来没对全世界公开过。

④代码解读
  • npm run dev 是前台阻塞的：终端停在 ready in xxx ms 不再返回提示符，这不是卡住，是服务器在工作。它占着这个窗口，所以窗口不能关。
  • netstat -ano | findstr :5173 → 会看到 TCP [::1]:5173 [::]:0 LISTENING 7432。LISTENING 表示"有进程正在这个端口等连接"，最后那个数字就是 node 的 PID——这就是"网站住在大家电脑里"的实锤。
  • curl http://localhost:5173/src/main.js 很关键：返回的不是写的原文件，而是 Vite 编译后的版本（import 被改写成带时间戳的 URL、.vue 被拆成 JS）。这直观证明了"开发服务器在实时编译大家们的源码"，浏览器拿到的从来不是大家们的原始文件。
  • npm run dev -- --host 里那个 -- 是必须的：它把参数和 npm 自己隔开，后面的才是传给 vite 的。--host 让 Vite 监听 0.0.0.0，同一 WiFi 下的手机就能用 http://你的IP:5173 访问。公共 WiFi 下不要乱开。

2.13

端口被占会自动 +1

①讲义要点

"复制地址：http://localhost:5173/，在浏览器中打开"——把 5173 写死了。而 实训1_软件安装及创建Vue项目/实验过程_实训1.md:83 里就真实遇到了这个情况（5173 被占，实际跑在 5171）。

②核心讲解

端口是"同一台电脑上的房间号"：IP 负责找到"哪栋楼"，端口负责找到"楼里哪个房间"。5173 是 Vite 约定俗成的默认房间号。如果房间已经有人住了（另一个 npm run dev 还在跑），Vite 不会撞门，而是自动去隔壁敲门：5173 不行就试 5174、5175…… 类比：酒店前台给大家 5173 房，发现有人了直接给大家 5174，不会把大家赶出去，也不会把里面的人赶出来。 所以永远不要背端口号，看终端输出。

2.14

①讲义要点

②核心讲解

2.15

讲义把 App.vue 叫"入口文件"不准

①讲义要点

第四部分第 5 条原文："精简 App.vue，App.vue 是作为项目的入口文件"。这个说法是错的（勘误第 5 条已指出）。

②核心讲解

入口（entry）的定义是"构建工具从这里开始往上爬依赖树"的那个文件。 在大家这个工程里是 src/main.js——因为 index.html 里 <script src="/src/main.js"> 直接指向它。App.vue 是 main.js 引用进来的一个组件，身份是"组件树的根"，不是"程序的入口"。类比：main.js 是开机键（按下去机器才开始转），App.vue 是默认桌面壁纸（开机后请看到的东西）——讲义的说法等于说"壁纸是开机键"。考试按讲义口径写没问题，但面试问到"Vue 工程入口在哪"答 App.vue 是要扣分的。

③示例演示

展开解析

2.16

createApp(App) / app.use(router) / app.mount('#app') 逐行拆解

①讲义要点

第四部分第 7 条只给了 main.js 的代码，一行解释都没有。可这三行是整个 Vue 应用的生命线，不讲透后面全讲不通。

②核心讲解

这三行是"造 → 装 → 挂"：createApp(App) 造一个 Vue 应用实例并指定根组件；app.use(router) 给它装插件（路由就是插件）；app.mount('#app') 把它塞进页面上那个空 div。类比：造一辆车 → 装上导航仪 → 把车开上路。 三步顺序不能换，少一步都不行。

③示例演示

④代码解读

  • const app = createApp(App)：接收一个组件对象作为根组件，返回应用实例（带 use、mount、component、directive、provide 等方法）。用 const 是因为 app 这个引用从头到尾不变，只是往它上面加东西。不写这行，后面 app.use 直接 ReferenceError: app is not defined。

  • app.mount('#app')：接收 CSS 选择器字符串或真实 DOM 元素。Vue 用它去 document.querySelector，把根组件渲染进去并清空原有内容。这是唯一真正碰 DOM 的一步。选择器对不上就报 Failed to mount app: mount target selector "#app" returned null。# 是 id 选择器，写成 'app' 会去找 <app> 标签。

2.19

App.vue 只保留 <RouterView /> 的意义

①讲义要点

第四部分第 5 条："精简 App.vue，App.vue 是作为项目的入口文件"——动作给了（精简成只留路由视图），但"为什么"和"入口文件"的说法都不对。

②核心讲解

<RouterView /> 是一个占位符：它自己不产生任何画面，就是一块留给路由的屏幕。当前地址匹配到哪个组件，那个组件就显示在这块屏幕的位置上。把 App.vue 精简成只剩它，等于让根组件退化成一块纯屏幕：页面显示什么，100% 由地址决定。类比：App.vue 是电视机，RouterView 是屏幕上的显示区域，路由是遥控器——以前电视机自带开机广告（脚手架生成的欢迎页），现在广告去掉了，屏幕上只有当前频道的内容。

global.css 全局样式 + 在 main.js 里 import 的顺序

①讲义要点

第四部分第 6 条："在目录 assets 下新建一个全局样式表文件：global.css，同时写上代码"。第 7 条："在 main.js 里面引入全局的 css"。同样只给动作，没讲"什么是全局样式"和"为什么要在 main.js 里引"。

②核心讲解

全局样式 = 不 scoped 的样式 = 影响整个页面，管的是"所有页面都一样的底色"：body 的外边距、默认字号、默认字体色。这些属性在组件里根本写不了（组件模板里没有 body 这个元素），所以必须有个地方专门管。类比：全局样式是房子的水电总闸和统一墙面漆，组件样式是每个房间自己的家具摆放——总闸得在整栋楼的总控室（main.js）合上，不能塞进某一个房间里。

2.21

①讲义要点

第四部分第 7 条下方说明："@ 是指向 src 的路径别名，在 vite.config.js 的 resolve.alias 里配好了，所以 @/assets/global.css 等价于 ./assets/global.css"。这个说明是对的，但"等价"只在当前这层目录下成立，跨目录就不等价了（见 ④）。

②核心讲解

  • '@': fileURLToPath(new URL('./src', import.meta.url)) 的意图是"算出 src 的绝对路径"，拆开看：import.meta.url 是当前这个配置文件自己的 URL（形如 file:///D:/course/Javaweb/实训1_软件安装及创建Vue项目/工程/hello-vue/vite.config.js）；new URL('./src', import.meta.url) 以它为基准解析出 file:///D:/course/Javaweb/实训1_软件安装及创建Vue项目/工程/hello-vue/src；fileURLToPath 转成 D:\course\Javaweb\实训1_软件安装及创建Vue项目\工程\hello-vue\src。为什么要这么绕？因为 resolve.alias 要的是绝对路径——写死 'D:/course/Javaweb/实训1_软件安装及创建Vue项目/工程/hello-vue/src' 的话，换台电脑、换个目录就废了。注意这里是 ./src 不是 ../src，因为基准是 vite.config.js 自己（它在工程根）。
  • 改别名练手：把 '@' 改成 '@@'，main.js 里的 @/assets/global.css 立刻报 Failed to resolve import。这证明 @ 不是 Vue 或 JavaScript 的内置语法，纯粹是 Vite 的配置。
  • jsconfig.json 和 Vite 的 alias 是两件独立的事：vite.config.js 的 alias 让编译器能找到文件（影响能不能跑）；jsconfig.json 的 paths 让 IDEA / VS Code 的智能提示能找到文件（只影响补全和跳转，不影响运行）。两边必须同步改——只改 Vite 能跑但 IDE 报红；只改 jsconfig 不报红但一运行就 Failed to resolve import。
  • @ 和 ./ 哪里不等价？ 讲义说"@/assets/global.css 等价于 ./assets/global.css"，这句只在 src/main.js 这一个文件里成立，因为 main.js 恰好就在 src 下，两者起点重合。换到 src/views/Home.vue 里，./assets/global.css 指的是 src/views/assets/global.css（不存在），而 @/assets/global.css 指的是 src/assets/global.css，完全不同。正确说法：@/xxx 恒等于「src 目录下的 xxx」；./xxx 等于「当前文件旁边目录下的 xxx」。
  • @ 能用在哪些地方？ 只在 JS 的 import 语句里可靠生效。写在模板属性字符串里（<img src="@/assets/a.png">）不生效，见 2.17 的易错点。
⑤工程对照

全部逐字核对过：vite.config.js:1 和 :13-17（resolve.alias 里的 '@': fileURLToPath(new URL('./src', import.meta.url))）；jsconfig.json:3-5（"paths": { "@/*": ["./src/*"] }）；src/main.js:4 是工程里唯一一处实际使用 @ 别名的代码；src/router/index.js:9 用的是 '../views/Home.vue' 相对路径——两种写法都合法，讲义给的就是相对路径版，知道它们指向同一个文件比纠结用哪种更重要。

⑥易错提醒

现象：报 Failed to resolve import "@/assets/global.css" from "src/main.js". Does the file exist?。原因：① alias 没配或被删；② 路径拼错（assets 写成 asset）；③ 改完 vite.config.js 没重启开发服务器。怎么改：核对配置；改 vite.config.js 必须 Ctrl+C 重跑 npm run dev（这是少数必须重启的情况）。现象：代码能跑但 IDEA 里 @/xxx 有红波浪线。原因：jsconfig.json 的 paths 没配或 IDEA 没重新加载。怎么改：确认内容正确后 File → Invalidate Caches / Restart，或右键 jsconfig.json → Reload project。现象：别人 clone 后报 Failed to resolve import 而大家本机是好的。原因：vite.config.js 没提交。怎么改：确认 vite.config.js、jsconfig.json 都在版本控制里。

⑦课堂思考

在 src/router/index.js 里，'../views/Home.vue' 和 '@/views/Home.vue' 是同一个文件吗？把 src/router/ 改名成 src/routes/，哪个要改？

展开解析

是同一个文件，都指向 D:\course\Javaweb\实训1_软件安装及创建Vue项目\工程\hello-vue\src\views\Home.vue。

  • '../views/Home.vue'：从 src/router/index.js 出发，../ 回到 src/ 再进 views/。
  • '@/views/Home.vue'：@ 就是 src，直接就是 src/views/Home.vue。

改名成 src/routes/ 之后：

  • '../views/Home.vue' —— ../ 依然回到 src/，所以碰巧还是对的（只改了父目录名字，层级没变）。
  • 但如果把文件从 src/router/index.js 挪到 src/router/admin/index.js（多了一层），'../views/...' 就变成指 src/router/views/... 了，必须改成 '../../views/...'；而 '@/views/Home.vue' 一个字都不用改。
