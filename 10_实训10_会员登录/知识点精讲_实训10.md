## 0. 这一讲在整门课里的位置

第 9 讲把员工表的增删改查跑通之后，后台已经能查、能加、能改、能删了——但它有一个致命问题：**谁都能进**。打开 `http://localhost:5173` 直接就是管理页面，后端接口也没有任何门。这一讲给整个系统装一扇门：先建一张 `user` 表存账号密码，再写一个登录接口，最后让前端拿着"登录过"的标记，才肯放人进 `/manage`。

技术上是三条线合流。后端第一次把 **Controller → Service → Mapper → XML** 四层完整地串在一个真实功能里（第 8 讲只是把 MyBatis 接上，第 9 讲是把增删改查重复了四遍，这一讲是一条最短、但每一层都不缺的业务链）；前端第一次把 **表单 + 请求 + 本地存储 + 路由守卫** 四样东西连起来用。前六讲学的 `v-model`、`el-form`、`router.push`，第 5 讲学的 `beforeEach`，到这一讲才真正"为了一个业务目标"被组装起来。

更重要的是一个观念：**登录是前端体验与后端数据的配合，不是某一处代码里的开关**。这一讲做完，大家会得到一个能登进去的账号（`admin/123456`），也会第一次撞见"前端拦得住手、拦不住 curl"这件事——这是第 12 讲账号管理、以及后面所有需要权限的功能的地基。

## 2. 知识点精讲

### 2.1 user 表：账号密码单独一张表

**① 讲义怎么说** —— "一、在数据库中，新增管理员表 `user`"，给出的建表语句是 `id / username / password / name` 四列，`username` 上加 `UNIQUE`，并插入一条测试账号 `('admin','123456','系统管理员')`。功能说明第 1 条强调：**"数据表独立：账号密码单独存在 `user` 表，和员工表完全分离"**。

**② 一句话讲透** —— 把数据库想成一栋楼：`employee` 是人事档案室，`user` 是门卫室那张登记簿。两件事得分开记——员工不一定有后台账号（只录资料的实习生），管理员也不一定是员工（外包运维）。合成一张表，每加一个能登录的人就得往人事档案里塞一条假员工；员工离职删档案，登录权限也跟着没了。分开后各自瘦身：登录只关心"你是谁、口令对不对"，一条 `where username = ? and password = ?` 命中唯一索引就返回，不联表、不扫全表。四列，正说明它只放登录必需的东西。

**③ 示例代码** ——

```sql
CREATE TABLE `user` (
  id       INT PRIMARY KEY AUTO_INCREMENT COMMENT '主键id',
  username VARCHAR(50) NOT NULL UNIQUE     COMMENT '登录账号',
  password VARCHAR(50) NOT NULL            COMMENT '登录密码',
  name     VARCHAR(50) DEFAULT ''          COMMENT '管理员姓名'
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

INSERT INTO `user`(username, password, name) VALUES ('admin', '123456', '系统管理员');

SELECT id, username, name FROM `user`;   -- 查的时候别把 password 带出来
```

**④ 逐行拆解** ——

- `id INT PRIMARY KEY AUTO_INCREMENT`：主键自增。前端拿到的 `id` 就是这一列，第 12 讲改密码、删管理员都靠它定位人。**不要用 username 当主键**——账号是可以改的，改一次所有引用它的地方都得跟着改。
- `username VARCHAR(50) NOT NULL UNIQUE`：`NOT NULL` 保证不会有"空账号"；`UNIQUE` 在数据库层建唯一索引，同时干两件事——**判重**（第 12 讲新增管理员插重复账号会直接报错）和**加速**（登录的等值查询走索引，几万行也是毫秒级）。
- `password VARCHAR(50) NOT NULL`：讲义这里是**明文**存的，长度 50 够放 `123456`，也够放 32 位 MD5。真实项目必须存哈希（见 2.9 的坑），这一讲先按讲义跑通。
- `name VARCHAR(50) DEFAULT ''`：显示用的姓名，登录后右上角那个"系统管理员"就是它。给默认空串而不允许 `NULL`，是为了前端 `name || username` 取值时少判一种情况。
- `ENGINE=InnoDB DEFAULT CHARSET=utf8mb4`：InnoDB 支持事务和行锁；`utf8mb4` 才是"真 UTF-8"（`utf8` 只占 3 字节，存不下 emoji）。
- `INSERT` 不写 `id`：自增列交给数据库；`('admin','123456','系统管理员')` 就是本讲的测试账号，**用户名和密码的大小写要和登录页敲的完全一致**。

**⑤ 在你仓库里** —— 实体类在 `D:\my-project\xm-pro\springboot\src\main\java\com\example\entity\User.java` 第 4~7 行，四个字段与四列一一对应（`id/username/password/name`，顺序都一样）；查询语句在 `D:\my-project\xm-pro\springboot\src\main\resources\mapper\UserMapper.xml` 第 8~10 行：`select * from user where username = #{username} and password = #{password}`；库名在 `D:\my-project\xm-pro\springboot\src\main\resources\application.yml` 第 3 行的 `jdbc:mysql://localhost:3306/xm-pro`。仓库里没有单独的 `user.sql`（`springboot/sql/` 下只有 `article.sql`），这张表要按讲义在 Navicat 里手工建——**建表这一步没有代码可抄，必须自己执行一次**。

**⑥ 常见坑** —— ① 报 `Table 'xm-pro.user' doesn't exist` → 表建在了另一个库（比如 `xm_pro`），或者 `application.yml` 第 3 行的库名与建表时选的库不是同一个 → 在 Navicat 里点开对应库执行 `show tables`，两边库名逐字对齐。② 第二次执行 `INSERT` 报 `Duplicate entry 'admin' for key 'user.username'` → `UNIQUE` 生效了，这是正常现象 → 先 `delete from user where username='admin'`，或改用 `INSERT IGNORE`。③ 用 `admin` 能登、用 `Admin` 也能登 → MySQL 默认排序规则 `utf8mb4_general_ci` **大小写不敏感** → 业务若要求区分，建表时给 `username` 指定 `COLLATE utf8mb4_bin`。

**⑦ 自测** —— 登录查询为什么用 `username + password` 两个条件，而不是先按 username 查出来、再在 Java 里比对密码？

<details><summary>展开解析</summary>

两种写法都能跑，但一条 SQL 少一次"查出来再传回来"的往返，而且把比对交给数据库，Java 侧只判断"有没有结果"。更关键的是：先 `selectByUsername` 再比密码，`User` 对象会在 Java 里完整存在一段时间，日志、异常栈都可能带出密码；一条 SQL 查不到就返回 `null`，泄露面更小。仓库 `UserService.java` 第 18~20 行选的正是前者。

</details>

### 2.2 登录接口：Controller-Service-Mapper 一条线

**① 讲义怎么说** —— "二、后端设计"列了五个文件：`entity/User.java`、`mapper/UserMapper.java`、`mapper/UserMapper.xml`、`service/UserService.java`、`controller/UserController.java 登录接口`。功能说明第 2 条：**"登录接口接收账号密码，直接去数据库匹配，查不到则返回 `400` 错误"**；第 6 条要求后端保持 **"三层架构（Controller-Service-Mapper）、MyBatis XML、@Resource 注入、REST POST 登录接口"** 的风格。

**② 一句话讲透** —— 三层架构像去银行办事：Controller 是**大堂经理**，只接住你递的材料、把结果原样告诉你，不碰钱；Service 是**柜员**，判断"这人能不能办、该走哪条流程"；Mapper 是**金库的门**，只认一句"给我账号密码，我把那行记录递出来"。登录这条链特别短：Controller 把账号密码交给 Service，Service 一行代码转手给 Mapper，XML 里就是一条查询。**没有业务规则时 Service 也不该跳过**——它是以后加"账号被锁、登录次数、验证码"的地方，位置要先留。

**③ 示例代码** ——

```java
@RestController
@RequestMapping("/user")
public class UserController {

    @Resource
    private UserService userService;

    @PostMapping("/login")
    public Result login(@RequestBody User user) {
        User loginUser = userService.login(user.getUsername(), user.getPassword());
        if (loginUser == null) {
            return Result.error("400", "账号或密码错误");
        }
        return Result.success(loginUser);
    }
}
```

```xml
<select id="selectByUsernameAndPassword" resultType="com.example.entity.User">
    select * from user where username = #{username} and password = #{password}
</select>
```

**④ 逐行拆解** ——

- `@RestController` = `@Controller` + `@ResponseBody`：方法返回的 `Result` 由 Jackson 直接写成 JSON，而不是去找一个叫 `Result` 的页面。
- `@RequestMapping("/user")` 是**类级别前缀**，方法上的 `@PostMapping("/login")` 拼起来才是 `/user/login`；前端 `request.post("/user/login", ...)` 的路径必须和这两段拼出来的一致，少一段就是 404。
- `@Resource private UserService userService;`：把 Service 注入进来。`@Resource` 按**名字**找（默认取字段名 `userService`），`@Autowired` 按**类型**找——本课程统一用 `@Resource`，和第 8、9 讲保持一致。
- `@PostMapping` 而不是 `@GetMapping`：登录要传密码，**密码不能出现在 URL 里**（URL 会进浏览器历史、Nginx 日志、Referer）。POST 把数据放在请求体里。
- `user.getUsername(), user.getPassword()`：Service 只收两个 `String`，不收整个 `User`——这样 Service 不依赖"前端多传了哪个字段"，将来加验证码只改参数列表。
- `if (loginUser == null)`：MyBatis 查不到时返回 `null`（不是空对象，也不抛异常），这是"账号或密码不对"的**唯一判据**。
- `Result.error("400", ...)` 与 `Result.success(loginUser)`：两个分支都返回 `Result`，前端只认 `code`，见 2.4。
- XML 里的 `#{}`：预编译占位符，等于 JDBC 的 `?`，值不会被当成 SQL 片段——这也是防注入的关键，详见 2.9。

**⑤ 在你仓库里** —— Controller 在 `D:\my-project\xm-pro\springboot\src\main\java\com\example\controller\UserController.java` 第 22~29 行（`@PostMapping("/login")` 在第 22 行，判空在第 25~27 行）；Service 在 `...\service\UserService.java` 第 18~20 行，方法体只有一行 `return userMapper.selectByUsernameAndPassword(username, password);`；Mapper 接口在 `...\mapper\UserMapper.java` 第 11 行，两个参数都加了 `@Param`；SQL 在 `...\resources\mapper\UserMapper.xml` 第 8~10 行。这四份文件缺一份，启动时就会报 `Invalid bound statement (not found)`。

**⑥ 常见坑** —— ① 启动报 `Invalid bound statement (not found): com.example.mapper.UserMapper.selectByUsernameAndPassword` → XML 的 `namespace` 或 `<select id>` 与接口对不上，或者 XML 不在 `mapper-locations` 覆盖的目录里 → 核对 `UserMapper.xml` 第 5 行的 `namespace`、第 8 行的 `id`，以及 `application.yml` 第 14 行 `classpath:mapper/*.xml`。② 接口 404 → 类上写了 `/user`、方法上又写成 `/user/login`，实际路径变成 `/user/user/login` → 方法上只写 `/login`。③ 前端提示"账号或密码错误"但数据库里明明有这条记录 → 传上去的 `username` 是 `null`（见 2.3）→ 在 Controller 里 `System.out.println(user.getUsername())` 打一下，再看 Network 的 Payload。

**⑦ 自测** —— 如果把 `@PostMapping` 改成 `@GetMapping`，前端 `request.post` 一行不改，会发生什么？

<details><summary>展开解析</summary>

405 Method Not Allowed。Spring 按"路径 + 方法"匹配处理器：`/user/login` 这个路径存在，但只接受 GET，POST 会被拒绝。前端 `request.js` 的错误分支里 `error.response.status` 是 405，走 `console.error`，页面上只看到按钮点了没反应。**路径对不代表方法对**，这是 404 与 405 的区别。

</details>

### 2.3 @RequestBody：JSON 怎么变成 User

**① 讲义怎么说** —— 讲义正文只写了"登录接口接收账号密码"，没有单独解释这个注解，但"二、5 controller/UserController.java 登录接口"给的代码第一行就是 `public Result login(@RequestBody User user)`；功能说明第 6 条把接口定性为 **"REST POST 登录接口"**——REST 的 POST 用请求体传数据，这就是 `@RequestBody` 存在的理由。

**② 一句话讲透** —— 把 HTTP 请求想成快递包裹：URL 是收件地址，请求头是面单（写着里面是什么、什么格式），**请求体才是箱子里的货**。前端提交时，axios 把表单对象序列化成 JSON 塞进箱子，面单上写 `application/json`。Spring 收到后，`@RequestBody` 等于说"把箱子打开、按面单拆"：它找到处理 JSON 的转换器，把文本**反序列化**成 `User` 对象再递进来。所以它读 body 不读 URL；前端一改 `Content-Type`，后端立刻 415。

**③ 示例代码** ——

```java
// 前端实际发出的请求体（Content-Type: application/json）
// {"username":"admin","password":"123456"}

@PostMapping("/login")
public Result login(@RequestBody User user) {
    // Jackson 按字段名赋值：username → setUsername()，password → setPassword()
    System.out.println("收到：" + user.getUsername() + " / " + user.getPassword());
    User loginUser = userService.login(user.getUsername(), user.getPassword());
    return loginUser == null ? Result.error("400", "账号或密码错误") : Result.success(loginUser);
}
```

**④ 逐行拆解** ——

- `@RequestBody` 只能挂在**请求体**上。GET 请求通常没有 body，所以它几乎总和 POST/PUT 一起出现。
- 反序列化的依据是**字段名**：JSON 里的 `username` 去找 `setUsername()`，`password` 去找 `setPassword()`；名字对不上就是 `null`，**并且不报错**（Jackson 默认忽略不认识的字段）。
- 一个方法最多一个 `@RequestBody`：请求体只有一个，拆不出两份来。
- 必须带 `Content-Type: application/json`；缺了会 415，写成 `application/x-www-form-urlencoded` 会 415 或参数全空。
- `User` 必须有**无参构造 + setter**：Jackson 先 `new User()` 再逐个 set。只写全参构造、不给无参构造，反序列化就会失败。
- 和 `@RequestParam`（取 URL 里 `?a=1` 的值）、`@PathVariable`（取路径里 `/delete/{id}` 的值）是三套不同的取数位置，别混着用。

**⑤ 在你仓库里** —— 注解用在 `D:\my-project\xm-pro\springboot\src\main\java\com\example\controller\UserController.java` 第 23 行，紧接着第 24 行就取字段；`Content-Type` 是 `D:\my-project\xm-pro\vue\src\utils\request.js` 第 11 行统一设的 `config.headers['Content-Type'] = 'application/json;charset=utf-8'`；真正把对象送出去的是 `...\views\Login.vue` 第 36 行 `request.post("/user/login", data.form)`（第二个参数就是 body）；能被反序列化的前提是 `...\entity\User.java` 第 4~7 行的字段名和第 9~39 行的 getter/setter。同文件第 94 行的 `@PathVariable Integer id` 正好拿来对比。

**⑥ 常见坑** —— ① 后端报 `Required request body is missing` 或 `HttpMessageNotReadableException` → 前端写成 `request.post(url, null, { params: data.form })`，数据跑到 URL 上、body 是空的 → 第二个参数直接传对象。② 415 Unsupported Media Type → `Content-Type` 不是 `application/json`（被手动覆盖成了表单格式）→ 保留 `request.js` 第 11 行的统一设置，别在单个请求里改。③ 后端 `user.getUsername()` 是 `null`，可 Network 里明明有值 → JSON 的 key 和实体字段名不一致（`userName` vs `username`）→ 以 `User.java` 的字段名为准改前端。

**⑦ 自测** —— `@RequestBody` 和 `@RequestParam` 分别从请求的哪个位置取值？把登录接口改成 `@RequestParam String username, String password`，前端要怎么改？

<details><summary>展开解析</summary>

`@RequestBody` 读请求体（body），`@RequestParam` 读 URL 查询串或表单参数（`?username=admin&password=123456`）。改了之后前端必须把参数放进 URL：`request.post("/user/login", null, { params: data.form })`，或者干脆改成 `request.get`。这也说明为什么登录不能用 GET——密码会明晃晃地留在 URL、历史记录和服务器访问日志里。

</details>

### 2.4 Result 返回：成功 200、失败 400＋msg

**① 讲义怎么说** —— 功能说明第 3 条："**统一返回格式：复用 `Result` 类，成功 200、错误自定义 code+msg**"；第 4 条："**全局异常兼容：密码错误直接返回 `Result.error`，不需要抛自定义异常也能正常弹窗**"。第 7 讲已经把 `Result` 建好放在 `common/Result.java`，这一讲是它第一次在真实业务里派上用场。

**② 一句话讲透** —— `Result` 像快递的统一纸箱：里面装的东西千差万别（一个 `User`、一个列表、什么都没有），但箱子外形、面单位置完全一样，收件人（前端）不用每次猜"这回送来的是箱子还是麻袋"。三个字段分工明确：`code` 是结论，`msg` 是给人看的话，`data` 是货。好处很实在：前端那句判断可以写一万遍不用改；出错时 HTTP 仍是 200，控制台不会一片红；所有接口结构一致。代价是**两层状态码**——HTTP 200 只代表"服务器答复了"，业务成没成要看 `code`。

**③ 示例代码** ——

```java
// UserController.java 第 25~28 行
if (loginUser == null) {
    return Result.error("400", "账号或密码错误");   // code="400"，msg 给前端弹窗
}
return Result.success(loginUser);                   // code="200"，data=User
```

**④ 逐行拆解** ——

- `Result.success(loginUser)` 调的是 `success(Object data)` 重载（`Result.java` 第 17~21 行）：先调无参 `success()` 拿到 `code="200"`、`msg="请求成功"`，再 `setData`。
- `Result.error("400", "账号或密码错误")` 调的是两参工厂（第 30~35 行），**code 和 msg 都是自己传的**；无参的 `Result.error()`（第 23~28 行）给的是 `"500" / "系统错误"`，两个别混用。
- `code` 是 `String` 不是 `int`：所以前端必须写 `res.code === "200"`，写 `=== 200` 永远不成立（第 7 讲踩过，这一讲还会有人踩）。
- 登录失败**依然是 HTTP 200**：`Result.error` 只是把 code 写进响应体，没有动 HTTP 状态码。浏览器 Network 里那条请求是绿的，页面上的红字来自前端 `ElMessage.error(res.msg)`。
- `data` 里装的是整个 `User`，**连 `password` 一起**序列化回了浏览器——这是本讲代码的真实行为，第 12 讲做账号管理时要收口，见 2.9 的坑。
- 前端 `then(res => ...)` 里的 `res` 已经是 `Result` 对象：`request.js` 第 19~27 行的响应拦截器 `return res`（`response.data`），不是 axios 原生响应。

**⑤ 在你仓库里** —— 三字段定义在 `D:\my-project\xm-pro\springboot\src\main\java\com\example\common\Result.java` 第 6~8 行，两个 `success` 在第 10~21 行，两个 `error` 在第 23~35 行；两个分支在 `...\controller\UserController.java` 第 25~28 行；前端读 code 在 `...\views\Login.vue` 第 37~43 行；`request.js` 第 19~27 行的响应拦截器决定了 `res` 就是 `Result`。

**⑥ 常见坑** —— ① 前端 `if (res.code === 200)` 永远进 else，明明登录成功却提示"账号或密码错误" → `code` 是字符串 `"200"` → 写 `"200"`，或 `Number(res.code) === 200`。② 某个接口直接 `return "ok"`，前端 `res.code` 是 `undefined` → 没走统一返回 → 一律 `return Result.xxx(...)`。③ 想让失败也返回 HTTP 400，于是加 `@ResponseStatus` 或改成 `ResponseEntity`，结果前端拦截器把它当网络错误、拿不到 `res` → 本课程约定：**HTTP 永远 200，业务状态放 code**，别混两套。

**⑦ 自测** —— 登录失败时，浏览器 Network 里这条请求的 HTTP 状态码是多少？页面上的红色提示又是谁弹的？

<details><summary>展开解析</summary>

HTTP 状态码是 **200**。`Result.error("400", ...)` 只改了响应体里的 `code`，没有改 HTTP 状态行；请求本身"成功地被处理并答复了"。红色提示是前端 `Login.vue` 第 42 行 `ElMessage.error(res.msg)` 弹的，`msg` 来自后端。**结论**：HTTP 状态码看"这次通信成没成"，响应体 `code` 看"这件业务成没成"。

</details>

### 2.5 Login.vue：一个表单、一个函数

**① 讲义怎么说** —— "三、前端设计 1. 新增登录页面 Login.vue"给了完整代码：`el-card header="系统登录"` 里套 `el-form`，两个 `el-input` 分别绑 `data.form.username` 与 `data.form.password`，按钮 `@click="login"`；`script setup` 里用 `reactive` 定义表单、`request.post("/user/login", data.form)` 提交、`res.code === "200"` 时存 `localStorage` 并 `router.push("/manage")`，否则 `ElMessage.error(res.msg)`。功能说明第 6 条要求前端保持 **"`script setup` + reactive、Element 表单弹窗、request 统一请求封装"** 的风格。

**② 一句话讲透** —— 这个页面只干三件事，像去银行柜台：**填单**（两个输入框用 `v-model` 把值实时写进表单对象）、**递单**（`request.post` 把整个表单当请求体发出去）、**听结果**（`code` 是 `"200"` 就存凭证进后台，否则把后端的话原样弹出来）。它**不校验密码长度、不判断账号格式**——那些是表单校验，讲义这版故意留白；它也**不负责"记住我"**，因为凭证已经写进 `localStorage`，关掉浏览器照样在。二十来行就够，是因为脏活都被 `request.js` 和守卫接走了。

**③ 示例代码** ——

```vue
<script setup>
import { reactive } from "vue";
import request from "@/utils/request.js";
import { ElMessage } from "element-plus";
import { useRouter } from "vue-router";

const router = useRouter();
const data = reactive({ form: { username: "", password: "" } });

const login = () => {
  request.post("/user/login", data.form).then(res => {
    if (res.code === "200") {
      ElMessage.success("登录成功");
      localStorage.setItem("loginUser", JSON.stringify(res.data));
      router.push("/manage");
    } else {
      ElMessage.error(res.msg);
    }
  });
};
</script>
```

**④ 逐行拆解** ——

- `reactive({ form: { ... } })`：外面包一层 `form`，是为了**整体传给后端**（`data.form` 正好是 `{username, password}`）；以后加"验证码""记住我"只往 `form` 里加字段，`request.post` 那行不用改。
- `v-model="data.form.username"`：双向绑定，输入即改值，不需要 `@input` 手动取；`show-password` 只是把明文换成小眼睛，值本身没有加密。
- `@click="login"`：`el-button` 不是原生 `submit`，在输入框里敲回车不会自动提交，所以点击事件必须显式绑。
- `request.post("/user/login", data.form)`：第一个参数是路径（拼在 `baseURL` 后面），第二个参数是**请求体**，第三个参数才是配置对象（`params`、`headers` 之类）。
- `.then(res => ...)`：响应拦截器已经 `return res`（`response.data`），所以这里的 `res` 就是 `Result` 对象，不用再写 `res.data.code`。
- `res.code === "200"`：字符串比较，理由见 2.4。
- `localStorage.setItem("loginUser", JSON.stringify(res.data))`：存的是 `User` 序列化后的字符串，键名 `loginUser` 是全局约定，见 2.6。
- `router.push("/manage")`：编程式导航，压一条历史记录；用户点浏览器"后退"会回到登录页。
- `ElMessage.error(res.msg)`：把后端的话直接展示，**不要自己写死"密码错误"**，否则后端改了提示、前端就对不上。

**⑤ 在你仓库里** —— `D:\my-project\xm-pro\vue\src\views\Login.vue` 第 5~15 行是表单结构，第 28~33 行是 `reactive`，第 35~45 行是 `login` 函数；登录路由注册在 `...\src\router\index.js` 第 6 行（`path: '/login'`，懒加载 `../views/Login.vue`）；请求前缀在 `...\src\utils\request.js` 第 4~7 行 `baseURL: 'http://localhost:8080'`；背景图文件是 `D:\my-project\xm-pro\vue\public\login_bg.png`，对应 `Login.vue` 第 60 行的 `url('/login_bg.png')`。

**⑥ 常见坑** —— ① 页面背景一片白 → 代码里写的是 `/login_bg.png`，而大家从素材里拷的是 `login_bg.jpg` → 图片放进 `vue/public/` 并把文件名改成与代码一致（`public` 下的文件用 `/` 开头直接访问）。② 点登录没反应，控制台报 `Cannot read properties of undefined (reading 'form')` → `reactive` 写成了 `ref` 却忘了 `.value`，或者把 `data` 整个传给了 `post` → 统一用 `reactive`，传 `data.form`。③ 登录成功却还停在登录页 → `router.push` 被守卫拦回来了，多半是 `localStorage` 键名和守卫里读的不一致（`loginUser` vs `loginuser`）→ 三处（写入、守卫、顶栏）用同一个字符串。

**⑦ 自测** —— `request.post(...).then(res => ...)` 里的 `res` 为什么不是 axios 原生的 `response`？如果拦截器里没有 `return res`，这里要怎么写？

<details><summary>展开解析</summary>

因为 `request.js` 第 19~27 行的响应拦截器把 `response` 换成了 `response.data` 并 `return`，所以下游 `then` 拿到的是**响应体**（也就是 `Result` 对象）。如果没有这行 `return`，`res` 会是 axios 的完整响应，得写 `res.data.code`、`res.data.msg`、`res.data.data`——三层 `.data` 极易写错。这也解释了为什么要做"统一请求封装"：把这一层差异一次性吃掉。

</details>

### 2.6 localStorage：把登录人存成一张便签

**① 讲义怎么说** —— 功能说明第 5 条："**前端权限控制：用 `localStorage` 存登录标识，未访问 `/manage` 后台路由自动跳登录页**"；登录代码里是 `localStorage.setItem("loginUser", JSON.stringify(res.data))`，退出时是 `localStorage.removeItem("loginUser")`。功能说明第 7 条又要求退出时"**清空本地存储返回登录页**"。

**② 一句话讲透** —— `localStorage` 是浏览器按**域名**发给每个网站的一个抽屉：同一个源下所有页面共用，关掉浏览器再打开还在，除非代码删掉或用户清缓存。它只认**字符串**——对象要先 `JSON.stringify` 塞进去，取出来再 `JSON.parse`。和 `sessionStorage` 的区别是"关标签页就没了"；和 cookie 的区别是"不会自动跟着每个请求发给后端"（这正是 2.9 要讲的）。把它想成贴在显示器边上的**便签**：写着"我是 admin"，自己看着方便，但谁都能撕下来换一张。

**③ 示例代码** ——

```js
// 存：登录成功后（Login.vue 第 39 行）
localStorage.setItem("loginUser", JSON.stringify(res.data));

// 取：守卫、顶栏、首页、个人中心都要用，统一加兜底
const readLoginUser = () => {
  try {
    return JSON.parse(localStorage.getItem("loginUser") || "{}") || {};
  } catch (e) {
    return {};
  }
};

// 删：退出登录（Manage.vue 第 113 行）
localStorage.removeItem("loginUser");
```

**④ 逐行拆解** ——

- `setItem(key, value)`：key 是字符串，value **必须是字符串**；直接传对象不会报错，而是静默存成 `"[object Object]"`——最阴的一个坑。
- `JSON.stringify(res.data)`：`res.data` 是后端返回的 `User`（`id/username/password/name`），序列化后形如 `{"id":1,"username":"admin","name":"系统管理员"}`。
- `getItem("loginUser") || "{}"`：没登录时 `getItem` 返回 `null`，`JSON.parse(null)` 得到 `null`，后面 `user.name` 立刻报错；给个 `"{}"` 兜底。
- `try / catch`：用户手改过 localStorage、或存进去的是 `[object Object]`，`JSON.parse` 会抛 `SyntaxError`，一个坏字符串能让整个页面白屏。
- `removeItem(key)`：只删这一个键；`localStorage.clear()` 会把同域名下所有键清空，别乱用。
- 生命周期：**永久**——除非代码删、用户清。所以"关浏览器就退出登录"这种需求它天然满足不了，要么用 `sessionStorage`，要么退出时手动清。

**⑤ 在你仓库里** —— 写入在 `D:\my-project\xm-pro\vue\src\views\Login.vue` 第 39 行；读取分别在 `...\src\router\index.js` 第 41 行（守卫）、`...\src\views\Manage.vue` 第 101~110 行（顶栏用户名）、`...\src\views\Index.vue` 第 80~87 行（首页问候）、`...\src\views\Profile.vue` 第 36~44 行（改密时取 `id`）；删除在 `Manage.vue` 第 113 行。**五处读、一处写、一处删，键名必须完全一致**。

**⑥ 常见坑** —— ① 刷新后右上角变成"系统管理员"而不是登录人 → 存的时候漏了 `JSON.stringify`，`JSON.parse("[object Object]")` 抛错被 catch 成 `{}` → F12 的 Application → Local Storage 看 `loginUser` 的值是不是以 `{` 开头。② 登录成功立刻被弹回登录页 → 键名不一致，或 `setItem` 写在 `router.push` 之后 → 先存再跳。③ 无痕/隐私模式下 `setItem` 抛 `QuotaExceededError` → 浏览器禁用了存储 → 用 `try/catch` 包住，失败时退化成内存变量，至少本次会话能用。

**⑦ 自测** —— 为什么不能把登录用户存成 `<script setup>` 里的一个普通变量，或者 Pinia 的 state？刷新一下会怎样？

<details><summary>展开解析</summary>

普通变量和 Pinia 的 state 都活在**当前页面的 JS 内存**里，按 F5 刷新，Vue 应用整体重建，内存清空，登录人信息和"登录过"的事实一起消失——守卫立刻判定未登录，把你踢回 `/login`。`localStorage` 存在浏览器的持久化存储里，刷新、关标签、重启浏览器都还在，所以它能承担"跨页面、跨会话记住登录人"的职责。代价是它只在浏览器里，后端看不见，见 2.9。

</details>

### 2.7 路由守卫：/manage 的门禁

**① 讲义怎么说** —— "三、2. 修改路由 router/index.js"：**"新增登录路由 + 简单登录拦截（未登录禁止进入后台）"**。功能说明第 5 条把效果说清楚了：**"未访问 `/manage` 后台路由自动跳登录页"**。

**② 一句话讲透** —— 路由守卫就是小区门口的**门卫**：每次路由要切换（点菜单、敲地址、`router.push`），页面真正渲染之前，`beforeEach` 先被调用一次，门卫手里有三个东西——`to`（去哪）、`from`（从哪来）、`next`（放不放行）。讲义这版只问两句："你要去的是不是 `/manage` 开头？""你身上有没有 `loginUser` 这张条？"都满足就 `next()`，否则 `next('/login')`。它守的是**前端路由**，不是接口——挡得住手滑，挡不住 curl。

**③ 示例代码** ——

```js
router.beforeEach((to, from, next) => {
  document.title = to.meta.title || '系统登录';
  const user = localStorage.getItem('loginUser');

  if (to.path.startsWith('/manage') && !user) {
    next('/login');
  } else {
    next();
  }
});
```

**④ 逐行拆解** ——

- `router.beforeEach`：全局前置守卫，注册一次、对所有路由生效；`router/index.js` 在模块顶层执行，`main.js` 第 10 行才 `app.use(router)`，所以它天然先于任何一次导航。
- `to` / `from` 是 Route 对象：`to.path` 是完整路径（如 `/manage/herb`），`to.meta` 就是路由配置里那个 `meta: { title: '中药材管理' }`。
- `document.title = to.meta.title || '系统登录'`：顺手把标签页标题改掉；`||` 是兜底——没配 `meta.title` 的路由显示"系统登录"。
- `localStorage.getItem('loginUser')`：只判断**有没有**，不判断内容对不对；取不到是 `null`，也就算"没有"。
- `to.path.startsWith('/manage')`：覆盖 `/manage`、`/manage/herb`、`/manage/dashboard` 全部子路由；写成 `=== '/manage'` 就只挡首页。
- `next('/login')`：中断当前导航，改去登录页；`next()` 是放行。**每个分支必须且只能调用一次**。
- 为什么不写在 `Login.vue` 或 `Manage.vue` 里：守卫是"所有入口的统一关口"，手敲地址、收藏夹、`router.push` 都经过它；写在页面里只能管"从页面点进去"这一种。

**⑤ 在你仓库里** —— 守卫在 `D:\my-project\xm-pro\vue\src\router\index.js` 第 39~48 行；登录路由在第 6 行，根路径重定向在第 7 行（`{ path: '/', redirect: '/login' }`，所以打开 `http://localhost:5173` 直接就是登录页）；后台父路由在第 10~35 行，各子路由的 `meta.title` 决定标签页文字；登录成功后的跳转在 `...\views\Login.vue` 第 40 行。

**⑥ 常见坑** —— ① 页面白屏、控制台警告 `next() called multiple times` 或导航卡住 → 某个分支忘了 `next()`，或 `if/else` 两边都调了 → 保证每条路径恰好一次。② 手敲 `/manage/herb` 能直接进 → 判断写成了 `to.path === '/manage'` → 改成 `startsWith`。③ 登录成功又被踢回登录页 → `setItem` 在 `router.push` 之后执行，守卫先跑、看到没凭证就拦了 → 先存再跳（`Login.vue` 第 39、40 行的顺序不能换）。④ 死循环：`/login` 也被拦 → 条件只对 `/manage` 生效，且 `next('/login')` 的目标本身不能再触发拦截。

**⑦ 自测** —— 把 `startsWith('/manage')` 换成 `to.meta.requiresAuth` 的写法，路由配置里要加什么？两种写法各适合什么场景？

<details><summary>展开解析</summary>

要给每个需要保护的路由加 `meta: { requiresAuth: true }`，守卫里改成 `if (to.meta.requiresAuth && !user)`。**前缀写法**胜在短、适合"整个 `/manage` 都要保护"；**meta 写法**更精确、适合"同一个父路由下有的页面要登录、有的不要"（比如 `/manage/detail` 是公开文章详情）。仓库用的是前缀写法，和讲义一致；两种不能混着写一半，否则会出现"这个页面忘了加 meta 就漏了"。

</details>

### 2.8 退出登录：撕掉便签、送回门口

**① 讲义怎么说** —— 功能说明第 7 条："**配套退出功能：后台顶部增加退出按钮，清空本地存储返回登录页**"；"三、3. Manage.vue 新增退出登录按钮"给的代码顺序是：`localStorage.removeItem("loginUser")` → `ElMessage.success("已退出登录")` → `router.push("/login")`。

**② 一句话讲透** —— 退出登录就是**把便签撕掉，再把人送回门口**。顺序不能反：先 `removeItem` 再 `push`，守卫放行时看不到凭证，才会把人挡在 `/login`；如果先 `push` 再删，跳转那一刻守卫还能读到 `loginUser`，会以为"你还登录着"，直接放你进 `/manage`。另外它只是"前台"的退出——本讲后端没有会话，所以没有任何东西需要通知服务器；真实系统里还要调一个 `/logout` 让 token 失效，否则别人捡到旧 token 照样能用。

**③ 示例代码** ——

```js
// Manage.vue 第 112~116 行
const logout = () => {
  localStorage.removeItem('loginUser')   // 1. 先撕便签
  ElMessage.success('已退出登录')          // 2. 给个反馈
  router.push('/login')                  // 3. 再送回登录页
}
```

**④ 逐行拆解** ——

- `removeItem('loginUser')`：只删这一个键，主题、草稿这些其它缓存不受影响。
- 顺序：**删 → 提示 → 跳**。删必须在跳之前，这是整个退出功能唯一容易写反的地方。
- `ElMessage.success`：退出不是错误，别用 `error`；提示条会跟着页面切换保留一两秒，用户能看到。
- `router.push('/login')`：留一条历史记录，用户点"后退"能回到 `/manage`——但守卫会立刻把他弹回登录页，所以**功能安全、体验不优雅**；想连历史一起抹掉用 `router.replace('/login')`。
- 按钮的两种写法：讲义是顶部 `el-button`，仓库把它放在左侧菜单底部（`Manage.vue` 第 77~82 行），用 `el-menu` 的 `@select` 触发——`index="logout"` 不是真路由，只是给菜单项一个标识。
- 真正让"退出后进不去"的不是这个函数，而是 2.7 的守卫；函数只负责把凭证删干净。

**⑤ 在你仓库里** —— 按钮在 `D:\my-project\xm-pro\vue\src\views\Manage.vue` 第 77~82 行，函数在第 112~116 行；守卫在 `...\src\router\index.js` 第 39~48 行（它才是"退出后进不去后台"的原因）；写入同一个键的地方在 `...\views\Login.vue` 第 39 行。**如果只删了键却没有守卫，退出后照样能点回 `/manage`**——两处要一起改。

**⑥ 常见坑** —— ① 退出后点浏览器"后退"又回到后台页面 → `push` 留下了历史，且组件可能还在缓存里 → 改用 `router.replace('/login')`，或在 `Manage.vue` 的 `onMounted` 里再校验一次。② 退出后个人信息还在 → 只跳转没删键，或删的键名写错 → 在 Application 面板确认 `loginUser` 真的没了。③ 图省事用了 `localStorage.clear()` → 把同域名下别的业务键一起清掉 → 只 `removeItem` 自己的键。

**⑦ 自测** —— 为什么 `removeItem` 一定要在 `router.push('/login')` 之前执行？把顺序调换，页面会怎么表现？

<details><summary>展开解析</summary>

`router.push` 会立即触发守卫，守卫读的是**执行到那一刻**的 localStorage。顺序反了，守卫读到的还是旧的 `loginUser`，判定"已登录"，于是放行到 `/manage`；等 `removeItem` 执行完，人已经在后台页面里了，看起来就像"退出没反应"。更隐蔽的是：这时刷新一下才会被踢出去，学生会误以为是"缓存问题"。

</details>

### 2.9 登录态的本质：HTTP 没有记忆

**① 讲义怎么说** —— 功能说明第 5 条把这一讲的做法说得很直白："**用 `localStorage` 存登录标识，未访问 `/manage` 后台路由自动跳登录页**"。注意措辞是"登录**标识**"，不是"登录**凭证**"——这个区别就是本节要讲的。

**② 一句话讲透** —— HTTP 是**没有记忆**的协议：每个请求都是陌生人敲门，服务器处理完就忘。所谓"登录态"，本质是让服务器在下个请求里还能认出你的一件东西——传统做法是 cookie 带 `JSESSIONID`、服务器查 session；现代做法是 header 带 token、服务器验签。本讲两者都没有：`localStorage` 里的 `loginUser` **只存在浏览器里**，一个字节都不发给后端。所以现在的"登录"是前端自己记张便签、自己看一眼；后端完全不知道谁在调它。这叫**前端自证**，解决体验，不解决安全。

**③ 示例代码** ——

```bash
# 不登录、不带任何凭证，直接调后台接口
curl http://localhost:8080/user/list

# 依然返回 {"code":"200","msg":"请求成功","data":[...]}
# 后端根本没问过你是谁
```

**④ 逐行拆解** ——

- 这条命令证明：**接口层没有鉴权**。浏览器里"没登录进不去"只是路由守卫拦的，绕过前端就没有任何阻拦。
- 那 `localStorage` 到底解决了什么：**刷新页面不丢登录人**（内存变量会丢）、**多个页面共享**（顶栏、首页、个人中心都读它）、**不用每次输密码**。它解决的是"连续性"。
- 真正的登录态要四步：登录成功时后端签发 token（或写 session）→ 前端存起来 → **每个请求都带上**（在 `request.js` 的请求拦截器里加 `config.headers.Authorization = ...`）→ 后端用 Filter/Interceptor 校验，不合法直接 401。
- 本讲为什么不做：目标是"跑通登录这条链路"，token/JWT 涉及签名、过期、刷新，放到后面；但**心里要有一张"还差什么"的清单**。
- 一个三十秒的自检：F12 → Application → Local Storage，把 `loginUser` 的值改成随便一个字符串，刷新 `/manage`——你依然进得去。这就是"前端自证"的边界。
- 顺手看 `UserMapper.xml` 第 8~10 行的 `#{}`：它是预编译占位符，值不会被拼进 SQL，这挡住了 SQL 注入；但它挡不住"没登录也能调接口"，两件事别混为一谈。

**⑤ 在你仓库里** —— `D:\my-project\xm-pro\vue\src\utils\request.js` 第 10~15 行的请求拦截器只设了 `Content-Type`，**没有 `Authorization`**；`...\controller\UserController.java` 第 22~29 行的登录方法只查了一次库，**没有签发任何 token**；`...\src\router\index.js` 第 41~47 行的守卫只读 `localStorage`，**不问后端**；`...\common\Result.java` 第 6~8 行的三个字段里也没有 token 的位置。四处一起看，就能看出这套登录"缺哪一块"。

**⑥ 常见坑** —— ① 以为"菜单藏起来、按钮不显示"就是权限控制 → 前端只是不给入口，接口照样能被调 → 权限必须做在后端接口上。② 把 `password` 一起存进 `localStorage`（现在就是这么存的，因为 `res.data` 是整个 `User`）→ 任何 XSS 或共用电脑都能直接读到明文密码 → 存之前把 `password` 置空，或只存 `{id, username, name}`。③ 改完密码后旧标签页还能继续用 → 没有失效机制 → 真实系统改密后要让 token 失效并强制重登。

**⑦ 自测** —— 如果后端完全不认登录态，那 `localStorage` + 路由守卫这套东西，到底解决了什么问题、没解决什么问题？

<details><summary>展开解析</summary>

**解决了**：刷新后还记得登录人、多页面共享登录信息、未登录者点后台入口会被温和地送回登录页、退出后能回到登录页——全是体验层面的问题。**没解决**：接口仍然对所有人开放，任何人用 curl、Postman 或在控制台改一下 localStorage 都能拿到数据，密码还以明文形式躺在浏览器里。所以它是"门帘"，不是"门锁"；真正的门锁要在后端每个接口上校验 token/session。

</details>

### 2.10 登录失败为什么不用抛异常

**① 讲义怎么说** —— 功能说明第 4 条："**全局异常兼容：密码错误直接返回 `Result.error`，不需要抛自定义异常也能正常弹窗**"。第 7 讲已经建了 `GlobalExceptionHandler` 和 `CustomException`，不少同学会以为"所有错误都要 throw"，讲义这句话正是在纠正这个误解。

**② 一句话讲透** —— 错误分两类，处理方式完全不同。**一类是预料之中的业务结果**：账号密码不匹配、账号已存在、旧密码错——不是程序坏了，是用户输入不对，属于正常分支，直接 `return Result.error("400", "...")`，前端拿到 code 弹提示就完事。**另一类是预料之外的故障**：空指针、除零、数据库连不上——不该由每个方法处理，`throw` 出去，让全局处理器统一兜底成 500 并打日志。打个比方：业务错误是"挂号时告诉你这科没号"，一句话解决；系统异常是"手术中途停电"，必须拉总闸、记录、上报。

**③ 示例代码** ——

```java
// 业务错误：直接返回，前端能预期，不打堆栈
if (loginUser == null) {
    return Result.error("400", "账号或密码错误");
}

// 系统异常：不在这里处理，交给 GlobalExceptionHandler 兜底（log.error + 500）
int x = 1 / 0;
```

**④ 逐行拆解** ——

- `Result.error("400", msg)`：`code` 用 `"400"` 是课程约定，表示"业务参数 / 校验错误"，**不是 HTTP 400**。
- 不抛异常最实际的好处：**没有堆栈**。业务错误一天几百次，每次都打一整屏堆栈，日志会被淹没，真故障反而找不到。
- 该抛的时候要抛：只有"这个方法没法继续、也不知道怎么告诉用户"时才 `throw`；`CustomException` 适合"规则复杂、在 Service 深处才发现"的场景（第 12 讲账号判重就是），Controller 里一眼能判断的，直接 return 更清楚。
- `GlobalExceptionHandler` 的 `@ExceptionHandler(Exception.class)` 兜住所有漏网异常，返回 `Result.error()`（`code="500"`），并 `log.error("系统异常", e)` 打出完整堆栈——**堆栈该出现在这里**。
- 两条路对前端是**一样的**：都是 `{code, msg, data}`，`Login.vue` 第 42 行 `ElMessage.error(res.msg)` 都能弹。这就是"全局异常兼容"的意思。
- 判断标准一句话：**这段代码"知道该对用户说什么"就 return，不知道就 throw。**

**⑤ 在你仓库里** —— 登录判空的返回在 `D:\my-project\xm-pro\springboot\src\main\java\com\example\controller\UserController.java` 第 25~27 行；全局兜底在 `...\exception\GlobalExceptionHandler.java` 第 16~21 行（`@ExceptionHandler(Exception.class)` + `log.error("系统异常", e)`），自定义异常分支在第 24~29 行；第 12 讲会用到的 `CustomException` 在 `...\exception\CustomException.java`。同一个文件里两种写法并排放着，最适合对照阅读。

**⑥ 常见坑** —— ① 密码错误也在 Service 里 `throw new RuntimeException("密码错误")` → 被全局处理器接住，返回 `code="500"`、`msg="系统错误"`，前端弹的是"系统错误"而不是"密码错误" → 业务错误用 `Result.error` 返回具体 msg。② 反过来，空指针被就地 catch 后 `return Result.error("400", "参数错误")` → 真正的 bug 被掩盖，日志里没有堆栈，线上查不出来 → 预料之外的异常不要 catch，让它冒到全局处理器。③ `Result.error("400", ...)` 后面忘了 `return`，继续往下执行 `Result.success(...)` → 编译不过（有返回值）或逻辑错乱 → 每个分支都要有 return。

**⑦ 自测** —— 同样是"登录失败"，什么情况下该 `return Result.error`，什么情况下该 `throw`？

<details><summary>展开解析</summary>

**该 return 的**：账号不存在、密码错误、参数缺失——这些是"用户能看懂、能自己改"的结果，前端只要把 msg 弹出来，流程就结束了。**该 throw 的**：数据库连不上、`user` 表不存在、某个字段突然为 `null` 导致空指针——这些"用户改不了、开发要看日志"的故障，统一冒到 `GlobalExceptionHandler`，由它打堆栈、回 500。一句话：**面向用户的结论用 Result，面向开发者的故障用异常。**

</details>
