## 本次复核结论

1. **讲义有 2 处会直接卡住学生的硬错误**：①「三、2 配置 Maven」的镜像地址是 **http**，在 Maven 3.8.1 下会被 `maven-default-http-blocker` 拦死（实测 `Blocked mirror for repositories`，一个依赖都下不来）；②「四、2 配置数据库」正文里的 `application.yml` **`url:` 这一行没有缩进**，照抄就 `APPLICATION FAILED TO START`。
2. **有 4 处"讲义文字 ≠ 讲义截图/代码"**：`message` vs `msg`、`@RestControllerAdvice` vs `@ControllerAdvice+@ResponseBody`、"控制台打印完整异常日志" vs 代码里没有日志、正文说"单独捕获 CustomException 返回 400"但**没给这段代码**（照截图写实测返回 **500**）。
3. **有一条流传很广的旧结论需要推翻**：「`@ResponseBody` 返回 String 默认按 ISO-8859-1 编码，中文必乱码」——在**本讲义指定的 Spring Boot 3.5.16 下不成立**。实测 `/hello`（讲义原样代码、无任何额外配置）返回 `Content-Type: text/plain;charset=UTF-8`，中文正确；原理是 Spring Boot 自动配置用 `server.servlet.encoding.charset`（默认 UTF-8）去构造 `StringHttpMessageConverter`（源码见勘误 7）。仓库里那个 `WebConfig` **不是必需项**。
4. **讲义有 4 处环境/版本信息过时或没说清**：说装 MySQL 5.7 但实测是 8.0.43；`xm-pro`（带横线）库名与建库方式没讲清（实测连接报 `Unknown database 'xm-pro'`）；"启动后一般会失败，原因是没有配置数据库"这句只在"完全没配 url"时成立（连不上库也能启动成功）；`/number` 前后两个版本没说要不要改。
5. **讲义正确、不需要改的部分**也确认了：`pom.xml` 三个依赖与版本、"从 4.1.1 降到 3.5.16"、JDK21、IDEA 编码 UTF-8（含"不含 BOM"）、`Result` 四个静态工厂、异常处理的基本思路、`@JsonInclude` 之外的结构。
6. 旧文档需要更新的地方（不改旧文件，只在此说明）：`知识点精讲_实训7.md` 的 **2.25 节**、第 42 行、第 854 行、第 1400–1432 行仍然写着"String 走 `StringHttpMessageConverter`，默认 ISO-8859-1，必乱码 / 未修时 `Content-Type: application/json`"，与本次实测冲突，详见 `.extract/verify/errata-b-handoff.md`。

## 一、严重问题

### 勘误 1：Maven 镜像用 `http://`，Maven 3.8.1 会直接拦截（严重）

**【讲义原文】** 「三、配置 SpringBoot 工程 → 2. 配置 Maven」配图（docx 第 50 段配图，图内编号第 7 步"已配好镜像"）中的 `settings.xml`：

```xml
<mirror>
  <id>nexus-aliyun</id>
  <mirrorOf>central</mirrorOf>
  <name>Nexus aliyun</name>
  <url>http://maven.aliyun.com/nexus/content/groups/public</url>
</mirror>
```

同一张图里 `Maven 主路径(H)`、`用户设置文件(S)`、`本地仓库(R)` 都填的是 `D:\soft\apache-maven-3.8.1\...`。

**【问题】**
1. **镜像地址是 `http://`**。Maven 从 **3.8.1** 起在 `conf/settings.xml` 里内置了一条 `maven-default-http-blocker` 镜像（`mirrorOf=external:http:*`、`blocked=true`），任何走 http 的外部仓库都会被拦。讲义指定的就是 Maven 3.8.1，等于**一边让学生装 3.8.1、一边给一个 3.8.1 会拦掉的镜像**。
2. 该地址是阿里云**已停用的老 nexus 路径**，即使改成 https，也建议换成 `https://maven.aliyun.com/repository/public`。
3. `<mirrorOf>central</mirrorOf>` 只镜像 central；本讲义 pom 只用到 central，勉强够用，但推荐写 `*` 以免漏掉插件仓库。
4. 三个路径都写成老师机器上的 `D:\soft\...`，其中 `repo` 是老师本机已有的本地仓库；学生必须换成自己机器上的真实路径（这一点讲义配图没有提醒）。

**【实测证据 / 原理】** 用与讲义完全一致的 http 镜像 + 保留 3.8.1 自带的 blocker，清掉本地仓库里的目标 artifact 后重新解析：

```
[ERROR] Failed to execute goal ...:maven-dependency-plugin:3.8.1:get ...:
  Could not transfer artifact joda-time:joda-time:pom:2.12.5
  from/to maven-default-http-blocker (http://0.0.0.0/):
  Blocked mirror for repositories: [nexus-aliyun (http://maven.aliyun.com/nexus/content/groups/public, default, releases)]
```

对照组（只把 `http` 改成 `https`，其余完全一样）：`BUILD SUCCESS`，正常下载（`joda-time-2.12.5.jar (638 kB at 842 kB/s)`）。

复现材料：`.extract/verify/errata-b_mvn_http_settings.xml`、`.extract/verify/errata-b_mvn_https_settings.xml`。

**⚠️ 一个容易误判的细节**：如果本地仓库里**已经缓存**了要用的包，http 镜像"看起来是好的"（本次第一次跑就出现过"Downloading from nexus-aliyun: http://... → Downloaded (0 B at 0 B/s)"），一旦换机器/清缓存就全崩。判断标准只能是清缓存后重跑。

**【正确写法】**

```xml
<mirror>
  <id>aliyun-public</id>
  <mirrorOf>*</mirrorOf>
  <name>Aliyun Public Repository</name>
  <url>https://maven.aliyun.com/repository/public</url>
</mirror>
```

（仓库实际使用的配置：`D:\software\apache-maven-3.8.1\conf\settings.xml` 第 14–22 行。）

**【影响程度】** ★★★ 严重。表现是"pom 一片红、所有依赖下载失败"，初学者几乎不可能自己定位到"http 被拦"上；直接导致整个实训做不下去。

### 勘误 2：`application.yml` 正文里 `url:` 没缩进，照抄必启动失败（严重）

**【讲义原文】** 「四、启动 SpringBoot 工程 → 2. 配置数据库」（docx 第 75–81 段，逐段原样）：

```yaml
# 数据库配置
spring:
  datasource:
    driver-class-name: com.mysql.cj.jdbc.Driver
    username: root
    password: 123456
url: jdbc:mysql://localhost:3306/xm-pro?useUnicode=true&characterEncoding=utf-8&allowMultiQueries=true&useSSL=false&serverTimezone=GMT%2b8&allowPublicKeyRetrieval=true
```

紧接着第 83 段还特意提醒：**"而且要注意下面红框里的代码要对齐，要有缩进，尤其是最后一行，要缩进"**。

**【问题】** 正文代码块里前四行有缩进（`spring:` 顶格、`datasource:` 2 空格、下面三项 4 空格），**只有最后一行 `url:` 顶格**（用 python-docx 读出的原文就是这样：`'url: jdbc:mysql://...'`，前面 0 个空格）。YAML 的层级完全靠缩进表达，`url:` 顶格等于把它变成**根级属性** `url`（Spring Boot 不认这个属性），`spring.datasource.url` 也就**不存在**。

即：**讲义自己配的图片是对的（图里第 7 行 `url:` 与 `driver-class-name` 对齐），但同一节的正文文字是错的**。

**【实测证据 / 原理】** 把讲义正文这 7 行**逐字**存成 `errata-b_bad_application.yml`，用同一个 jar 启动：

```
--spring.config.location=file:...\errata-b_bad_application.yml

APPLICATION FAILED TO START
Description:
Failed to configure a DataSource: 'url' attribute is not specified and no embedded datasource could be configured.
Reason: Failed to determine suitable jdbc url
```

这个报错和**讲义自己给的那张"启动失败"截图（docx 第 70 段配图）一字不差**（"Failed to configure a DataSource: 'url' attribute is not specified…"），所以学生分不清"我是没配数据库"还是"我配了但缩进错了"——两种错长得一模一样。

**【正确写法】**（`url` 与 `driver-class-name` 同缩进，4 空格）

```yaml
# 数据库配置
spring:
  datasource:
    driver-class-name: com.mysql.cj.jdbc.Driver
    username: root
    password: 123456
    url: jdbc:mysql://localhost:3306/xm_pro?useUnicode=true&characterEncoding=utf-8&allowMultiQueries=true&useSSL=false&serverTimezone=GMT%2b8&allowPublicKeyRetrieval=true
```

**【影响程度】** ★★★ 严重。这是"照讲义抄 100% 失败"的错误，且报错方向（"没配数据库"）与真实原因（"缩进错"）错位。

## 二、一般问题（讲义文字与讲义代码/截图不一致）

### 勘误 3：`Result` 文档写 `message`，代码里是 `msg`（一般）

**【讲义原文】** 「五、统一返回包装类 Result → 2. 统一返回结果封装」（docx 第 112–120 段）：

> 新建common包，创建 Result 类，包含三个属性：
> `code`：状态码（200 成功、500 系统异常、400 业务异常）；
> **`message`：提示信息；**
> `data`：接口真实返回数据（Object 类型兼容所有数据）；
> …所有接口统一返回 Result 对象，前端只需固定读取 **`code`、`message`、`data`** 字段。

而同一节第 128–131 段的代码是：

```java
public class Result {
    private String code;
    private String msg;
    private Object data;
```

**【问题】** 文字写 `message`，代码写 `msg`。JSON 的 key 就是字段名，实测响应体是 `"msg"`。前端如果按讲义文字写 `res.message`，拿到的是 `undefined`，而且**不报错**、只在页面上显示空白/ undefined，很难查。

顺带：文字里的静态方法只列了三个（`success()`、`success(Object)`、`error(String code, String msg)`），代码其实有**四个**（另有 `error()`），讲义没提。

**【实测证据 / 原理】** 按讲义代码部署后请求：

```
GET /result  → HTTP 200  application/json
{"code":"200","msg":"请求成功","data":"测试统一返回包装类成功！"}
GET /number  → {"code":"500","msg":"系统错误"}     ← 键名同样是 msg
```

讲义自己的运行截图（第 193 段配图，`/number` 的运行结果）里也是 `"msg": "系统错误"`、`"data": null`，**与正文文字自相矛盾**。

**【正确写法】** 二选一，全局统一：
- 以代码为准（推荐，改动最小）：文档改成 `msg`，前端读 `res.msg`；
- 或者把字段名改成 `message`（同时改 getter/setter 和所有调用处）。

**【影响程度】** ★★ 一般。前端字段名对不上是最常见的"接口通了但数据显示不出来"。

### 勘误 4：全局异常处理器的注解，文字说 `@RestControllerAdvice`，截图代码是 `@ControllerAdvice`+`@ResponseBody`（一般）

**【讲义原文】** 「六、全局异常统一处理 → 1. 全局通用异常捕获」（docx 第 189 段）：

> 新建exception包，创建GlobalExceptionHandler全局异常处理类：添加注解 **`@RestControllerAdvice`、`@ResponseBody`**；捕获顶层 Exception…

同一段配图（第 191 段配图）里的代码却是：

```java
@ControllerAdvice("com.example.controller")
public class GlobalExceptionHandler {
    @ExceptionHandler(Exception.class)
    @ResponseBody  // 返回json串
    public Result error(Exception e) { return Result.error(); }
}
```

**【问题】**
1. 文字写的 `@RestControllerAdvice` 是**类级注解**，它本身 = `@ControllerAdvice` + `@ResponseBody`；如果按文字"再加一个 `@ResponseBody`"，是**冗余**的。
2. 截图代码用的是 `@ControllerAdvice("com.example.controller")` + **方法级** `@ResponseBody`，与文字不一致（两种都能跑，但学生不知道照哪个抄）。
3. 截图里把包限制成了 `com.example.controller`，这是"只拦 Controller 层"的写法，讲义没解释——以后异常从 Service 层抛出来，照样能拦（Controller 出口统一拦截），但概念上要说清。

**【实测证据 / 原理】** 仓库现有实现（`GlobalExceptionHandler.java:18`）用的是 `@RestControllerAdvice`，实测 `/number`、`/business` 均被正确拦截并返回统一 `Result`（见勘误 7 的响应对照）。

**【正确写法】** 统一写一种，推荐：

```java
@RestControllerAdvice          // 已经包含 @ResponseBody，方法上不用再写
public class GlobalExceptionHandler {
    @ExceptionHandler(Exception.class)
    public Result handleException(Exception e) { ... }
}
```

**【影响程度】** ★★ 一般。写法不统一，但两种都能跑；真正会坑人的是勘误 5。

### 勘误 5：正文说"单独捕获 CustomException，返回自定义 400"，但讲义没给这段代码——照截图写实测返回 500（一般）

**【讲义原文】** 「六、2. 自定义业务异常」（docx 第 196 段）：

> 新建 CustomException，继承运行时异常，自定义 code、message 属性；**在全局异常处理器中单独捕获 CustomException，返回自定义 400 业务错误码**；业务代码中手动抛出异常示例：`throw new CustomException("400","禁止请求")`。

讲义随后给的配图只有"新建包/新建类"的目录树（第 197 段配图，能看到 `CustomException`、`GlobalExceptionHandler` 两个文件），**没有任何一段 `@ExceptionHandler(CustomException.class)` 的代码**，也没有 `CustomException` 类的代码。

**【问题】** 学生按讲义现有代码抄（全局处理器里只有 `@ExceptionHandler(Exception.class)` 一个分支），`throw new CustomException("400", ...)` 会被**更宽泛的 `Exception` 分支**接住，返回的是 `code=500`，不是 400 —— 与本讲"业务异常 400 / 系统异常 500 要区分开"的教学目标相反。

**【实测证据 / 原理】** 实验工程里把处理器**只留** `@ExceptionHandler(Exception.class)`（即讲义截图的写法），业务接口抛出 `CustomException("400","禁止请求")`：

```
GET /business → HTTP 200
{"code":"500","msg":"系统错误"}          ← 期望 400，实际 500
GET /number   → HTTP 200
{"code":"500","msg":"系统错误"}          ← 对照
```

补上专用分支（仓库写法 `GlobalExceptionHandler.java:40-44`）后：

```
GET /business → {"code":"400","msg":"禁止请求"}   ← 正确
```

**【正确写法】**

```java
@ExceptionHandler(CustomException.class)     // 更具体的异常类型优先匹配
public Result handleCustomException(CustomException e) {
    return Result.error(e.getCode(), e.getMsg());
}
```

**【影响程度】** ★★ 一般。代码"能跑"，但行为与讲义文字相反，学生会以为 400/500 区分机制没生效。

### 勘误 6：正文说"控制台打印完整异常日志"，截图的代码里根本没有日志（一般）

**【讲义原文】** docx 第 190 段：

> 控制台打印完整异常日志，方便定位代码报错行。

同一节配图（第 191 段）的处理器代码：

```java
@ExceptionHandler(Exception.class)
@ResponseBody
public Result error(Exception e) {
    return Result.error();          // ← 没有任何 log
}
```

**【问题】** 文字承诺"打印完整异常日志"，代码里连 `Logger` 都没有 import；学生照抄后控制台**什么都看不到**，真出异常时会怀疑"异常被吞了"。

**【实测证据 / 原理】** 以讲义代码起服务后请求 `/number`（1/0），服务端控制台除启动日志外**没有**异常堆栈输出，响应体仍是 `{"code":"500","msg":"系统错误"}`。

**【正确写法】**（仓库 `GlobalExceptionHandler.java:21,27-31` 的写法）

```java
private static final Logger log = LoggerFactory.getLogger(GlobalExceptionHandler.class);

@ExceptionHandler(Exception.class)
public Result handleException(Exception e) {
    log.error("系统异常：{}", e.getMessage(), e);   // 第三个参数 e 让堆栈一起打出来
    return Result.error();
}
```

**【影响程度】** ★★ 一般。"看不到日志"会把简单问题拖成玄学排错。

## 三、提示 / 过时 / 没说清

### 勘误 7：⚠️ 旧结论推翻——"`@ResponseBody` 返回 String 默认 ISO-8859-1、中文必乱码"在本讲义版本下**不成立**（提示，但很重要）

**【讲义原文】** 讲义正文**没有**讲过这件事（全文没有"乱码/编码/ISO"字样），只有「四、3 写一个接口」给出这段代码（docx 第 91–100 段）：

```java
@RestController
public class WebController {
    @GetMapping("/hello")
    public String hello() {
        return "Hello 安徽中医药大学！";
    }
}
```

第 102 段配图是浏览器访问 `http://localhost:8080/hello` 的结果：**"Hello 安徽中医药大学！"，中文完全正常**。

**【问题】** 本仓库长期流传一条结论（`WebConfig.java` 注释、`知识点精讲_实训7.md` 2.25 节、`实验过程_实训7.md` 附8 第 2 条）："`@ResponseBody` 返回 String 走 `StringHttpMessageConverter`，它默认 ISO-8859-1，中文必乱码，所以要加 `WebConfig` 改成 UTF-8"。**这条在 Spring Boot 3.x（本讲义 3.5.16）下不成立**，需要按版本更正。

**【实测证据 / 原理】**
实验工程 = 讲义代码原样 + **删掉仓库后加的 `WebConfig`**，Spring Boot 3.5.16 / Spring 6.2.19 / JDK21，`java -jar` 起在 8081，按字节读响应：

| 接口 | 讲义写法 | 实测 Content-Type | 实测响应体（按 UTF-8 解码） | 字节证据 |
|---|---|---|---|---|
| `/hello` | `String hello()` | **`text/plain;charset=UTF-8`** | `Hello 安徽中医药大学！` | `48656C6C6F20E5AE89E5BEBDE4B8ADE58CBBE88DAFE5A4A7E5ADA6EFBC81`（"安"= `E5AE89`） |
| `/plain` | `String plain()` | `text/plain;charset=UTF-8` | `中药：霍山石斛，安徽六安霍山县` | UTF-8 严格解码通过、无 `?`（`3F`）出现 |
| `/map` | `Map map()` | `application/json`（无 charset） | `{"name":"安徽中医药大学","age":18}` | 字节仍是 UTF-8 |
| `/result` | `Result result()` | `application/json`（无 charset） | `{"code":"200","msg":"请求成功",...}` | 字节仍是 UTF-8 |

原因（回到 jar 里的源码，不是猜测）：
1. Spring **Framework** 层的 `StringHttpMessageConverter.DEFAULT_CHARSET` 确实是 `ISO_8859_1`（`spring-web-6.2.19-sources.jar` 的 `StringHttpMessageConverter.java:51`）；
2. 但 **Spring Boot 会自动配置一个 charset 取自 `server.servlet.encoding.charset`** 的实例：`spring-boot-autoconfigure-3.5.16-sources.jar` 的 `HttpMessageConvertersAutoConfiguration.java:77-88`：

```java
@Bean @ConditionalOnMissingBean
public StringHttpMessageConverter stringHttpMessageConverter(Environment environment) {
    Encoding encoding = Binder.get(environment).bindOrCreate("server.servlet.encoding", Encoding.class);
    StringHttpMessageConverter converter = new StringHttpMessageConverter(encoding.getCharset());
    converter.setWriteAcceptCharset(false);
    return converter;
}
```
3. `org.springframework.boot.web.servlet.server.Encoding` 的 `DEFAULT_CHARSET = StandardCharsets.UTF_8`（`spring-boot-3.5.16-sources.jar` 的 `Encoding.java:37`），且该属性默认没有配置 → 取 UTF-8。

所以：**不配 `WebConfig`，Spring Boot 3 下 String 返回值也是 UTF-8**，与讲义第 102 段截图"中文正常"完全吻合。

**【正确写法】** 讲义本身不用改。需要改的是仓库里的说法与代码注释：
- `WebConfig` **保留无害**（它把 `application/json` 也显式标上 `charset=UTF-8`，对老旧客户端更保险），但它的注释**不应**再写"不加就乱码"；
- 讲课正确说法：**"Spring Framework 原生默认 ISO-8859-1；Spring Boot 用 `server.servlet.encoding.charset`（默认 UTF-8）盖掉了这个默认值。想验证只需要 `curl -I` 看 `Content-Type`。"**

**【影响程度】** ★ 提示（对讲义而言）；★★★ 对仓库文档而言——这是个**结论性错误**，会误导学生"必须写一堆配置类"，也会让他们在答辩/笔试中答错。

### 勘误 8：JSON 响应的 `Content-Type` 不带 charset（提示）

**【讲义原文】** 讲义没有说明 JSON 响应的 `Content-Type`。

**【问题】** 实测 `/map`、`/result`、`/number`、`/business` 的响应头是 **`application/json`（无 `charset=` 参数）**，而 `String` 返回反而是 `text/plain;charset=UTF-8`，"哪个带 charset"和很多人的直觉相反。字节本身仍是 UTF-8（JSON 按 RFC 8259 强制 UTF-8），现代浏览器/axios 都会正确解析 —— 这一点要讲清楚，别让学生以为"没 charset 就一定会乱"。

**【实测证据 / 原理】** 见勘误 7 表格的 Content-Type 列；仓库修正版 `WebConfig.java:36-42` 通过 `setSupportedMediaTypes` 把 JSON 的类型换成 `application/json;charset=UTF-8`，这才是"加 charset"的效果来源 —— 它**不改变字节**，只改变响应头。

**【正确写法】** 讲义可补一句："返回对象时 Content-Type 是 `application/json`，JSON 规范默认 UTF-8，不加 charset 也能正确显示；要加则用 `produces` 或消息转换器配置。"

**【影响程度】** ★ 提示。

### 勘误 9：异常被统一处理后 HTTP 状态码仍是 200（提示）

**【讲义原文】** 「六、全局异常统一处理」只说 `Result` 里 `code=500/400`，未提 HTTP 状态码。

**【问题】** 学生容易以为"抛异常了浏览器会看到 500"。实测：`/number`（除零）、`/business`（业务异常）**HTTP 状态码都是 200**，只有响应体里的 `code` 是 500/400。前端必须按 `body.code` 判断，不能按 `res.status` 判断；写实验报告时"接口返回 500"的说法也要限定"业务码"。

**【实测证据 / 原理】** 

```
GET /number   → HTTP 200  {"code":"500","msg":"系统错误"}
GET /business → HTTP 200  {"code":"400","msg":"禁止请求"}
```

原理：处理器**正常返回了一个 `Result` 对象**，Spring MVC 认为请求成功；要让 HTTP 状态码也变，得用 `@ResponseStatus` 或返回 `ResponseEntity`。

**【影响程度】** ★ 提示。属于"前后端约定"的关键细节。

### 勘误 10：说要装 MySQL 5.7，实际参数/环境是 MySQL 8；`xm-pro` 库名与建库方式没说清（提示）

**【讲义原文】** 
- docx 第 7 段：「再安装Mysql5.7数据库，账号为root 密码为123456」；
- 第 8 段：「用Navicat中新建数据库：**xm-pro**（以后各类表就放在这个数据库里）」；
- 第 81 段 URL 里带 **`allowPublicKeyRetrieval=true`**（这是 MySQL 8 + `caching_sha2_password` 才需要的参数）；
- 第 82 段：「注意：数据库的名字一定要为自己的数据库名字…默认的是叫mysql」。

**【问题】**
1. **版本自相矛盾**：让装 5.7，却给 8.x 才需要的 `allowPublicKeyRetrieval`。本机实测服务端是 **MySQL 8.0.43**，默认认证插件 `caching_sha2_password`——说明老师实际用的就是 8.x，讲义文字过时。
2. **库名带横线**：`xm-pro` 在 SQL 里必须写成 `` `xm-pro` ``（反引号）。用 Navicat 图形界面建库没问题，但后期写 SQL/建表时一顺手就会语法错。讲义没有提示。
3. 仓库为了省事改成了 `xm_pro`（下划线），于是**讲义 URL（xm-pro）与仓库 URL（xm_pro）不一致**：谁照讲义抄 URL、却按仓库建库，就会连不上。

**【实测证据 / 原理】** 用 Connector/J 直连本机 MySQL（`errata-b_jdbc_probe.txt`）：

| 测试 | 结果 |
|---|---|
| 讲义 URL（`.../xm_pro?...&allowPublicKeyRetrieval=true`，库名换成实际存在的） | ✅ 成功，`catalog=xm_pro` |
| 去掉 `allowPublicKeyRetrieval` | ✅ 仍然成功（见下方"未证实"说明） |
| 去掉 `serverTimezone` | ✅ 仍然成功 |
| 讲义写的库名 `xm-pro` | ❌ `SQLSyntaxErrorException: Unknown database 'xm-pro'` |

**未证实项**：`allowPublicKeyRetrieval=true` 是否"必须"。MySQL 8 + `caching_sha2_password` + `useSSL=false` 在**首次全量鉴权**时确实可能报 `Public Key Retrieval is not allowed`，但本次实测去掉该参数仍能连（服务端已缓存 root 的认证结果），且不能为此重启 MySQL 服务去强制复现。**结论按"MySQL 8 建议保留该参数、MySQL 5.7 不需要"来讲，不要断言"一定必须"。**

**【正确写法】** 讲义把软件列表改成实际版本（MySQL 8.x），并加两句提示：
- 库名与 yml 里的 `url` 必须**逐字符一致**（`xm-pro` ↔ `` `xm-pro` ``，或统一用 `xm_pro`）；
- `allowPublicKeyRetrieval=true` 是 MySQL 8 的兼容参数，5.7 可以不加。

**【影响程度】** ★ 提示（但"库名不一致"会直接导致连不上库）。

### 勘误 11："启动后一般会失败，原因是没有配置数据库"——只对"完全没配"成立（提示）

**【讲义原文】** docx 第 69 段：「启动后一般会失败，原因是没有配置数据库：」+ 第 70 段配图（报错原文：`Failed to configure a DataSource: 'url' attribute is not specified and no embedded datasource could be configured. Reason: Failed to determine a suitable driver class`）。

**【问题】** 这句容易被理解成"数据库连不上就启动失败"。实测不是：**只要 yml 里配置了 `spring.datasource.url`，即使数据库根本连不上（端口写错、服务没开），Spring Boot 也会启动成功**，因为 HikariCP 是懒连接（第一次真正取连接时才报错）。反过来，"完全没配 url"才会在启动阶段就失败——这正是讲义截图那个错误。

**【实测证据 / 原理】** 
- 实验工程把 url 指向不存在的端口（`jdbc:mysql://localhost:3399/xm_pro?...`）：**启动成功**，`GET /hello` 返回 200；日志里只有 `Started SpringbootApplication in 4.085 seconds`，没有任何数据库错误。
- 用讲义正文那份缺缩进的 yml（等于没配 `datasource.url`）：**启动失败**，报错与讲义截图完全一致（见勘误 2）。

**【正确写法】** 讲义补一句："这里失败是因为**完全没配** `spring.datasource.url`；如果配了但连不上库，项目照样能启动，要等到第一次执行 SQL 才会报连接错误。"

**【影响程度】** ★ 提示。这个认知差异会直接影响学生排查"启动成功但查不出数据"的方向。
